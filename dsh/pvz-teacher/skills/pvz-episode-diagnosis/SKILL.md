# 诊断一局输掉的 PvZ 对局

## 顺序不能颠倒

1. **`capture` 落盘。** 没有存档，后面什么都做不了。
2. **`index` 看哪里值得看。** 它是**目录**，不是结论 —— 它告诉你哪几路有问题，
   不告诉你该改什么。
3. **`frame` / `lane` / `actions` 定位到具体某一步。**
   `actions --max_life` 找「种下去很快就死」的决策，这类失败是局部的、可归因的。
4. **`whatif` 做反事实回放。** 模拟器是确定性的，所以它给的是**精确**结果，
   不是估计。这一步之前的所有说法都只是猜测。

## 别做的事

- **别拿 `narrative` 下结论。** 它压缩过，只能当线索。
- **别在没跑 `whatif` 之前说「这样改应该有用」。** 「应该」不是证据。
- **别用规则去推「该改哪一步」。** 规则能告诉你在哪条路、哪一段时间找，
  但「把这一株往右挪 4 格」这种事规则推不出来，回放能精确算出来。

## 关于动作写法

`whatif` 的 `try` 参数写法、植物 id 表、行列范围，都在资源 `pvz://vocabulary`
里。**不确定就去读，别猜 id** —— 猜错不会报错，会静默拿另一个植物的结果。

## 关于数值

血量、花费、冷却、引爆时间、tick 与秒的换算，在资源 `pvz://constants` 里，
从 C++ 源码现场解析。**这是另一个实现，不要用通用 PvZ 常识替代。**

## 证据

```pvz-evidence
kind: procedure
rationale: 顺序不能颠倒，因为 whatif 之前的每一步都只产出「候选」而不是「结论」——
  index 是规则生成的候选，narrative 是压缩过的候选，规则能覆盖的失败方式本来就有限
  （原版 render_episode 写死规则，漏掉了植物类型选错、位置太靠前、资源花在错的地方）。
  所以「先落盘 → 再定位 → 再回放」不是流程洁癖：跳到最后一步就没有可回放的靶子，
  停在中间一步就只能拿到猜测。这条 rationale 本身是可被反驳的 ——
  如果存在某种失败方式，不跑 whatif 也能从 index 直接读出确定的结论，
  那这个顺序就该改。
```
