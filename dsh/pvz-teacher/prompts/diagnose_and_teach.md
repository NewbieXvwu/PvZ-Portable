# 任务模板：诊断一局 + 把判断写成 skill

用法：把下面 `---` 之间的内容整段贴给 `dsh`，替换 `<SEED>` / `<OUT>` / `<SKILLS_DIR>`。

设计依据：S3（2026-10-03）跑完发现，模型在最终回答里给出了 4 条「可复用的判断」，
但**一条 skill 都没写** —— 推理轨迹里 `skill` 这个词出现 **0 次**。
原因不是它没内容，是**没有判据**。所以这份模板把判据写进去，
并且把「不写」变成一个有理由的、必须显式给出的决定。
S4（2026-10-03）验证判据有效后又暴露了新问题：模型强烈倾向「单点通关改动」
—— 把操作数压到最小、找一步刚好够用的替换。这与任务的真实目标相反，
所以下面先讲清楚**我们在产出什么**。

---

第 `<LEVEL>` 关、随机种子 `<SEED>` 这一局，用默认（脚本）策略打的结果是**输**。
你的任务有两件，**第二件是重点**。

## 你在产出什么（先读这段再动手）

**目标不是"让这一局勉强通关"，是产出能拿去教策略的数据。**
一步改动、刚好够用、赢了也说不清为什么 —— 这样的数据教不了任何模型。
我们真正要的是：

1. **策略的缺陷模式**：这个脚本策略在决策规则层面缺了什么/错在哪
   （它看不到的东西？它顺序不对的优先级？它写死却不该写死的阈值？）。
2. **可迁移的判断**：换一局还成立的机制（判据见第二部分）。
3. **有证据的结论**：每个判断后面都有 whatif 反事实，
   而且不止一个决策点。

「把第 N 步的 X 改成 Y，通关」如果只是恰好补上了这一个洞，
它是一条**探针结果**（probe），不是答案 —— 它的价值在于回答
"这个策略的规则层缺了什么"，而不在它自己。

## 一、诊断这一局的策略缺陷

- 工具就是你的眼睛。**不要凭游戏常识猜**，所有判断都要有工具输出支撑。
  工具怎么用，看它们的描述。动作语法与植物 id 在资源 `pvz://vocabulary`，
  游戏常量（血量/花费/冷却/引爆时间/tick 与秒的换算/地形与卡组约束）
  在 `pvz://constants` —— **这是另一个实现，不要用通用 PvZ 常识替代**。
- 存档请放在 `<OUT>` 下面（自己建目录）。
- **不要在"找一步改动"上停**。单点改动只是探针：用它验证你的机制假设，
  然后回答"策略规则层缺了什么"。如果同一个改法在多个同类决策点上都有效，
  这才是证据；如果只有一点有效，说明它是局部补丁，说清它为什么不能推广。
- 如果整局是**结构性**的（卡组覆盖不了地形、某几路物理上没有防线），
  这本身就是一个重要发现 —— 说清结构、验证它、评估"换卡组还是换规则"。
  **「没有能通关的改动」是一个合法答案，比编一个强。**
- 如果试了几轮都没有进展，**直接说「卡住了」**，并说明你觉得是工具给的信息不够，
  还是这局确实没救。不要为了显得有进展而报一个你没验证过的改动。

## 二、把值得留下的判断写成 skill

**这一件比第一件重要。** 一次性答案（「这一局把第 N 步改成 X」）只对一局有用；
可复用的机制才对后面的局有用。注意：**"最小操作数的改法"不是加分项** ——
我们评估你的产出看的是可迁移的判断有几条、证据有多硬，
不是你找到的改动有多小。

但**不是每一局都值得写 skill** —— 大多数局没有。所以先过判据，再决定写不写。

### 判据：三问，全过才写

1. **反例问**：这条判断在什么情况下**不成立**？
   答不出来 ⇒ 它不是判断，是复述。
2. **证据问**：它在**至少 2 个不同的决策点**上被 `whatif` 验过吗？
   只有一个点 ⇒ 可能是运气。（实测过：同一类改动，某个落点通关，隔壁落点反而更差。）
3. **迁移问**：它的判据**换一局还能算出来**吗？
   判据里出现本局的坐标 / 决策号 / seed ⇒ 这是一次性答案，不是 skill。

### 四类产出，四个去处

| 产出 | 特征 | 去处 |
|---|---|---|
| **机制** | 三问全过 | 写 skill，`kind: mechanism` |
| **手法** | 第 1 问答不出（不可证伪），但顺序有理由 | 写 skill，`kind: procedure`，必须写 `rationale` |
| **假设** | 第 1 问过、第 2 问不过 | **不写**。留在回答里，或写进已有 skill 的「待验证」段 |
| **一次性答案 / 工具注记** | 第 3 问不过 | **不写**。该改的是工具或文档，不是 skill 库 |

**负结论同等对待**：验证出「某类做法无效」也算知识，但只有在**说出机制**
（为什么无效）时才算；只说「改 X 没用」不算。

### 怎么写

skill 写在 `<SKILLS_DIR>/<名字>/SKILL.md`：

- frontmatter 必须有 `name`（**与目录名一致**）和 `description`。
- 正文写规则本身。
- **必须带一个 ` ```pvz-evidence ` 块**：

  ```
  kind: mechanism
  claim: 一句话说清这条机制
  falsifier: 什么情况下它不成立
  point: <存档目录> | <决策号> | <改动前> | <改动后> | <结果>
  point: ...
  ```

  `kind: procedure` 则换成 `rationale: 为什么是这个顺序`。
  `claim` / `falsifier` / `rationale` 可以折行（缩进的续行接到上一个字段），
  `point` 必须一条一行。`改动前` / `改动后` 用 `whatif` 的写法
  （`plant:packet:row:col` / `wait:ticks` / `shovel:row:col`）。

### 可选：把它写成能自动跑的条件

如果这条机制的判据**能只用工具本来就在显示的那些量表达出来**
（火力、最前僵尸距离、植物类别、这株活了多久……），就在 frontmatter 里加一个
`probe` 块，它就能被自动跑在之后的每一局上，把可疑的局挑出来 —— 你今天看的
这一局是抽样，有了它，几万局都能先筛一遍再决定给不给你看。

```
probe:
  action_type: plant
  plant_role: [producer, shooter]
  lane_front_zombie_x_max: 260
  plant_life_ticks_max: 600
```

**能写哪些字段：读资源 `pvz://probe-fields`（封闭词表，不许自己发明判据）。**
这条限制是有意的：一份能自由发挥的"条件"会长成第二个策略脚本 —— 那是把硬编码
塞回主线，正是我们要避免的。它只能**贴标签、挑局**，不能给策略出主意。

写法要点：

- 条件要在**你自己的证据点**上命中 —— 不然它描述的不是你号称的那个现象。
- **必须给反例点**：`counterpoint: <存档目录> | <决策号>`，写在你觉得"这里不该
  被标红"的那一步上。散文写的反例机器验不了，等于没写。
- 反例点被标红（泛化过头），或证据点抓不到（条件比你的主张窄），闸门都会拒。
  被拒了要么改条件，要么**不写 probe** —— 那条机制仍然留在报告里当叙述，
  只是不变成自动筛子。这也是正常结果。

### 写完必须过闸门

调 **`lint_skills` 工具**，`dir` 填 `<SKILLS_DIR>`。

> 为什么是工具而不是命令行：隔离层里**没有命令执行能力**（`tool-bash` 是关的，
> 那是答案泄漏的通道）。所以闸门做成工具 —— 它是你唯一的检查入口。

它会去存档里核对：证据里的决策号必须存在，`改动前` 必须与那一帧**真实做出的动作**一致。
**对不上就是编的** —— 存档是原局跑出来的，你改不了它。

返回 ✗ 时按它说的补证据；**别把没过闸门的 skill 留在库里。**

### 如果这局没有够格的判断

**明确写出来**，不要沉默。这是正常结果，不是失败：

```
本局无新增 skill。
落选的判断：
  - <判断 1>：卡在第 2 问（只在决策 N 上验过）
  - <判断 2>：卡在第 1 问（说不出反例 —— 它是描述，不是机制）
```

写一条够不上闸门的 skill 才是失败：它会留在库里，被后面的局当成事实读。
