# task262：同卡组重点配额与 L29 起点前推

已在 `focuscells` 完成代码与配置，基线为 `ec539401`（pkg238）。两项新增份额默认均为 **0**，保留现行课程行为。建议审过后同时设为 **0.25**。本次未跑对局、未连接台式机、未部署。

## 1. 改动与参数

`scripts/curriculum_queue.py::plan_round` 增加两类内部预留配额，复用现有任务解析、种子偏移与起点恢复。普通类别继续调用现有 `allocate`。新增类别按 `last_round`、格名顺序轮转，每格最多 `games_per_group // FLOOR_SHARE`，生产参数下为 24 局。已完成组扣除相应配额，当前轮已完成的格跳过，续跑保持总预算上限。

| 参数 / 配置键 | 默认 | 建议启用值 | 含义 |
|---|---:|---:|---|
| `--focus-share` / `focus_share` | 0 | 0.25 | 从随机卡组主配额划给重点格的比例 |
| `--l29-start-share` / `l29_start_share` | 0 | 0.25 | 示范起点主配额中预留给两条 L29 起点的比例 |
| `--focus-manifest` | `configs/curriculum_focus.json` | 同左 | 重点格与 L29 起点清单 |

`qc_launch.py` 默认读取其随版本安装的 `configs/curriculum_focus.json` 两个份额，并将清单路径指向生产工作树。显式启动参数覆盖配置。配置内置值均为 0，两个参数归零即可关闭。持久启停以配置为准，部署与看门狗重启都会读取。直接运行课程队列时，两个份额的命令行默认仍为 0，清单中的份额值由共用启动器传入。

八个重点格为 `pool_user_l22_user`、`pool_user_l29_user1`、`pool_user_l29_user2`，以及 `fog_good_l32_train`、`fog_good_l34_train`、`fog_good_l36_train`，再加 `roof_user_l47_user` 与 `roof_user_l49_user`。启用后这些格从普通倍率池划到重点类别，每轮共 48 局，即两格各 24 局，约四轮覆盖八格。它们沿用门禁对应的同卡组任务，仍在各自当前课程倍率采集，倍率阶梯和升降档规则未改。

L29 起点为 `user_l29_0257d51bd462_start` 和 `user_l29_c08db8116248_start`。启用后每轮各 24 局，其他示范起点共享剩余 144 局。按 task261 的 128 个起点口径，均匀轮转时两格合计约 3 局/轮，改为固定 48 局/轮，轮转机会约为原来的 16 倍。当前晚盘若继续通过 >85% 的晋档线，便能逐轮向更早决策点移动。

**前推范围受原阶梯限制。** 两条 task253 阶梯最早分别为决策 739 与 486，约为原录像的 46%。本次保留这些阶梯，也保留 task71 的至少 8 局、>85% 升档和 <50% 降档规则。因此能更快到达已有最早档，无法直接推进到第 1 波。更早档需要另行取得可接手证据后登记，不在本任务内。

## 2. 每轮配额与实际局数

下面以生产参数 `round-games=768`、`games-per-group=48`、随机份额 0.25、示范份额 0.25、短题份额 0.05，以及八个开局专项为口径。建议同时开启两项 0.25。

| 主预算类别 | 现状 | 启用后 | 变化 |
|---|---:|---:|---:|
| 动态随机卡组 | 192 | 144 | −48 |
| 重点同卡组独立配额 | 0 | 48 | +48 |
| 示范起点共享配额 | 192（含两条 L29） | 144（其他起点） | −48 |
| L29 起点独立配额 | 0 | 48 | +48 |
| 短题配额上限 | 38 | 38 | 0 |
| 开局专项 | 192 | 192 | 0 |
| 普通倍率余额 | 154 | 154 | 0 |
| **主预算合计** | **768** | **768** | **0** |

154 是按类别上限计算的余额，普通格原来包含八个重点格，启用后这八格由独立配额负责。主预算分配为上限，未用足的类别份额仍按已有规则留给普通倍率格，实际局数还受组宽、已采轮次、种子和存档可用性影响。

用 52 个普通格、43 个随机格、128 个示范起点、90 个短题和八个开局专项构成轻量分配样本，各格均有种子且到达保底轮转时间。只调用规划函数，得到以下实数：

| 实际规划类别 | 现状 | 启用后 |
|---|---:|---:|
| 动态随机卡组 | 192 | 144 |
| 重点同卡组 | 包含在普通倍率格中 | 48 |
| 其他示范起点 | 192（此轮未轮到 L29） | 144 |
| 两条 L29 起点 | 0 | 48 |
| 短题 | 36 | 36 |
| 开局专项 | 192 | 192 |
| 普通倍率格 | 144 | 144 |
| **实际主局数** | **756** | **756** |
| **预算余量** | **12** | **12** |

现有分配器按组宽取整，因此该样本留下 12 局，前后逐项变化符合预期。没有为填满预算新增尾组逻辑。

**额外复习局单独计算。** 现行 `review_share=0.25` 会在主预算之外，为非 1 倍组追加 `ceil(组局数 × 0.25)` 局 1 倍复习，原样保留。因此总采集量可以超过 768，task261 的随机卡组实际占比 28.3% 也包含这些组。这里的 0.25 从 192 局随机主配额划出 48 局，并非直接从实际采集占比乘算。如果替换的随机组与重点组均为非 1 倍，两组 24 局各带 6 局复习，约转移 60 局实际采集量。示范池转给 L29 的是 1 倍起点，若替换掉原有非 1 倍起点，其额外复习量会相应减少。缺少上线时各格倍率和轮转状态，不能承诺每轮复习局数完全相同。

组边界若位于轮中，已完成的随机组无法追回，第一段续跑仍受剩余预算约束。完整新轮才对应上表的目标分配。

## 3. 雾 / 屋顶执行先验与能力转移

本次不改路由。`search_play.py::_terrain_policy`（约第 111 行）在雾、屋顶和 Boss 上选取 `gptbc_s1`。`main` 约第 975 行将选择结果写回 `args.rollout_policy`，随后 `_load_nets` 与工作进程初始化都使用该路径，实际执行动作和 C++ 搜索续走共享这份先验。现任晋升不会自动更新固定的 GPT 克隆模型。

因此新增的雾 / 屋顶配额增加的是 GPT 先验及搜索所到达局面的训练样本。采集帧保留实际执行动作 `action` 和搜索标签 `label`，完成组通过 `curriculum_queue.py::pack_labels`、`TrainingPipeline.enqueue` 并入既有训练配方。本次没有改训练来源权重，局数也不能直接当作训练行权重。这些样本有机会把同卡组解法蒸馏给现任学生，采集胜率本身不能证明学生已学会，更无法覆盖现任独立执行时特有的失败局面。最终能力仍由既有纯学生门禁衡量。

`beta` 只控制搜索动作的执行概率：0 执行路由后的先验，0.5 混合先验与搜索，1 执行搜索。调 beta 无法把 GPT 先验换成现任。队列的选择点在 `curriculum_queue.py::_run_group`（约第 2475 行），参数为 `--beta-threshold`、`--starved-beta` 和 `--probe-interval`。最终动作切换在 `search_play.py` 第 635–638 行，搜索标签继续保留。

后续若让这些格使用现任，有两种改动范围，均只列方案：

- **同时更换执行与续走先验：** 在 `qc_launch.py::command` 的 `--rollout-policy-gpt` 入口或 `_terrain_policy` 增加指定任务的选择，使目标格使用现任路径。直接撤掉 GPT 参数会影响全部雾 / 屋顶 / Boss，范围过大。即使限定格子，换现任仍会同时改变候选先验与搜索续走，可能失去已有胜局、降低老师标签质量。课程窗口也混有旧 GPT 执行成绩，切换后的采集胜率需要按执行方区分。
- **现任执行、GPT 搜索续走：** 在 `search_play.main` 的策略选择处保留两个路径，在 `_load_nets` / 工作进程初始化中分开执行模型和导出给 C++ 的续走模型，再让 `_play` 的先验动作来自现任。C++ 搜索和帧存档继续复用。这样能采到现任的真实失误局面，同时保留较强续走，但会增加一份模型及模型身份管理，候选锚点和历史特征必须接到正确执行方，需做有限同卡组对照后再采用。

对于 L29 用户 1，老师从开局仍无胜局证据，重点整局加量无法单独解除冷启动。两条用户起点的优先轮转承担逐步前推的作用，不能把新增零胜局数当作解决证据。

## 4. 定向测试

## 5. 审阅后上线与回退

本分支的两个配置值保持 0。主控审过后，在准备上线的发布修订中将 `configs/curriculum_focus.json` 的 `focus_share`、`l29_start_share` 同时设为 0.25，再合入既有 deploy26 发布线。此设置是共用启动器的唯一持久来源，重启不会丢失。不需要复制部署脚本，也不需要重建游戏程序。

由主控在生产仓库取得审过的发布修订后，使用既有入口：

```sh
python3 scripts/deploy26.py --revision <审过且两项份额为0.25的发布修订>
```

deploy26 等待当前采集组结束，安装代码与 JSON 配置，保留现有状态、档位和偏移，然后调用共用启动器。第一轮可能从轮中续跑，按已完成组扣除配额，随后完整新轮采用目标比例。

参数回退为 `--focus-share 0 --l29-start-share 0`。持久回退应在发布配置中把两项份额恢复 0，再走同一组边界上线流程，保留已采样本和课程进度。若需撤回整个版本，使用 deploy26 的既有备份目录：

```sh
python3 scripts/deploy26.py --rollback <该次上线输出的备份目录>
```
