# task106：校验成本清查（只报告，不改代码）

用户 2026-10-26 要求：全面找出浪费时间的形式主义校验。规则见 AGENTS.md §6.5。

起因：llmplay `resume()` 在 GPT Pro 沙箱里把 191 份存档逐份串行重放，外部模型干等了几十分钟。而这些存档我们导入时本来就要全量重放。

## 范围

1. **生产 qc 流水线**（cq 工作树现行代码，deploy14c / fd1a0b61）：
   - 每组、每轮都会走到的校验：SHA、配置核对、窗口核对、预检；
   - 打包、训练前后的校验；
   - 选择面板的准备与校验（含 `validate_random_tasks` 起引擎）；
   - 门禁评估之外的附加检查；
   - 部署脚本 `qc_deploy*.sh` 的预检与 dry-run。
2. **LLM 通关包导入链**：`import_llm_run.py`、`adaptive_verify.py`、`takeover_scan.py`。
3. **llmplay 包运行时**：`export_archive`、自动交付、`robustness()`、`selfcheck`。也就是外部模型每局都会碰到的开销。
4. **其他常驻脚本**：`hf_sync.py`、`agent_pool.py`、Mac 标签导入、`loose_ends.py`。
5. **Agent 的工作习惯**：翻最近 3 天的任务书“结果”节和提交记录，统计验收、复跑、审计花了多少时间，例如：
   - 冷解压、断网容器、跨机器逐位比对；
   - 全机种子审计；
   - 反复重打包重测。

   列出最耗时的 10 项，并说明哪些不是任务书要求的。

- 它检查什么，在哪个文件哪一行。

- 频率：每局、每组、每轮、每次部署、每次续跑。
- 谁在等它：采集、训练、Agent、外部模型。
- 下游是否本来就会做同样的事。
- 建议四选一：保留、换便宜做法、改异步 / 并行 / 推迟、删除。

检查过、不值得动的（保留）：

- `validate_random_tasks`（d14c python/pvz_selection_refresh.py:92）：每个 selection 面板对 3 个随机族逐 seed 起引擎核卡组；round_000020 实测面板 12 cell × 25 局、3 随机族，工件落盘全程 ~2 s，引擎 reset 估 ≤2 min——成本可忽略，且它拦"卡组池/告警漂移"，保留。
- `hf_sync.py` 的 SHA256（:78,:95,:124,:156）：对 43 MB 级检查点全量哈希，单文件亚秒级、每 run 秒级总开销；是传输完整性闸门，保留。
- `import_mac_labels.py`（macpool）：ledger sha256 与磁盘核对（:47,:120），增量导入只在头部做一次，保留。
- `loose_ends.py`、`agent_pool.py`：只读巡检/调度记录，日志里无校验耗时，保留。
- 流水线内 manifest/receipt 的 file_sha 复核（curriculum_queue.py:971–1008）：全是小 JSON 的哈希，毫秒级，保留。

结论：真正"形式主义"级别的浪费集中在 **LLM 包链的重放复验重复**（#1 #2 #3，同一份存档最多被重放 3 次：
resume→导入→独立引擎抽验）和**部署失败循环**（#4）；生产 qc 流水线本身的校验（SHA/预检/面板）要么毫秒级、
要么是必要闸门，没有值得删的。Agent 工作习惯里最大的教训是 #8（参数未核对就跑统计）和 #10（重复读同一批证据），
都是流程问题而不是代码问题。
