# task149：游戏进程全线崩溃时，采集队列暂停，不再空转烧掉整轮

主控 2026-10-29 定。分支 `sysfail`，以 `origin/prodint` 为底（生产代码 deploy14p = `4beab441`）。

## 事故

2026-10-28 23:52–23:57，台式机更新显卡驱动替换了系统库。之后每个游戏进程一启动就报 `Inconsistency detected by ld.so: dl-setup_hash.c ... Assertion failed`。`curriculum_queue.py` 把每组都记成 `group skipped: incomplete/invalid game results: 0/24`，5 分钟内把第 37 轮 38 组全部“跑完”。结果是：
- 记了 `last_round`；
- 写了 `round 37 done ... 768 games`（实际 0 局有效）；
- 把一个没有新数据的训练任务排进了后台队列。

同一时间，后台的 r34 选拔与 r35 打包也因同一原因失败。

## 要做的

1. 识别“系统性失败”：例如连续 N 组（N=3）都是 0 有效局，或者失败用时远短于正常组。出现时队列停在组边界，不再继续空转。
   - 写一行清楚的日志；
   - 每隔几分钟用一组很小的探测（1 局）重试，恢复后自动继续；
   - 不把这些组算进 `last_round`，也不算进本轮完成数。
2. 整轮 0 有效局时，不入队后台训练。
3. 后台任务（选拔、打包、训练）因同类原因失败时，不消耗 task140 的有限重试次数，等探测恢复后再重试。
4. 测试：只用 `-k` 跑相关用例。Mac 上每次运行都加 `timeout 300` 和 `ulimit -f 2000000`，同一时间只开一个 pytest（AGENTS §6.5 第 8 条）。**禁止整套运行** `test_curriculum_queue.py`、`test_curriculum_pipeline.py`、`test_qc_resilience.py`。
5. 结论写在本文件末尾，推送 `sysfail`。部署由主控决定。

## 约束

- 不部署、不碰台式机生产。
- 不加自校验。

## 结论（2026-10-28，分支 `sysfail`）

基于 `origin/prodint` 的 `e2f8cc16` 完成，按小步提交并逐次推送：`423a9e58` 修正空组计数与空轮训练入队，`2542d3e7` 增加采集暂停和恢复探测，`cff9ab38` 接通后台故障恢复。

采集以连续 3 组 0 有效局作为暂停条件，计数写入状态，重启后保留。每 180 秒运行一次单 worker、1 局探测，使用晋升面板第一个任务和当前采集学生，结果与帧只写临时目录。退出码为 0 且得到 1 条 `won` 为布尔值的结果才恢复，正常输局同样证明引擎可用。探测不推进采集种子，不计入训练数据。恢复后重新安排当前轮，跳过已完成格并扣除其预算，失败组使用已经持久化推进后的新种子。

失败组仍保留错误记录供定位，0 有效局不会更新 `last_round`。轮末日志只统计成功组及其实际局数，无成功组时不排入后台训练。暂停期间遇到停止标志可结束，后台关闭会唤醒等待并保存可续跑状态。

后台捕获动态链接器报错、缺失共享库和 `SimulatorExited` 的稳定错误文本，与采集共用一个恢复探针。选拔准备、打包、训练、选拔与晋升评估发生这类失败后，保留同一快照等待恢复，不增加 `attempts`。已完成阶段继续复用既有标记。选拔子进程的标准错误保留，门禁与后台命令向上传递当次运行最多 8 KiB 的日志尾部，历史日志不会触发故障分类。普通任务失败继续使用原有次数限制，健康状态下的正常后台收尾保持不变。

相关定向用例已通过，覆盖连续空组后的同轮恢复、新种子不重复、暂停重启及停止、单局探测结果判定，以及五个后台阶段连续三次系统故障不消耗重试次数。既有普通后台失败限次、跨重启组记录与采集训练重叠用例通过。每次测试均使用 `-k`、`timeout 300` 和 `ulimit -f 2000000`，pytest 串行执行。Mac 既有选拔测试受 `/var` 到 `/private/var` 的临时目录软链影响，改用 `TMPDIR=/private/tmp` 后通过，未改动其业务逻辑。
