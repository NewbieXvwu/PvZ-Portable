## 0. 背景（10-09 已知事实）

- **v3**（`bc_finetune_level7_v3`）：从 GRU 行为克隆检查点出发，1M 决策 / 84 次更新 / 11.2 小时，
  评估 **84.38% → 92.58%**（+8.2 点，约 3.6σ）。**这是目前唯一站得住的结论。**
- **A/B**（`bc_kl_ab_v1`）：只把 `ppo.target_kl` 0.03→0.3，跑 100k。
  84.77% → 81.64%，但**统计上不显著**（两比例 z=0.95；配对符号检验 p=0.256）。
- **教训**：256 局的胜负噪声是 **±4.5 个百分点**。过去一直拿 1~3 点的差异下结论，**全在噪声里**。

**→ 你的第一优先级不是跑实验，是把尺子修准。**

## 1. 环境（务必逐条遵守）

- **非交互式 shell 读不到 `.bashrc`**（开头有 `case $- in *i*) ;; *) return;; esac`）。
  取环境变量必须：`eval "$(grep -E '^export (HF_TOKEN|PVZ_HF_REPO)=' ~/.bashrc)"`
- **python 用 `~/.venvs/ml/bin/python3`**（系统 python3 没装 torch / huggingface_hub）。

- **⚠️ GPU 独占**：起任何 CUDA 任务前先
  `nvidia-smi --query-compute-apps=pid,used_memory --format=csv` 确认空闲；
  **`pkill` 之后等 5 秒**（进程退出前 GPU 仍被占），否则 `CUDA error: device busy`。
- **⚠️ 训练实验必须串行**（PPO 阶段 GPU 95~100% 满载）。
  **但 PPO 阶段 CPU 几乎全闲（load≈1.0/20）→ CPU 任务可以并行跑，见 §2。**
- **⚠️ WSL 无客户端连接约 60 秒自动关机**，已挂 Windows 计划任务 `PVZWSLKeeper` 保活，**别动它**。
- **改 PPO 参数只能改配置 JSON**——`--ppo-epochs`/`--minibatch-chunks`/`--learning-rate`
  等 CLI 参数对研究配置**完全无效**（`pvz_research.py` 里没有 `args.ppo_*` 引用）。
  `--workers`/`--rollout-threads`/`--rollout-device` **一律不许传**（会 raise）。
- **先查磁盘**：`df -h ~`。每个 run 约 1~2 GB，**剩余不足 30 GB 就停止启动新 run 并报告**。

## 3. 轨道 A：不需要 GPU 的验证（先做，全程并行）

**每一项都要给出数字结论，写清楚数据来源（文件路径 + 字段名）。**

### A1 ★地基：把主指标从"胜负"换成连续指标
评估记录每局都有连续字段（`output/evaluations/update_*.json.gz` →
`seed_results.<mode>.<task>[]`）：

| 字段 | 含义 |
|---|---|
| `terminal_wave` | **推进到第几波**（1~30，30=通关）|
| `terminal_tick` | 局长 |
| `peak_offense` | 峰值火力 |
| `events.zombies_killed` | 杀敌数 |
| `events.sun_spent` | **花掉多少阳光**（花 0 = 根本没建防线）|
| `events.plants_eaten` | 被吃掉的植物 |
| `events.mower_triggered` | 割草机触发 |
| `action_counts` | 动作构成 |

**做**：提取**所有已有评估**（v3 的 10 个节点 + A/B 的 2 个节点 + `idle_control`）的连续指标；
**量化每个指标的噪声**（用同一节点的 greedy/sampled 两版，或 idle_control），
和"胜负"的标准误对比。
**产出**：**推荐主指标 + 它的噪声水平（多少局能达到 ±2 点以内）**。后面所有实验都用它。

### A2 ★地基：量出"学习信号里有多少是种子运气"
用 v3 的 10 个评估节点（同一批 256 种子），对每个种子看它 10 个节点的胜负序列。
- 算：**多少比例的种子"跨节点完全不变"**（从头赢到尾 或 从头输到尾）？
- 算：在策略明显变强那段（250k→1M），**多少种子翻转了**？
**产出**：一个数字——"训练里有多少优势信号是运气"。**这决定要不要换任务池。**

### A3 用连续指标重判 A/B + 重画 v3 曲线
- 昨天"v3 vs A/B 在 100k"的差异，换连续指标看还成不成立？
- v3 的 84.38%→92.58% 在连续指标下是否更平滑、更早能看出趋势？
- **定位转折点**：10 个节点里从哪个开始明显变好？

### A4 塑形项是否严格抵消
**怀疑**：Φ 塑形理论上望远镜相消（`G_t = −Φ(s_t) + Y`），但**终局折扣被移除后**可能不再严格
→ **Φ 里的"植物平均血量"可能在真教"少种植物"**。
**做**：从存档 episode 重算 `Σ shaping` 与 `−Φ(开局)` 的差；**再按"种了多少植物"分组看有无系统偏移。**

### A5 critic 从哪来（★可能是价值函数烂的根因）
配置 `initialization.note` 说"从 BC 传同配置权重"。**BC 模型里有 critic 吗？**
如果没有 → critic 是随机初始化的 → 直接解释"`mc_value_explained_variance` 常为负（最差 −10.7）"。
**再做**：检查 `value_semantics` 改版（`undiscounted_terminal_v1`）后，
旧检查点里的 critic 权重是否带着**旧价值语义**的先验。

### A6 为什么裁剪不触发
实测 `clip_fraction` 中位 **0.00528**（最大 0.032）→ **PPO 的核心机制形同虚设**。
查：是优势归一化把比值压小了？还是 `minibatch_chunks=2` 导致每步变化太小？

### A7 它到底在干什么（行为侧写）
从评估记录里统计：
- `action_counts` 构成（种/等/铲的比例，以及**在哪些行列种什么**）
- `economy_curve` 阳光收支（**会不会"只收不花"**？历史上主线出现过"花费 0.0"）
- `peak_offense` 分布（**会不会不建防线**？）
- `wait_summary`：一次"等"平均跨多少 tick（已知约 60），**会不会一直在等**
- 按"赢了/输了"分组，看这几项差在哪 → **它输的时候到底输在哪**

### A8 读代码回答一批结构性问题（纯读，逐条给结论）
1. **截断 BPTT 漂移**：`train_pvz_ppo.py` 里每个 minibatch 用**当前**参数重建前缀，
   但"旧对数概率"是旧的。**第一个 minibatch 误差 3e-5（已验），后面的 minibatch 有没有更大漂移？**
   （`first_minibatch_log_prob_max_error` 只记了第一个，**这是个观测缺口**。）
2. **AdamW 从零状态起步**的影响（初始化注释说"Start a new AdamW optimizer"）。
3. **每次更新的 16 局种子是怎么抽的**（随机？固定？相邻更新会不会高度相关）。
4. **采样器是不是空转**（`frontier_v1` 只挑通过率 20~80% 的任务，但只有 1 个任务）。
5. **动作空间只有 54 个** —— 5 行 × 9 列 × 7 种植物 = 315 种可能。**54 够表达好打法吗？**
6. **`sequence_length=128` + GRU** 的梯度路径。
7. **训练路径里有没有同类"记忆不推进"的 bug**（`render_episode.py:436` 有过一个前缀不推进 GRU 记忆的 bug）。

### A9 ★扩大评估种子，重建可信基线
评估清单 `experiments/t7/bc_finetune_level7_v1/progress_evaluation.json` 的
`tasks[0].seeds` 是**显式列表**（现为 30000~30255，共 256）。
**试着扩到 1024（30000~31023），跑通验证。**
然后用 1024 种子**重评**：v3 的 10 个节点 + A/B 的 2 个节点。
**→ 得到一条可信的 v3 学习曲线 + 对 A/B 的最终判决。**
（如果 A1 显示连续指标已经够敏感，**这步可以降级为"只重评关键节点"**——自己判断并说明依据。）

## 4. 轨道 B：训练实验队列（GPU 串行）

**规矩**：
- **每个实验相对基线只改一个变量。**
- **基线 = v3 的 100k 节点**；每个实验的评估节点设为 **`[50000, 100000]`**（两个点，能看趋势）。
- **评估先用 256 种子**（快，约 15 分钟）；**全部跑完后再用 1024 种子统一重评**（见 A9）。
- **一个失败不影响后面**：记录、跳过、继续。
- **跑之前先建配置 + `load_config` 静态校验**（不碰 GPU）。
- **严格串行**：每个跑完/失败后**先确认 GPU 空闲**再起下一个。

### 队列（**按序做，不跳**；做不完就停在哪算哪）

| 序 | run 名 | 唯一变量（相对什么改） | 预算 | 检验的猜想 |
|---|---|---|---|---|
| **B1** | `bc_seed1_v1` | `initialization_seed`+`sampling_seed` **0 → 1**（相对 v3 配置）| 100k | ★**噪声地板**：只换种子会差多少。**没有它，其他实验的差异都无法解读** |

`ppo.target_kl` **保持源配置的值**（v3 是 0.03，B2 的源是 0.3）。

## 5. 内嵌决策规则（**不要停下来问我，按规则自己走**）

- **若 A1 结论是"连续指标并不比胜负敏感"** →
  轨道 B 的前 3 个实验改成**每个 300k 预算**（用更长的时间换信号），后面的按剩余时间做。
- **若 A2 显示"跨节点完全不变的种子"占比 > 60%** →
  **立刻在报告里置顶警告"训练信号大部分是种子运气"**，
  并把轨道 B 的优先级改成先做 **B8**（大 batch，最可能改变信号质量）。
- **若 A5 显示"critic 是随机初始化的"** →
  在 B10 之外**再加一个 `bc_criticwarm_v1`**：先用 20k 决策只训 critic（策略冻结），再正常训。
- **若某个实验的评估结果显示"主指标相对基线变化 < 该指标的噪声"** →
  **报告里必须写"不显著"**，不许写"更好"或"更差"。
- **若磁盘剩余 < 30 GB** → 停止启动新 run，报告。
