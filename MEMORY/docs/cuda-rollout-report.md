## 实际架构

一条续走一个线程，游戏状态按字段连续（SoA）。每轮先由 PreKernel 推进无需网络的等待，
把需要前向的泳道压缩为连续激活槽；cuBLAS 完成三层卷积与选格头的 1×1 卷积；
PostKernel 完成上下文、动作头、选动作和动作执行。StoreKernel 回收统计与叶子特征。
每条泳道有独立随机流。批内调度不应改变同一根与未来的结果。

`cuda/SimImpl.inc`、`SimTick.inc`、`NetForward.inc`、`Rollout.inc` 由 nvcc 与 g++ 双编译。
主机参考与 GPU 的差异用于定位设备侧问题；主机参考与原版的差异用于定位机制问题。
主机参考支持 ASan。常规搜索通过 Unix socket 连接 `build/rollout_cuda --serve`，
一个服务进程汇聚各 worker 的候选；已有服务框架仍需实测汇聚规模与吞吐。
客户端在原版恢复根局面后执行 `CUDA_DUMP`，只把续走交给服务。

叶子直接输出价值网络特征 `[92×6×10 board][113 scalars][35 context]`。
Python 用同一个价值网络在 CPU 上打分，终局取真实 1/0。
学生权重常驻 GPU；真实根局面、候选与未来种子逐请求传入。
当前 `.cudaroot` 是 v9，含动画进度、学生历史和显式持物标记；旧语料必须明确拒收。v5 的旗帜生成定义曾整项为零。

## 支持范围与仍须补齐的机制

范围是冒险第 7 关白天草地，卡组 `[0,1,2,3,4,5,7]`，普通、路障、旗帜、撑杆僵尸。
已有向日葵、豌豆/寒冰/双发、坚果、樱桃、土豆雷、行走/啃食/伤害/死亡、
天降阳光、自动拾取、卡槽、波次倒计时与割草机代码；存在代码不等于已逐项验真。

机制状态（更新到第 32 轮；每条都有对应的短步/长程对照与 ASan/UBSan 回归）：

- 撑杆：起跳、空中运动、落地位移、落点窄嘴 [50,70]、普通步速，第 21–26 轮逐条对齐。
- 土豆雷：NOTREADY→RISING→ARMED 三段（19 帧 × 18fps）、触发后下一 tick 才爆、多目标伤害、
  命中即移除不留尸体、爆炸竖向 30px 起点差（第 19/24 轮）。
- 未来组成重抽：CPU RESEED 对应按未来种子与波号惰性采样，与存档未来表解耦（第 15–19 轮）。
- 行走动画：逐帧 _ground 轨迹（5 clip / 313 坐标）替代平均常数；身体动画在实体尾部推进，
  全局 EffectSystem 跳过 attachment（第 20–21 轮）。
- 死亡：真实动画 + fade；superlongdeath 的 _ground 非恒定，按动画滑动（第 25 轮）。
- 修剪机：行进中 chomp 减速、命中先触发、body/eating 保留到第 51 tick、独立动画双更新（第 21/24 轮）。
- 豌豆枪口：按 stem 轨迹插值、截断取整后加 (24,-33)（第 23 轮）。
- 空槽扫描：僵尸/抛射物高水位，仅缩小遍历、不重排实体（第 22 轮）。
- 进场：remaining→elapsed 换算，补 100 tick 双 S 曲线（第 26 轮）。

仍缺（明确不在当前门槛内）：

- 其他地形、植物与僵尸不在本任务范围。学生v1/v2lite/v2已接入，见第34–35轮验收。
- 模仿卡：导出器直接判 unsupported（20000+48），任务族不含模仿卡，未实现。
- 卡槽 mRefreshing 用“正冷却值”推断；在当前关卡与卡组内等价，未覆盖传送带/老虎机。

f198afa 对卡槽刷新做了正确方向的修正：导入原始 refreshTime；种植时写入实际冷却；
计数严格大于 refreshTime 后激活并清零。原版还有 mRefreshing 标志，当前用正冷却值推断，
仅可在当前关卡范围内视为等价，不能宣称覆盖传送带与老虎机。

## 搜索语义

CPU 与 GPU 都必须保留用户选择的 successive halving。
交接实现曾在 CUDA 后端静默关掉 halving；这会改变候选获得的随机未来数及最后动作，
已修正。需要全网格对照时，两臂显式选同一全网格配置。
不通过加宽搜索换取更好的 GPU 批量数字。

## v2lite 学生输入的接入代价（评估，2026-10-18）

当前 GPU 侧只支持 v1 输入（92×6×10 板 + 113 标量 + 35 上下文）。现行学生 v20 用 v2lite，
比 v1 多 4 个板通道与 1 个标量，且都依赖**历史**：

1. 4 个板通道：僵尸健康加权位置、健康加权速度、格内最大速度、格内植物年龄（最小 (tick−born)/1500）。
2. 1 个标量：min(1, (tick − 本波开始 tick)/3000)。
3. 历史状态：每个 (row,col,kind) 的首次出现 tick，以及本波开始 tick。

接入需要动三处：`RootPlant`/车道状态新增出生 tick 并在种植/铲除时维护；每波开始时记录 tick；
特征编码从 92 通道扩到 96、标量 113→114，同时改网络镜像的输入布局（学生权重必须按新布局导出）。
前两项在核内每轮都能从现有状态算出来（僵尸位置/速度/健康已在车道里），不需要额外回读；
真正的工作量在**布局与镜像**：`.pvzrn` 版本升级、`kValueFloats` 与价值网络特征同时改、
所有既有语料与逐位对照需要重跑。

代价估计：中等，1–2 天（含全量复验），风险集中在“历史字段在续走起点是否正确”——
续走根是从原版存档恢复的，出生 tick 只能从原版的 `mPlantAge`/动画进度反推，
对已经在场上的植物会有一次近似；对短程（≤2500 tick）影响小，但必须逐条对照才能声称一致。

结论：阶段 1 / 2 用 v19（v1）先把门槛过掉；v2lite 作为独立一轮再做，不与门槛混在一起。

## 服务形态：一个进程汇聚多个 worker（第 32 轮实测）

8 个 worker 共用一个 `rollout_cuda --serve`，gather 80ms、2048 道。逐波日志（PVZ_SERVE_TRACE）显示：
每波稳定合并 8 个请求、18–24 道；合批本身是成功的（每个 worker 单独只有约 3 道）。

但每轮耗时随波内请求数线性增长：1–2 个请求 2.2–3.3ms，8 个请求 19ms（私有 shared 路径 12–13ms）。
一个请求要 47 轮，于是每请求 0.9 秒（私有路径 0.6 秒），吞吐 13→17 请求/秒。
同期 2 个 CPU worker 的吞吐是 9.3 请求/秒——服务只快 1.4–1.8 倍，而每局墙钟慢 7–10 倍。

原因不是显存也不是算力：服务进程单线程，每轮 4 次核函数 + 一次 8 字节回读同步；
主机 load 23（正式实验在跑）时，核函数发射被调度器拖长，GPU 事件测到的是含等待的墙钟。
结构性结论：这个搜索每请求只有约 8 道（`per-card 1` + 早期只有 2–3 张卡可用），
而每轮固定成本约 5–13ms，所以**延迟由轮数决定、与道数无关**。
要让 GPU 真正赢，需要每波 ≥100 道，也就是 ≥30 个 worker 同时供给——超出本机 4 进程/6GB 的资源纪律。
因此在当前任务族上，服务形态的价值是“多 worker 共享一块 GPU”，不是“让单局更快”。

预测（可证伪，逐条待扫描判定）：

1. gather 收益有饱和点。合并深度 ≈ 到达率×窗口（18.6 道/s ⇒ g300≈5.6 道、g1200≈22 道、g4000≈74 道；

   需回头修到达率而不是庆祝。
2. 大 gather 会拿延迟换吞吐。g1200/g4000 的 mean_game_s（每局延迟）应显著恶化（每请求最多白等
   一个窗口），作业墙钟却应改善。若两者同时变好，则本轮的到达率或窗口语义有一条是错的。
3. 主机侧占大头，合批摊不掉它。按 12.13 vs 3.42 ms/轮，每请求等待里非核内部分应过半；
   若扫描测出 host_ms_per_request 中位数 < gpu_ms_per_request 中位数，则"实现出波与主机活重叠"
   这条杠杆应当降级，优先项改为压缩核内固定成本（每波 144.3 ms 的截距项）。
4. 即使最优档，也未必打得过 CPU。合批把每轮固定成本摊到 13.5 道只是打平，而 4 worker 的真实
   合并深度受限于并发局数（纪律上限 4）；因此"GPU 在 DAgger 实际形态下比 CPU 快"这件事，
   预期的答案是**不成立**，成立的是它需要在更高并发形态下才成立——若最优档仍慢于 CPU，
   这就是本轮给主控的定量结论（对应 codex_cuda_questions.md 的 Q1）。

判定用的字段（已写进各臂 wall.json，不靠事后补算）：elapsed_wall_s（作业墙钟）、mean_game_s（每局延迟）、
lanes_per_request（合并深度）、serve.gpu_ms_per_request 与 host_ms_per_request（核内 vs 主机拆分）、
gate.load1（入场负载，让"匹配负载"可核验）。每请求的客户端份额可由 (mean_game_s×局数 − cuda_seconds)
×1000/请求数 现算，不必另测。

### 追加两条（仍在测量前）：波不是被服务端剪空的，是被搜索剪空的

`gpu128` 已完 39 局的真实计数（本轮现算，非引用）：每搜索点 **3.00 次请求、8.56 道**，即每请求 2.85 道；
`cpu128` 同 39 局的 searched/decisions = 0.200（gpu 侧 0.196），两臂搜索密度一致。
减半调度 `search_play.py:356-380` 的 `keep = max(2, (len(ranked)+1)//2)` 就是波变空的直接原因：
最后几轮每请求只剩 2 道。而 `--no-halving`（`--per-card` 默认 1、`--samples` 3）是
**1 次请求带 候选数×3 道**：6–10 张可用卡 ⇒ 21–33 道/请求，按 wave_ms≈144.3+3.33×道 得 214–254 ms/波，

5. 预测：把 `--no-halving` 接上 GPU（gather 保持 80ms，波本来就满）应当**首次让 GPU 快过 CPU**，

## 第47–50轮：GPU 臂块级节奏波动的真身是窗口混叠（2026-10-19 03:33–03:38）

第46轮排除了主机负载，但没解释 GPU 臂内部 89.1–131.2 s/局（1.47 倍）的摆动。四轮零额外负载的
盘上再分析给出的答案是：**这个摆动主要是"每10局窗口"这个读法自身的伪影**，链条如下。

**第47轮（乘法分解）**：把节奏写成恒等式 `cadence = 每局道数 × 每道主机秒 ÷ 有效并发`，块序对应由
`search_play.py:580-583` 保证（`imap_unordered` 的同一个循环既按完成顺序写 `games.jsonl`、又打
"i/N (Xs)" 进度行）。5 个完整块的结果：每局道数只摆 **1.056 倍**（1905–2012 道），每道主机秒摆
1.172 倍（0.2111–0.2476 局秒/道），而派生的"有效并发"摆 1.46 倍——**且两次超过 `--workers=4`
的物理上限**（[3.24, 4.73, 3.68, 4.36, 3.80]）。并发不可能大于 worker 数，所以问题出在估计量。
另有一处数据缺口：`cpu128` 的行里**没有 `rollout_lanes/rollout_batches` 字段**（产自计数器加入之前），
跨臂只能退到"每搜索点成本"。

**第48轮（窗口粒度检验，判据开算前写死）**：同一批完成事件换窗宽。GPU 臂 10 局窗
[131.2, 89.1, 128.3, 100.9, 119.0] 的 **lag-1 自相关 = −0.793**（高-低-高-低交替），

[3.84, 4.11, 3.97, 4.05]（贴着上限 4）。CPU 臂不交替（lag-1 = +0.13）而是缓变：10 局 1.97 倍、
20 局 1.567、40 局 1.269，丢掉含建池启动的首窗后 20 局 1.348 倍——**两臂机制不同**，
一类是完成成批（burst 大小≈worker 数）造成的窗口混叠，一类是启动暂态＋缓变趋势。

**第49轮（把分解搬到 20 局窗）**：极差分别为 节奏 1.054、每道主机秒 **1.124**、每局道数 1.044、

合理解读是：混叠修掉之后，GPU 臂的真实性能是一句很平的读数，残余 ±6% 级别的摆动没有可用的
归因抓手。**可用于后续引用的干净读数（20 局窗中位）**：

整段口径给的比值是 113.7/28.1 = 4.05 倍，与 4.33 一致 ⇒ **阶段2这套真实 DAgger 形态下，

## 第51轮：每请求延迟的主体是"波头阻塞"，不是主机算力（2026-10-19 03:46，零额外负载读盘）

审计第44轮阶梯脚本时发现的隐患：`host_ms_per_request` 与末尾那条"下一件要实现什么杠杆"的判定，
唯一输入是 `serve['gpu_ms_per_request']`，而该键**只在日志里有 `serve-trace:` 逐波行时才被写入**
（`tmp/codex_r44_inline_wall.py` 的 `if traces:` 分支）。第50轮已证明长 GPU 阶段常常没有
`PVZ_SERVE_TRACE`，于是阶梯会在跑完几小时后静默给不出判定。已在原脚本补了不依赖 trace 的
汇总口径（`gpu_ms_per_request_mean = 服务端 GPU 总毫秒 / 请求数`，三处引用同一兜底），并把它做成
独立的读盘分析器 `tmp/codex_r51_serve_split.py`，落 `artifacts/cuda/codex_r51/serve_split.json`。

口径（三者不可混）：`worker_ms_per_request = Σcuda_seconds/Σcuda_batches`（worker 亲历，含编码、IPC、
排队、等波）；`gpu_ms_per_request = 服务端 GPU 总毫秒/请求数`（设备真正 busy 的每请求成本）；
二者之差以前一律叫"主机侧"。三个历史阶段（请求数与道数两端全部对得上，3/3）：

| 阶段 | 局/请求/道 | 每请求道数 | worker 亲历 | 设备 busy/请求 | 差值占比 | 请求/波 | 波均设备 | 亲历÷波均 |
|---|---|---|---|---|---|---|---|---|
| `codex_phase2_v19_v3_gpu` | 128/85101/236327 | 2.78 | 788.1 ms | 95.8 ms | 87.8% | 7.57 | 725.5 ms | **1.086** |
| `dagger_gpu` | 4/2676/7509 | 2.81 | 453.0 ms | 225.8 ms | 50.2% | 1.95 | 439.8 ms | **1.030** |
| `phase2_smoke_gpu` | 2/1434/3721 | 2.59 | 540.9 ms | 277.9 ms | 48.6% | 1.85 | 514.1 ms | **1.052** |

**结论：那一"差值"的主体是波头阻塞，不是编码/IPC。** 三个阶段的 worker 亲历时间除以波均设备时间
都≈1（1.030–1.086，而绝对毫秒在 439–788 之间摆 1.7 倍），即一个请求的时间几乎就是"我搭乘的那一波
跑完"的时间，而那一波里装着 1.85–7.57 个请求的活。合并越深，每请求的设备成本越低（34.5 ms/道
@21 道/波 vs 107.1 ms/道@5 道/波）但亲历延迟越高（283.5 vs 208.8 ms/道）——合批买的是吞吐，卖的是延迟。

**对第44轮判据的影响（改，不是补）**：阶梯末尾那条"主机侧 vs 核内"二选一，在这批数据上会把
波头阻塞误判成主机算力，从而推荐"服务侧多线程/双缓冲"这个错误的杠杆。裁决列改成
**作业墙钟（吞吐口径）**；`host_ms_per_request` 只作为上界保留（它含等波）。附带一条不得跨阶段
滥用的提醒：三阶段 rounds/道 = 2.25 / 8.47 / 9.48 差别很大，每道毫秒的跨阶段比较被续走深度混淆；
每轮毫秒随道数上升（9.5 ms@5 道 → 15.3 ms@21 道）与"固定+边际"模型方向一致，但不同二进制/配置的
两点拟合只能算指示性，同二进制的那份要等阶梯。

**监控附带读数（03:46）**：`gpu128` 63/128 局；阶梯仍卡在 `waiting for controllers 260806/261316 to exit`。
另有外部队列 `~/pvz-logs/queue_teacher.sh`、`queue_teacher2.sh` 在跑 3 个 teacher 作业（worker 4+2+2），
可用内存 2558 MB < 门禁 6144 MB、loadavg1 11.1（阈值 12）⇒ 阶梯放行受内存这一条限制，
不是 GPU 占用；那批作业不属于本轮，不干预，只把等待记下来。

## 第52轮：合批合并度被**并发度**封顶，不是被窗口宽度封顶（2026-10-19 03:53，预登记，零负载）

第51轮顺带把三个历史 GPU 阶段的 `config.json` 与服务端汇总行放到一起看，出现一条此前没写过的关系：
`请求/波` 贴着 **worker 数**，而三个阶段 `cuda_gather_ms` 全是 80（唯一变量是并发）。

| 阶段 | workers | gather | 请求/波 | ÷workers | 道/波(取整展示值) | 道/请求 |
|---|---|---|---|---|---|---|
| `codex_phase2_v19_v3_gpu` | 8 | 80 ms | 7.57 | 0.946 | 21.0 | 2.78 |
| `dagger_gpu` | 2 | 80 ms | 1.95 | 0.975 | 5.0 | 2.81 |
| `phase2_smoke_gpu` | 2 | 80 ms | 1.85 | 0.925 | 5.0 | 2.59 |

比值 0.925–0.975 由**整数计数相除**得到（requests、waves），不受 `lanes per wave` 的 `%.0f` 取整影响；
恒等式 道/波 ÷ (道/请求×请求/波) = [0.998, 0.912, 1.044] 的偏离量级正是取整幅度（±10%）。
含义：**一波里装的是"当下阻塞在请求上的那些 worker"**，所以合并度上限 = 并发度 × 每请求道数。
本仓库历史上没有任何一个阶段实验过"窗口宽度"这一维，"把 gather 拉宽就能填满波"这个直觉从未被数据支持。

由此给第44轮阶梯（4 worker、4 局、gather∈{0,80,300,1200,4000}）登记两个**并列可判别**的预测：
- 模型 (b) 实证外推：80ms 就已凑到 0.949×4=3.8 请求/波 ⇒ 每波 10.8 道、波 180.2 ms、设备 60.0 道/s，
  且 **80/300/1200/4000 四档互相持平**（极差 ≤1.10），只有 gather=0 一档落在 2.85 道/波、18.5 道/s；
- 模型 (a) naive（按 0.5 s 独立到达）：每波道数 [2.9, 3.3, 4.6, 9.7, 11.4] 随窗口单调上升。
  两模型在 80 档相差 3.28 倍，阶梯自己裁决。

**若判据全部成立**，目标3 的正确结论形态是："真实 DAgger 形态下 GPU 合批收益被并发度封顶，
窗口宽度只决定能否到达那个上限"，下一步杠杆是**提高每请求道数**（第45轮 `--no-halving`）或
**提高并发**（更多 worker / 异步预取），而**不是**服务侧多线程——这与第51轮"延迟主体是波头阻塞"
指向同一处：单请求延迟口径在这里选不出杠杆，只有作业墙钟（吞吐）可以。

**本轮自查记录**：首版（03:51:33）用模型 (a) 外推并写下"窗口 ≥1500ms 才凑满、1200 与 4000 必须持平"，
其中"持平"的方向对但机制说反了——实证填充率显示 80ms 就已接近上限。已在同名批覆盖并注明两批差异。

**机制核对（读码，非推测）**：这条关系不只是经验规律，服务端的持窗逻辑就是按并发度写的——
`cuda/RolloutCuda.cu:1644` `packed = queued*2 >= dev.lanes || allClientsWaiting()`，
即只要每个已连接客户端都各有一个待处理请求，服务器立刻停止等待开波（`allClientsWaiting`
定义在 `:1610–1622`，逐 client 查队列）；`:1801` 的续窗条件同样带 `!allClientsWaiting()`。
所以"一波能装的请求数"在结构上等于"当下待处理的 client 数"，窗口宽度只决定能否盖住到达时差；
容量闸门 `queued*2 >= dev.lanes` 在本形态（≈11 道/波，`dev.lanes` 默认 8192，即便按 128 槽布局
也要 64 道才触发）远未生效。填充率是 0.925–0.975 而不是 1.0，正是因为并非所有时刻全体 client
都在排队。两个推论随判据一起登记：(i) gather∈{80,300,1200,4000} 四档每波道数应互相持平（±10%）；
(ii) 由于"人人都在等"时立刻开波，宽窗口**不会**额外增加作业墙钟——阶梯大概率只能区分
`gather=0` 与 `gather>0` 两类，中间没有可调旋钮。真正的旋钮是每请求道数（第45轮 `--no-halving`）
或 client 并发数；两者都不需要动服务侧多线程。

### 第54轮补强：换算到"道/秒"之后，D1 的 build-matched 对照其实早就在盘上（04:37，零额外负载）

第53轮说"服务形态贵 N 倍这句话要等 D1（同 build 对照）才作数"——这句话只对了一半：
第42轮基准的 per-run 文件**本来就自报** `wall N ms for M rollouts -> R rollouts/s`，
而它的"基线"臂用的正是 gpu128 服务进程的同一个二进制
（`codex_r36/frozen/rollout_cuda_small` = cef25086）。换掉 `ms/轮` 这个不含"每波几条道"的单位，
三方就能画在一张表上（一条"道"= 一个 horizon 2500 tick 的学生走子续走 rollout）：

| 波宽（道/波） | `rollout_cuda_small`（=生产服务进程同件） | `rollout_cuda_inline_tick` | 折算成 CPU 核 |
|---|---|---|---|
| 8 | 26.97 道/s（37.08 ms/道） | 46.78 道/s（21.38 ms/道） | 1.53 / 2.66 核 |
| 30 | 83.96 道/s（11.91 ms/道） | 122.78 道/s（8.14 ms/道） | 4.77 核 |
| 300 | 543.48 道/s（1.84 ms/道） | 926.88 道/s（1.08 ms/道） | 30.86 / **52.63 核** |
| **生产 served（~12 道/波）** | **17.05 道/s（58.67 ms/道，墙钟口径）** | — | **0.97 核** |
| CPU 参照 | 单核 17.61 道/s（56.8 ms/道）；4 worker 聚合 **70.45 道/s** | | |

**落档**：同一件二进制在**最小波宽 8 道**的批模式就值 1.53 个核，而它作为服务进程在生产形态只值 0.97 个核
⇒ 服务形态比自己的批模式慢 **1.58 倍**（按 30 道点是 4.9 倍）。所以"GPU 只等于一个 CPU 核"
不是 GPU 的能力上限，是**服务形态的开销**。

**这同时否证了第53轮那条"窗口这条路数学上已封死（L\*=13.3–13.9 > 并发上限 11.4）"**：
那个拐点是拿服务形态的线性拟合 `ms/轮 = 3.79+0.383·道` 外推的，
而同件批模式实测 8→300 道波宽的道/秒涨幅是 **20.2 倍**——线性外推在 30 道以上严重低估收益。
正确说法：填满波依然有效，但**有效区间在生产当前拿不到的宽度（≥30 道/波，那里 83.96 道/s 已单独越过 CPU 四核）**，
所以必须同时改并发结构（更多 client，或每请求带更多候选 ⇒ 第45轮 no-halving 与第44轮 gather 阶梯正是这个形态）。
目标3 至此有了两段式定量答案：当前 17.05 对 70.45 差 **4.13 倍**，
其中"波宽 12→30"与"压掉 1.58 倍服务损耗"两件事各自负责一部分。

**可比性边界（必须与上表同批读）**：批模式的 `wall ms` 只是 bench 二进制内波循环自身的耗时——
根预先落盘、叶子张量不回传、波间背靠背无空隙；生产的 17.05 道/s 是**整段作业墙钟**摊道数，
含客户端 `cuda_dump` 根、取叶子张量、CPU 搜索这些与 GPU 串行的活与波间空闲。
⇒ 1.58/4.9 倍是"服务形态里 GPU 在等主机"的**下界**，不是内核慢。
分清二者只要 gpu128 退出时 `serve:` 里的 `gpuMs/阶段墙钟`（设备占空比）：
>0.9 ⇒ 每波真的贵（回到内核/波宽）；明显 <0.9 ⇒ 主要损失是主机侧串行，
那"实现最有希望的一个"就不再是 kernel 优化而是**把根导出/叶子评估与波推进流水化**（或摊薄到更多 worker）。
两种情况的下一步实验不同，所以这条判据在 D1 落地前就登记。

### 第54轮定量方案：GPU"只值一个核"是占用率算术，靶心是每请求 6–11 道（04:41，零额外负载：读码 + 已在盘上的读数）

第54轮补强留下一个反直觉事实：同一件二进制，批模式 8 道波就值 1.53 个 CPU 核，服务形态只值 0.97 个核。
机制在代码里（`cuda/RolloutCuda.cu:1197/1221–1222`）：私有波每轮 launch 是
`PrivateRoundKernel<<<batchLanes, privateThreads>>>`，`:1143` 的 `privateThreads` 默认 128，
⇒ **一条道一个 block**，`blockDim=128`。卡是 RTX 5080、84 个 SM（`:274/:281` 的注释也按 84 SM 算）。

| 每波波宽 | grid（block 数） | block/SM | 空闲 SM | 线程数 | 同件实测道/秒 |
|---|---|---|---|---|---|
| 8（批） | 8 | 0.095 | 76 | 1024 | 26.97 |
| 30（批） | 30 | 0.357 | 54 | 3840 | 83.96 |
| 300（批） | 300 | 3.571 | 0 | 38400 | 543.48 |
| **11.4（生产，4 client × 2.85 道/请求）** | **11** | **0.131** | **73** | **1408** | **17.05** |

生产每波只有 **13.1% 的 SM 拿到活**（满载线程数口径 1.09%）。⇒ "GPU 只等于一个 CPU 核"不是内核慢，
是**每波 block 数小于 SM 数**：这是算术，不是猜测。

**剂量-响应与需要多宽的波**：同件批模式三个点（8/30/300）的 log-log 弹性 **0.827**（接近线性 ⇒ 填满波几乎等比换吞吐），
拟合 `道/秒 ≈ 4.92·波宽^0.827`。跨过 CPU 四核（70.45 道/秒）需要波宽 **25.0 道**（若无服务损耗）
到 **43.6 道**（按本轮实测的 1.58 倍损耗折回）。4-worker 纪律下 client 数固定 4 ⇒
**每请求要带 6.3–10.9 道，而现在是 2.85 道**。内联件把整条曲线上移 1.46–1.71 倍
（30 道 122.78、300 道 926.88 道/秒），所以第44轮阶梯（内联件 + trace）若能把服务损耗压到 ≈1，
靶心就降到每请求 ~6 道，压不动就要 ~11 道。**这就是任务书目标3 要的定量方案，而且两个分支都能由

### 第54轮worker标度：加并发这条路的方向是反的（04:57–04:58，零额外负载：纯代数 `tmp/codex_r54h_worker_scaling.py`）

"不改搜索语义、只多在飞的 client 把波填满"看起来是第三条路（波宽 = W × 每请求道数）。但比较必须同 W 对同 W：
GPU 决策率 ∝ `W^0.827`，CPU 决策率 ∝ `W^1` ⇒ 比值 ∝ `W^-0.173`，**随并发单调下降**。减半形态实测底数代入：

| W（worker 数） | 波宽（道） | 内联件+批上界 vs CPU | 内联件+含 1.58× 损耗 vs CPU |
|---|---|---|---|
| 2 | 5.7 | 0.94× | 0.59× |
| **4（纪律上限）** | **11.5** | **0.83×** | **0.53×** |
| 8 | 22.9 | 0.74× | 0.47× |
| 16 | 45.9 | 0.66× | 0.41× |
| 24 | 68.8 | 0.61× | 0.39× |

⇒ 并发越高，GPU 相对 CPU 越差（因为 CPU 是线性标度、GPU 是次线性的幂律）；比值最高的那一格恰好是并发最低的
W=2，但那里绝对产出也最低（3.96 决策/秒 vs W=16 的 22.07）。所以**加 worker 不是出路**，
`每请求道数` 才是唯一能抬波宽的旋钮——而它连着搜索语义（见 Q3 补强 3）。
GPU 真正的位置在另一侧：同件批模式 300 道波 = 543 道/秒 = CPU 单核的 30.9 倍 ⇒ **离线大批量续走**。

**边界**：这条代数假设 CPU 每 worker 恒定 2.11 决策/秒（对 CPU 有利）；机器 20 个逻辑 CPU（i7-12700F），
W≤16 内自由核够多，假设大体成立，但若 CPU 先于 GPU 客户端因内存带宽退化，曲线下降会变缓甚至反转。
不影响交付，因为纪律上限本来就是 4 worker；登记它是为了防止"W 越大 GPU 越差"被引用成硬件定律。
（本条 04:57:09 首次落盘时把 W=4/W=16 两组数写成了同一个值 0.66→0.66，04:58 已按上表更正，其余结论未变。）

### 第54轮决策率分解：真正的那一维是每决策串行请求数 R，不是每请求道数（05:04–05:05，零额外负载 `tmp/codex_r54k_rate_decomposition.py`）

把前面所有读数压成一个闭式（自检：公式给"减半/非内联/批上界"= 4.294 决策/秒，
第54轮决策率预算的网格给 4.29 ⇒ 两者同源，可放心用它做外推）：

**决策率 = a · W^b · L_dec^(b−1) · R^(−b)**，a=4.915、b=0.827、W=4、
L_dec = 每决策道数、R = 每决策的**串行请求数**。三个弹性各自的含义：

| 旋钮 | 弹性 | 含义 |
|---|---|---|
| **R（每决策串行请求数）** | **−0.827** | 把 k 次串行请求并成 1 次 ⇒ 决策率 ×k^0.827；3→1 就是 **2.47 倍** |
| L_dec（每决策道数） | **−0.173（负）** | 每决策多跑道数**降低**决策率：幂律 b<1，翻倍工作量 ⇒ ×2^−0.173 = 0.887 |
| W（在飞 worker 数） | GPU 0.827 / CPU 1.0 | 已在 worker 标度那条：加并发方向是反的 |

由此**否证本回合交给主控的靶心数**："每请求 6.3–10.9 道"（第54轮定量方案 04:41）是**道/秒**口径的目标，
在决策率口径里方向是反的——R 固定为 3 时，每请求道数↑必然意味着 L_dec↑（同一批候选、同样的 3 个阶段），
而 L_dec 的弹性是负的。例：把每请求从 2.87 道抬到 10 道（波宽 40 道、103.8 道/秒 > CPU 的 72.5 道/秒，
按道/秒算"赢了"），但每决策变成 30 道 ⇒ 决策率 **3.46 < 现状 4.29**。

**真正的那一维是 R**：固定 L_dec=8.60、其它全取最理想（无服务损耗、非内联件）时追平 CPU 需 **R ≤ 1.33**；
换内联件也只要 **R ≤ 2.40**（仍要从 3 次串行请求压到 2 次以下）。⇒ **目标3 在"不动任务族"前提下的代数上限**：
质量中性（L_dec、R 都不变）时可动的只剩"件"（内联 ×1.63）与"服务损耗"（÷1.58，压到 1 为上界），
两者都取极限 = **7.02 决策/秒 = CPU 的 0.83 倍**（保留实测损耗则 4.44 决策/秒 = 0.53 倍）。

**口径边界（这两个弹性不能混着用）**：减小 L_dec（例如 samples 3→2）也会提高决策率
（10.35 决策/秒 = CPU 的 1.23 倍），但那是"少算"换来的；判据仍是口径边注那两句——
(1) 等质量（固定 L_dec 与候选/未来数）下道/秒之比 ≥1 才算 GPU 真赢；(2) 任何改变 L_dec 的方案必须另有标签质量证据。
R 这一维特殊在于：**把 3 次串行请求并成 1 次而不改变每次请求的内容**（服务器侧脚本化减半）
只削服务损耗、不会把波变宽（同波仍只有 ~2.9 道在飞），所以它是**质量中性**的协议优化，
上限就是 4.44→7.02 决策/秒这一段；而真正把波从 11.5 道填到 52 道的只有"取消阶段依赖"，那必然改 L_dec。
（写入事故：05:04:32 与 05:04:43 的前三条是同一次分析的重复——第一版脚本在循环里崩在第 4 个元素，
但前 3 条已落盘，修好后重跑又写了一遍。读一次即可，不要当成两次测量。）
