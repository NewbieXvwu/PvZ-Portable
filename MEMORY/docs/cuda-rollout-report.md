# CUDA 续走模拟器 —— 设计与实测报告

分支 `cuda-rollout`。任务书：把老师搜索用的"续走"（从当前局面用学生网络往下推 2500 tick）搬到 GPU。
真实对局、评估、DAgger 帧档案仍跑原版模拟器，不受影响。

本文档随实现推进更新：每节先说结论。

---

## 0. 一句话架构

一条续走 = 一个 CUDA 线程（lane）。游戏状态按字段连续存放（SoA），256 条 lane 一个线程块。
学生网络也按 lane 并行：每个线程用 64 个累加寄存器算自己那一条的卷积。
核函数里连续推进 tick，只在需要决策时做前向；不需要决策的 tick 完全不碰网络。

---

## 1. 为什么要做、门槛怎么定

老师的墙钟时间几乎全花在续走上。实测（2026-10-17，台式机，负载 0.6）：

| 量 | 数值 |
|---|---|
| 一条续走（2500 tick，含 31.9 次学生前向）C++ 内部耗时 | 25.38 ms |
| 单线程续走速率 | 39.4 条/秒 |
| 1 / 2 / 4 线程扩展性 | 39.40 / 38.72 / 38.32 条/秒/线程（近线性） |
| CPU 基准（任务书口径 = 单线程 × 20） | **788 条/秒** |
| 阶段 0 门槛（× 5） | **GPU ≥ 3940 条/秒** |

一条续走的算力构成（决定设计重心）：

- 游戏模拟：4.23 µs/tick × 2515 tick = 10.65 ms（42%）。原版这部分含动画/粒子系统，重写后可以砍掉。
- 学生前向：31.9 次 × 0.462 ms = 14.75 ms（**58%**）。v14 宽 64，每次 4.3–5.7M MAC。
- 折算 GPU 需求：3940 条/秒 ⇒ 约 7.2e11 MAC/秒，只有 RTX 5080 峰值 FMA 的 **2.6%**。
  结论：**门槛不是算力问题，是访存与指令效率问题**。设计目标是"别写出自杀式的核函数"，不是榨干张量核心。

## 2. 数据结构

### 2.1 lane 状态（SoA，全局内存）

上限固定 + 活跃标记。所有槽位每 tick 都被扫一遍（SIMT 下所有 lane 走同样的循环 trip count，
避免发散）；空槽只做一次 flag 判断。

| 数组 | 槽位数 | 字段 | 每 lane 字节 |
|---|---|---|---|
| 植物 | 60（= 格号 row*10+col，草地每格最多一株） | type、hp、计时器 A/B/C | 60×5×4 = 1200 |
| 僵尸 | 64 | type、row、state、body/helm/shield、posX、velX、计时、chilled、eating、目标格 | 64×12×4 = 3072 |
| 子弹 | 96 | kind、row、posX、active | 96×4×4 = 1536 |
| 硬币（阳光） | 24 | state、posX、posY、vy | 24×4×4 = 384 |
| 小推车 | 6 | row、state、posX | 6×3×4 = 72 |
| 卡槽 | 10 | type、active、refreshCounter、refreshTime、cost | 10×5×4 = 200 |
| 波次表 | 30 × 8 | 每波僵尸种类列表 | 960 |
| 标量 | — | tick、sun、wave、倒计时、阳光收入直方图、计数、终局标志 | ≈ 400 |

合计约 7.2 KB/lane。按门槛速率聚合访存 ≈ 70 GB/s（HBM 960 GB/s），L2 命中率很高，不是瓶颈。

坐标一律 `float`（不是定点）：原版 `mPosX -= 0.47f * mVelX` 是 float 运算，
用同样的类型才能保证"机制忠实"里的数值语义。

阳光收入（学生特征 scalars[3]）原版是一条 `(tick, produced)` 事件流、6000 tick 滑窗求和。
GPU 上用 **60 个 100-tick 桶**的直方图代替：窗口边界误差 ≤ 100 tick。已记入 §5 偏差清单。

### 2.2 局面导入

C++ 端新增协议命令 `CUDA_DUMP <path>`（`src/main.cpp`），把当前局面写成一个定长二进制记录，
字段与 §2.1 一一对应。格式定义放在 `cuda/CudaRollout.h`（纯 C++，无 CUDA 语法），
导出端与核函数端共用同一个结构体，避免两处定义漂移。

导出内容：关卡/地形/倍率/卡组与卡槽状态、逐格植物、逐个僵尸（含 hp 三池、state、posX/velX）、
子弹、硬币、小推车、波次计数与各倒计时、阳光与收入窗口、`mSunMoneyProduced`/`mZombiesKilled`/
`mPlantsEaten`/`mTriggeredLawnMowers`、以及本关出怪表（见 §4 的"未来重抽"）。

**不导出随机数状态**：任务书允许随机数顺序不同，每条 lane 用自己的 Philox 计数器流。

## 3. 核函数划分

```
一次批 = N 条续走（每条 = 一个 (根局面, 随机未来, 首个动作) 三元组）
  ├─ H2D：N 份根状态（同一根局面复制 K 份）+ 首动作 + Philox 种子
  ├─ kernel：while (未到 until_tick && 未到 max_actions && !terminal)
  │     ├─ 推进 tick：植物 → 僵尸 → 子弹 → 硬币 → 小推车 → 卡槽 → tick++ → 天降阳光 → 出怪
  │     ├─ 到决策点：算合法性（EnvironmentAnyLegalPlant 的等价判断）
  │     │     ├─ 无合法动作 → WAIT 60 tick（不做前向）
  │     │     └─ 有 → 提取 92×60 棋盘 + 115 标量 → 学生前向（本线程）→ 选动作
  │     └─ 执行动作（种植 / WAIT 60）
  └─ D2H：每条 lane 的终局统计 + （阶段 1）终点价值特征
```

决策语义严格对齐 `src/main.cpp` 的 `ROLLOUT` 与 `EnvironmentRollout::Predict`：

1. 先查"有没有合法种植点"，没有就直接 WAIT 60 且**不计前向**（CPU 侧也是这样省的）。
2. `plant` logit ≤ 0 → WAIT 60。
3.  packet 选择：在"能拿起 且 该种子至少有一个合法格"的卡槽里取 `packets[index]` 最大者。
4. 细胞选择：对选中的 packet，`cells[row*9+col]` 在合法格里取最大。
5. 种植在同 tick 内完成（原版 `EnvironmentPlant` → `MouseDownWithPlant` → `AddPlant` + 扣阳光，
   没有排队延迟），卡槽立刻进冷却。

### 3.1 学生前向：为什么用"线程 = lane"而不是块协作

v14：conv 92→64(3×3) → 64→64(3×3) → 64→64(1×5) → mean/max 池化 + 标量分支 → 三个头。
一次约 4.3M（CPU 稀疏）–5.8M（稠密）MAC。

- 每条 lane 的特征图 = 60 格 × 64 通道 = 15 KB。32 条 lane 就要 480 KB 共享内存 ⇒ 块协作方案必须
  按 batch 分片、把权重和激活都塞进共享内存，实现复杂且收益小（门槛只要 2.6% 峰值）。
- 线程 = lane：累加器 = 1 个输出格的 64 通道（64 个寄存器），内层遍历 92×9 个 (通道, 抽头)；
  权重地址在 warp 内一致（广播，无 bank 冲突），激活地址按 lane 连续（合并）。
  寄存器约 90 ⇒ 每 SM 约 700 lane，够用。
- 代价：conv1 不做通道稀疏（92 通道全算），比 CPU 多约 30% 的 FMA。先用稠密跑通，
  若小批次延迟碍事再上"块内通道并集"稀疏。

### 3.2 延迟与占空比（影响阶段 2 的批量策略）

单条 lane 的续走约 2.8e8 次 lane-op（含加载）。一个线程每周期只能发一条指令 ⇒
**单条续走的 GPU 延迟下限约 100 ms**，吞吐靠并发：一个 SM 满占约 1200 条/秒，整卡 4–10 万条/秒。
所以门槛 3940 条/秒需要约 2800 条同时在飞。阶段 2 必须把多个对局的续走凑成大批次
（共享一个 GPU 服务进程），否则只是把延迟搬过去。这点会在阶段 2 报告里用实测曲线量化。

## 5. 已知偏差（阶段 1 要能解释）

1. 随机数流不同：允许（任务书 + `PVZ_RNG_JITTER` 实验）。
2. 阳光收入窗口用 100-tick 直方图近似：边界 ≤ 100 tick，只影响 scalars[3]。
3. 动画系统不搬：行走/啃咬/射击时序编译成常数表；表中数值从原版实测得到。
4. 表现层跳过：sim-skip 29 的等价物（不画颜色/弹跳/附着矩阵/消息）——GPU 版本来就只算逻辑。
5. 粒子、墓碑、雾、水路、屋顶、Boss、其他植物/僵尸种类：不在范围（任务只跑 level 7 白天草地）。
6. 阶段 0 的波次洗牌代替重抽（§4）。

## 6. 与 Python 的对接

`libpvzcudarollout.so`（ctypes）+ `python/pvz_cuda_rollout.py`：
`load_weights(pvzrn_path)`、`run(roots, actions, futures, horizon) -> stats`。
权重只做一次 H2D（常驻显存），进程内多次批用同一个 stream。
阶段 2 给 `scripts/search_play.py` 加 `--rollout-backend cuda`（默认仍是原版）。

终点价值分：阶段 1 先在 GPU 上算出**价值网络的特征**（92×60 + 113 + 35），
交给 Python 的 torch 批量前向（与 CPU 后端完全同一个 V 网络，避免"两套实现"混进对比）。

## 7. 构建集成

CUDA 是**可选目标**：`-DPVZ_CUDA_ROLLOUT=ON` 才编 `cuda/`，默认 OFF。
没有 nvcc 的机器（Mac）走原来的 CMake 路径，不受影响。
`cmake/OpenCudaRollout.cmake` 里 `enable_language(CUDA)`、arch `sm_120`，
主程序只在 `CUDA_DUMP` 命令上多一段纯 C++ 的导出代码（不依赖 CUDA runtime），
所以阶段 0/1 的导出与验证不需要 GPU。
