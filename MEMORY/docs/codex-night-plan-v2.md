**时间不设上限，跑到天亮或清单做完。**
**唯一原则：每个结论都要能经受"统计上显不显著"的追问。**

## 0. 前情（10-10 一整天得到的）

- **v3**：BC 起点 → 1M 决策，**1024 局重评后确认**推进 +1.78pp、胜率 +8.2pp（6 项 Holm 校正后显著）。
  **但 100k / 500k 都不显著 —— 前 50 万决策全在噪声里。**
- **十次实验**：B6/B7/B8 不显著；**B9（截断 128→32）降 14~16pp、B10（价值权重 ×4）降 9.4pp、
  criticwarm（先只训 critic）崩 42.8pp**。**没有任何一条让成绩变好。**
- **B1（换种子）/B2（批大小）/B3（学习率）/B4（λ）根本没测到**——全是基础设施故障
  （CUDA 抢用 / 显存不够）。**不许把它们当成"被证否"。**
- **★ 刚量出来的关键事实**（v3 1M sampled，1024 局）——**失败是两种完全不同的病**：

| 簇 | 占总局 | 峰值火力 | 杀敌 | 判读 |
|---|---|---|---|---|
| **赢** | 90.72% | 22.47 | 157.3 | 基准 |
| **死在最后一波 (30)** | 1.17% | **22.50** | 144.8 | **打得跟赢局一样好，还是输**；种得更多(61.5 vs 49.5)、花得更多(6025 vs 5029) |
| 晚死 (25-29) | 0.68% | 21.71 | 122.0 | 同上 |
| **中死 (13-24)** | **5.57%** | **16.37** | **39.8** | **防线没建起来** |
| **早死 (≤12)** | **1.86%** | **12.11** | **13.8** | **完全没建起防线** |

**⚠️ 累计量有 confound**：死得早 → 局短 → 累计量天然都小。
（早死局**每波**种 4.5 次，赢局每波只种 1.65 次——**按比率反而更密**。）
**→ 必须用"每波/每 tick 的比率"或"死前那一刻的状态"，不能直接比累计量。**

## 2. 轨道 A：**看清它在干什么**（纯读数据，全程并行，**先做**）

### A1 ★ 失败分簇的完整画像
用 `artifacts/research/bc_eval_1024_v1/output/` 下 5 个节点的 1024 局 raw
（v3 初始点 / 100k / 500k / 1M × greedy+sampled，加 A/B 100k）。
**对每个节点**，按 `terminal_wave` 分簇：**赢 / 最后一波(30) / 晚死(25-29) / 中死(13-24) / 早死(≤12)**。

**每簇算这些（注意用比率，不要累计量）**：
- `peak_offense`、`events.zombies_killed`、`events.sun_spent`、`events.sun_produced`、
  `events.plants_eaten`、`events.mower_triggered`、`action_counts.*`
- **每波的种植次数 / 每波的等待次数 / 每 1000 tick 的花费**
- `economy_curve` 的形状（12k/24k/36k/48k tick 的余额）
- **各簇占比随训练的演化**（起点 → 100k → 500k → 1M，每簇比例怎么变）

**产出**：一张"节点 × 簇"的表 + **每个簇的典型画像一句话**。

### A2 ★ "死在最后一波"专门分析（12~24 局，火力跟赢局一样却输）
- 最后一波**之前**的余额（`economy_curve` 最后两个点）
- 最后一波的 `wait_records` 密度（决策间隔有没有变）
- `mower_triggered`（割草机是不是已经用完了）
- 和**同种子的赢局**对比（A1 的赢簇里有没有同种子？没有就找最接近的）
**产出**：**"它最后一波到底缺什么"** 的一句话结论 + 数字。

### A3 ★ "早死/中死"专门分析（为什么建不起防线）
- 开局前 3 波种了什么（`action_counts` 不够，**要用 `capture` 出来的序列，见 C**）
- **先只用现有字段做**：`economy_curve` 前 12k tick 的花费 vs 赢局
- 这些局是不是"某个种子固定会死"（跨节点看同一批种子）
**产出**：一句话 + 数字。

### A4 种子难度分层
把 256 个种子按"跨 11 个评估节点的胜负稳定性"分层（全赢 / 全输 / 会翻转）。
**每层的行为画像**（火力、花费、杀敌）。
**产出**：**"哪些种子是天生打不过的"** —— 这决定训练任务池要不要换。

## 3. 轨道 B：**用"策略自己的两个阶段"做参考对照**（★ 最有价值的一招）

### ⚠️ 先说清楚：**不要用脚本基线当参考打法**

`scripts/scripted_baseline.py` 的作者在文件开头明确写了：

> "A **deliberately simple hand-written policy**, used as a **difficulty probe**.
> The point is **not to write a good bot** … a **40-line rule bot**"

而且 `RESEARCH_EXECUTION.md:805` 记录：`wait` 和 `scripted` 都是非学习控制，**"0 胜"**。
**→ 它一局都赢不了，拿它当"参考"等于拿全输的对照说"你走错了"。**

**只需要花 5 分钟做一件事**：在 level 7 上跑几局 `--policy scripted`，
**确认它的胜率是不是 0**。是 0 就在报告里写明"**已确认脚本基线在本任务上 0 胜，不作为参考**"，然后**彻底放弃这个思路**。

### ★ 正确的参考：**策略自己在不同训练阶段的对照**

**核心思路**：同一个种子、同一个任务、同一个环境，**只换检查点**。
这样"哪里不同"就只可能来自策略本身——**不需要任何外部基线**。

**分组**（用 `bc_eval_1024_v1` 的 v3 初始点 vs v3 1M，同 1024 个种子按 seed 配对）：

| 组 | 定义 | 要回答什么 |
|---|---|---|
| **B1 学会了** | 起点**输**、1M **赢** | **它改了什么才赢的** ← 最重要 |
| **B2 学废了** | 起点**赢**、1M **输** | **它改了什么才输的** |
| **B3 一直输** | 起点输、1M 也输 | **它一直错在哪** |
| **B4 一直赢**（对照） | 两边都赢 | 基准打法 |

**做法**：
1. 从每组里各取 **20~30 个种子**（不够就取全部）
2. 用 `capture --policy ppo --checkpoint <pt>` 跑 **v3 起点**和 **v3 1M** 两个检查点（**同一批种子**）
3. **逐决策对齐两个动作序列，找第一个分叉点**
4. 统计：
   - **分叉点集中在第几波**？（如果集中在某一波，那就是关键）
   - **分叉时两边各做了什么动作**（类型 + 目标格子）
   - **分叉之后那局的结局**
   - **同组内分叉点有没有共性**
5. **再做一层**：对同一组的"赢局"和"输局"，**把它们的动作序列在相同波数处对齐**，
   看**输局从哪一步开始和赢局不一样**

**产出**：**"它第一次走错是在哪里、错成什么样、走对了会怎样"** —— 这是本次任务最想要的答案。

### B5 补充：不要只信"第一个分叉"
轨迹一旦分叉，后面全都不同，**"第一个分叉"不等于"错误"**。
所以必须**同时统计分叉点的分布**：如果 20 局里有 15 局都在第 12 波分叉，那才是有意义的信号；
如果分叉点散得到处都是，**就报告"没有集中的分叉点"**，不要硬找。
