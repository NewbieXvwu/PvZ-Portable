## 第6步：n10 为什么更好（墓碑吞噬者一次都没种？）

**结论：任务书里的前提是读数错误，不是事实。** `games.jsonl` 的 `planted` 键是**卡槽序号**，不是植物类型；把 n9（9 槽，slot 8 = 阳光菇 9）与 n10（10 槽，slot 9 = 墓碑吞噬者 11）按同一个数字比较，就会把“n9 没有 slot 9”读成“阳光菇 0 棵”，把 n10 的 slot 9 读成“阳光菇 5–14 棵”。

证据：

- `src/main.cpp:469` 是 `std::array<int,10> planted{}`，`:525` 是 `++planted[action.packet]`；`scripts/search_play.py` 的 Python 循环同样按 `action["packet"]`（槽）累加。两者都是槽索引。
- 单局逐动作核对（同 seed 30000、L14、纯学生）：n9 的动作按槽 {8: 74} 对应类型 {9: 74}，`games.jsonl` 写的是 `"8": 74`；n10 的动作按槽 {9: 7} 对应类型 {11: 7}，`games.jsonl` 写的是 `"9": 7`。逐键完全一致。
- 因此 n9 的阳光菇一直是每局约 66–69 棵（不是 0），n10 的墓碑吞噬者是每局 4.7–13.6 棵（不是 0）。

### 6.3 老师为什么不种阳光菇（同样不成立）

用 dw4i_s1 做老师、n9 L12、同 seed 4 局、`--no-halving`（每个候选同样 3 条未来，值可直接比较）重跑并留档：

- 1560 个搜索决策里 672 个（43.1%）有阳光菇候选；其中 321 个（47.9%）阳光菇是最好的种植候选。
- 但只有 57 个决策（占候选决策 8.5%）真的选了阳光菇；四局合计种了 281 棵（约 70 棵/局）——**老师不是不种，只是搜索锚定学生动作时很少改选它**。
- 阳光菇是最好的种植候选时，91.9% 没被选；它与被选动作的价值差中位数只有 0.0008、均值 0.0077，只有 15.6% 超过 `--margin 0.02` 的改选门槛。
- 引擎常数解释了为什么它的估值偏低：阳光菇造价 25，产阳光间隔 2500 tick（`mLaunchRate`，Plant.cpp:58），小形态每次 15 阳光（Coin.cpp:1299），12000 tick 后才长大（Plant.cpp:1076–1096 与 `mStateCountdown = 12000`）。而搜索的 `--horizon` 是 2500 tick：造价 25 需要两次 15 阳光掉落才回本（约 5000 tick = 2 个视野），长大后的 25 阳光/2500 tick 完全在视野之外（12000/2500 = 4.8 个视野）。所以搜索对它的估值天然偏保守，但这只是“偏保守”，不是“从不种”。

### 建议（不改默认）

1. **n10 作为夜间卡组是对的**，理由要改成“墓碑吞噬者被真的用上、清坟减少最后一波坟头僵尸”，不是“阳光菇开始被种”。
2. **修报表口径**：`planted` 按槽索引，跨卡组比较前必须用卡组把槽翻成类型。这次的误读已经导致一整条诊断方向跑偏；建议后续在面板/汇总层统一按类型输出（不改 C++ 协议、不改默认）。
3. 想进一步确认清坟的因果，可做“n10 但墓碑吞噬者设为不可用”或“无坟头夜间关”的对照；本次控制组只排除了“空槽扰动”。
