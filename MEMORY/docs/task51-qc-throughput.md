## 背景
用户 10-23 定的判据：到 10-27，纯 CPU **正式课程采集的整局吞吐**（同任务族同倍率，局 / 小时）对 10-22 旧构建：
- ≥ 2.0×：GPU 线继续退役；
- < 1.5×：复活 GPU，先做占采集时间最多的族；
- 中间由主控定。

已有的单项数字：
- task35 引擎整局四族几何平均约 1.67×；
- task37 价值网进引擎，CPU 再降到 0.78–0.82；
- 还有一个反向因素：qc 轮间打包空转，task49 在修。

这些是基准测出来的，不是正式采集的口径。

## 要做的
1. **定口径**：
   - "正式课程采集整局吞吐" = qc 实际产出的局数 ÷ 墙钟小时。分两种报：
     - (a) 只算采集段；
     - (b) 含轮间打包训练。
   - 按任务族 × 倍率分开报；
   - 从 `~/pvz-logs/curriculum.log`、`~/pvz-logs/qc.out`、`~/pvz-logs/metrics/` 与历史 qc 日志里取数。10-22 旧构建时期的日志若已轮转，就去 `~/pvz-logs` 和 qc 的状态目录找。
   - 同时报 worker 数和 MemAvailable 的影响：worker 数受内存公式约束，旧新时期的 worker 数可能不同，要归一到每 worker。
2. **受控对照**（日志口径混入太多变量，必须补这个）：
   - 10-22 旧构建：cq 工作树在 10-22 用的那份二进制与 Python，从 git 历史找提交号，在本工作树另建 `build-old/`；
   - 现行：deploy2 + cq 现版；task50 完成后再加 deploy3 + zones；
   - 在**同样的 worker 数、同一批任务与种子**下各跑一小段正式采集命令（照 `curriculum_queue.py` 的 `command_for`）；
   - 四族各 16 局：白天 L7 d7、夜间 L14 n10、泳池 L24 p9k、传送带 L10 orig；
   - 机器有负载就按配对 + 交替。
3. **结论表**：每族、整体两个比值（只采集 / 含轮间），对照判据给出"≥2.0 / 1.5–2.0 / <1.5"落在哪一档。如果在中间档，列出差距主要来自哪一段。
4. 结果写 `MEMORY/docs/qc-throughput-20261027.md`。提交、push，在本文"结果"记一行。
