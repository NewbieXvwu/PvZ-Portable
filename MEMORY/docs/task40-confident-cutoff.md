## 问题

- 夜间族按任务书取 L14，而不是 bench_engine 的 L12–14 合并族。frames_v2 的 n14 档 meta 没有卡组，按首帧 packets 重建为 `[0,1,2,3,4,5,7,8,9]`（9 张，没有墓碑吞噬者 11；与 queue103 注释里的 n10 十卡组不同）——本测量按存档实际卡组回放，不自造卡组。
- 前缀校验第一次实现按 “trace 行 observation.tick == 叶 tick” 配对，32 例中 1 例误报：植物动作不推进 tick，同一 tick 会有多个决策点，按 tick 取到了后一个决策。改成按决策序号（t 推演最后一个动作之后的下一决策）配对后 32/32 通过——这是测量脚本配对口径的问题，不是引擎前缀性质的问题。
- task37（`vcpp`）不可作为第 2 步的依赖：`src/EnvironmentValueNet.{h,cpp}` 与 `LOAD_VALUE_NET` / `STATIC_SCORES` / `LEAF_VALUES` 已在该本地分支提交（fe2a5aff 等），但没有 `origin/vcpp`（未 push），工作树还有未提交的文档 / 测试 / 脚本改动；task37 自己记录“朴素前向性能回退（worker CPU 16.46→3.74 s，引擎 100.58→174.57 s）定位中、未验收为加速”。任务书说“已可用就基于它”，按此判据它不可用；第 2 步先用 Python 侧验收慢版本量质量，速度留给引擎实现（见第 2 步记录）。
- `confident_cutoff.py report` 修了两个 bug 后才有上面的表：① 某格没有自信推演时 `round(None)` 崩溃；② 汇总表误用了上一族循环残留的 `full` 变量，一度打出 |差| p95=0.837 的假数（数据本身最大 |差| 只有 0.21）。两处都只影响报表，不影响 JSONL。
- 测量口径说明：t 叶是“最后一个动作执行完、下一决策开始前”的状态；与 2500 推演按决策序号（而非 tick）配对，32/32 一致。t 推演若在 t 前已终局，则按 `_score_terminal_or_value` 取 0/1，不参与检查点自信判断。
