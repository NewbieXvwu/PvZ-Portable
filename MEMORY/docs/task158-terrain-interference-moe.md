# task158：地形之间是否互相拖累？按地形路由的专家（MoE）对照

分支 `terrainmoe`，基于 `origin/prodint16`。训练在 Mac 上做；台式机只做只读的数据抽样。

## 背景

- 门禁 v5 要求每个地形都不能显著退步。r26 白天退步、r28 夜间退步被否决；关卡平衡的 B 配方（屋顶权重 2% → 10%）自 r27 起从没被选中。
- r36 训练包：白天 66%（L7 一关 47%），夜间 18%，泳池 11%，雾 4%，屋顶 1.8%（见 `task156-data-mix-census.md`）。
- 现行学生只有约 18 万参数（宽 64 CNN）。10-22 task23：同语料宽 128 补回了一半早关差距。
- 计划 382 行定过顺序：先测干扰，再在“加宽 / 按地形适配层 / MoE”里对照。
- 按地形硬路由的好处：地形在输入里已知，不用学路由器；推理只算一个专家，续走速度不变（加宽做不到这点）；以后门禁可以只换某个地形的专家，不影响其他地形。

## 要做的

1. **抽样数据**（台式机，只读）：从 r36 训练包（`~/pvz-logs/curriculum_state.pipeline/frames/packs/5ef558eee5632210.npz`，读法见 `scripts/train_rollout_policy.py` / `python/pvz_training_pack.py`）按地形分层抽样，每个地形最多约 60 万行，留出按对局划分（同一局不跨训练 / 留出），压成小 npz，总量 ≤ 2 GB，拷到 Mac。v2timer 包若已打好也可以用。
   - 台式机约束：先看 `free -g`；单进程，systemd 用户服务限内存（MemoryMax 4G），Nice=10；不碰 qc 和生产状态；不 `pkill -f` 含 `curriculum_queue` 的模式。
2. **对照臂**（Mac，同数据、同轮数、至少 2 个种子）：
   - 联合 64（现行）；
   - 联合 128（加宽，参数约 3–4 倍）；
   - 每个地形单独一个 64（5 个网络，各只用本地形数据）；
   - 共享主干 + 按地形路由的专家：前两层卷积共享，第三层和三个头按地形各一份（硬路由），总参数与联合 128 大致相当，单次推理成本与联合 64 相当；
   - 有余力再加：联合 64 + 地形嵌入 / FiLM 调制（最便宜的条件化）。
3. **指标**：各地形留出上的完整动作准确率、种 / 等 AUC、等待误判、卡包 / 格子准确率，均值与范围。判读：
   - 单独网络在小地形（屋顶、雾）上比联合 64 好 → 存在干扰或数据被淹没；
   - 联合 128 追平单独网络 → 是容量问题，加宽即可；
   - 专家臂在所有地形都不差于联合 128，且推理成本低 → 推荐专家方案。
4. 写清在生产里实现专家方案要改哪些东西：C++ 前向（按地形选权重）、训练器、导出格式、门禁能否按专家分别晋升。

## 生产改造（与测量结果无关的机制部分）

### A. 零 C++ 改动的部署路径（专家臂已经可用）

五个宽 64 的 RolloutNet 与产品学生同构（obs v2timer、meanmax、row_pool、identity 头），
`pvz_rollout_policy.export_student` 直接产出五份 PVZRN006。地形在输入里已知且一局内不变：

- `python/pvz_env.py:808 load_rollout_net` 加载任意一份；
- `src/main.cpp:813` 的 `LOAD_ROLLOUT_NET` 明确支持在同一模拟器进程内换网络，
  `src/EnvironmentRollout.cpp:135-142` 在成功 Load 后清空全部派生缓存（im2col 通道表、
  权重双精度缓存、packet logits），因此逐局换模型是安全的；
- `scripts/search_play.py:678-681` 现在只在 worker 首次创建 env 时加载一次。要改成每局
  （`_play` 拿到 `kw["level"]` 后）用 `pvz_constants.background_for_level(level)` 选文件并重载；
  教师的续走用的就是这个 C++ 网络，所以教师与学生同时切换；
- 若用 `--student-candidates`，Python 侧 `_W["fast"]`（`act` / `ranked_plants`）也要
  `load_student` 对应地形文件，并与当前地形一起记账，避免两套网络不同步；
- 部署清单写 `terrain → 文件路径 + sha256`，未晋升的地形继续指向现行 joint64 文件。

### B. 单文件方案（PVZRN007，可省一次重载，非必要）

header 增加专家数与 terrain→expert 映射；共享层（0–3、6、7）存一份，专家层
（4、5、8–16、19、20）每地形一份。`Load` 的 counts 按专家复制，`Encode` 用共享层，
`Heads`/第三层按传入的 terrain 索引。terrain 由协议参数传入比在 C++ 里再解析关卡表更稳。
hard_moe 这种“共享主干 + 分地形头”的结构只能走这条路，expert 臂不必。

### C. 训练器与导出

`scripts/train_terrain_arms.py --arm experts` 已实现“按地形过滤训练行、同一验证种子划分”。
生产化只需：用 r36 全量按地形各训一份、导出五份 PVZRN006、把行数/地形/种子写进训练日志；
五份 checkpoint 与数据仍走 HF，不进 git。

### D. 门禁能否按专家晋升

v5 面板本来就按 day/night/pool/fog/roof 分 zone（`python/pvz_promotion.py:71` 起），
`decide_scored` 的 Holm–Bonferroni zone veto 就是逐地形判定。但 `promotion_gate.py`
的 contract 只接受“一个 candidate 文件 vs 一个 incumbent 文件”，总体 -3pp 规则是全局的。
按专家晋升需要二选一：

1. 按地形跑五次门禁：面板只取该 zone 的任务，总体规则退化为该地形，证书写明 terrain；
2. 扩展 contract 接受 terrain→file 映射，总体规则在“混合部署”（每 zone 用对应专家）上重算。

在扩展前**不能**拿单地形证书替换混合部署里的一个文件后声称整体通过；
未晋升的地形必须继续用现行学生。

## 结果（2 个种子，均值 [种子范围]）

### 读表前：一次输入口径修正

第一轮硬路由 / 软门控 / FiLM 的报告作废（备份在 `artifacts/terrainmoe/confounded/`）。
原因：`RolloutNet` 的 identity 卡包头在 `encode` 里先把 108 个旧式逐槽标量清零，再按植物种类
做 scatter-amax（`python/pvz_rollout_policy.py:130-140`）；而这三个自写结构直接读旧式逐槽标量。
同一权重上两个网络算出的输入不同，结果不可比。修正方法是三处 forward 统一调用
`identity_scalars(scalars, packet_info)`（`scripts/train_terrain_arms.py`），然后三臂 × 2 种子重训。
硬路由拆成五个 RolloutNet 的等价性在这之后复验：同一批、同一地形子集上逐位一致
（plant/packet/cell 最大相对差 0.0，`missing=[] unexpected=[]`，每个 182,147 参数，
导出 728,624 B = PVZRN006）；只有不同批次组成下的 MKL 累加顺序带来 ~2.6e-3 的绝对差
（logit 量级 ~100，相对 2.6e-5），不是语义差。

代价一栏按每行 MAC 解析计算（不是墙钟，MPS 上小批量分块会放大）：联合64 9.37 M、
联合128 29.39 M（3.14×）、硬路由与单地形 9.37 M（同样的层，硬路由只是权重 2.35×）、
软门控 14.29 M（共享两层 + 5 份第三层，1.52×）、FiLM 9.37 M。

### 3. 软门控的路由学到了什么

- 种子 1：专家 1 一次也没被选中（五个地形的计数都是 0）；种子 2：专家 0 只在夜间被选中 10 次
  （seen）/ 25 次（unseen），日间、泳池、雾、屋顶都是 0。
- 种子 1 的 top-1 专家按地形：day→3、night→0、pool→0、fog→0、roof→3；种子 2：day→2、night→2、
  pool→2、fog→3、roof→3。`distinct_dominant` 两个种子都是 2（五个地形只落到 2 个主导专家）。
- 归一化熵 0.47–0.63（最大值 1），主导份额 0.47–0.80。
- 结论：**没有退化成“地形分类器”**——五个地形并不对应五个专家，反而有两个专家闲置。
  但这也不是好消息：top-2 软混合在每个地形内部几乎五五开，等于在主干中段做了一次
  大号平均池化，代价 1.52×，收益在陌生卡组上是负的（all −0.97pp，屋顶 −2.86pp）。

### 4. 单地形专家有没有“训练不足”的嫌疑

有。五个专家各自只过本地形约 50 万行 × 12 epoch；联合臂同样每地形过 12 遍本地形数据，
但优化器步数是专家的 5 倍。这个方向只会**低估**专家，不会高估，所以“专家没赢”本身是保守结论；
在任务书点名的小地形（雾、屋顶）上我另跑了等步数对照：每地形 60 epoch，2 个种子
（`--terrains fog,roof --epochs 60 --tag eq60_`，结果在 `experts_eq60__s{1,2}.json`）。

## 判读（任务书的三条）

1. **单独网络在小地形上比联合 64 好 → 存在干扰。** 不成立。屋顶 seen −2.52pp、pool −1.07pp、
   day −0.77pp，雾 −0.07pp；陌生卡组上屋顶 +0.28pp、雾 −0.15pp。唯一正号是日间陌生卡组
   +2.08pp（两个种子都为正）。数据被淹没或者地形互相拖累的说法得不到支持：
   只看本地形数据的网络，连自己地形都赢不了联合网络。
2. **联合 128 追平单独网络 → 是容量问题。** 见过卡组：追平且超过（每个地形 +0.43…+0.76pp）。
   陌生卡组：日间仍落后专家 1.29pp、屋顶反而超过专家 1.30pp、雾比联合 64 低 0.43pp
   （两个种子都低）。所以“容量”能解释见过卡组上的差距，解释不了陌生卡组：
   加宽买到的是对现有卡组的拟合，不是对新卡组的泛化。10-22 的教训（加宽伤陌生卡组和夜间）
   在这个样本上只部分复现：夜间 +0.34pp、陌生卡组总体 +0.59pp，都没退，只有雾退了 0.43pp。
   这不构成给“加宽”翻案——本样本只有 12 epoch、2 个种子，且泳池的陌生卡组池子极薄。
3. **专家臂在所有地形都不差于联合 128，且推理成本低 → 推荐专家方案。** 单地形专家臂不满足
   （陌生卡组泳池 35.41%，比联合 64 低 15.34pp，等待行有 41.3% 被判成种植；
   该地形 96.9% 的行属于同一副卡组，专家在训练里没见过第二副，泛化不了）。
   **硬路由臂满足“不差于联合 64”的通过条件**：见过卡组每个地形 +0.12…+0.55pp，
   陌生卡组每个地形 +0.14…+4.33pp，总体 +0.36pp / +1.89pp，代价只有 2.35 倍权重、
   算力 1.0×。它也比联合 128 在陌生卡组总体上高 1.29pp，但**不能**说在所有指标上更好：
   陌生卡组泳池 AUC −7.04、屋顶 −2.24（相对联合 64），雾的漏种率 66.7%（联合 64 58.6%）。
   它在屋顶/雾上把动作准确率做上去的机制是“少误种、多等待”，AUC 并没有同步变好。

## 结论

1. **没有地形互相拖累的证据。** 按地形单独训练不带来任何地形的收益（日间陌生卡组除外），
   小地形（雾/屋顶）的短板在共享主干里反而更容易补。把专家的优化步数补齐到 5 倍（雾/屋顶各 60 epoch）
   只会过拟合：雾 seen 降约 2.1pp、两地形的陌生卡组 AUC 降 1.5…5.3。此前“先测干扰”的三次决定，
   答案是否。
2. **加宽（联合 128）只买到见过卡组的拟合。** 陌生卡组上它和联合 64 打平（+0.59pp），
   且雾上退 0.43pp；3.14× 算力换不到泛化。宽度继续维持 64。
3. **唯一值得继续的结构是硬路由（共享前两层 + 按地形选第三层与三个头）。** 它是唯一在
   “陌生卡组 × 各地形”两个维度都不低于联合 64 的臂，算力与联合 64 相同，参数量 2.35×；
   导出上它可以精确拆成五份 PVZRN006（已验证逐位一致），因此**不需要改 C++ 就能先试点**。
   但它的收益集中在雾/屋顶的陌生卡组，且以“多等待”换取，AUC 有退化；不能把它当成
   “全面更好”的结论，只值得一次全量 r36 + 面板的真实试验。
4. **放弃另外三个方向。** 单地形专家在泳池陌生卡组上崩掉（−15.34pp）；软门控没有学出地形划分，
   1.52× 算力换来陌生卡组 −0.97pp；FiLM 最便宜但没有稳定收益（日间陌生卡组 −2.64pp）。
5. **不要用本测量直接改生产。** 结论建立在 2,500,936 行的分层子样本、12 epoch、2 个种子上；
   泳池的陌生卡组只有 15,533 行且其中 96.9% 属于同一副主卡组，泳池结论最脆弱。
   下一步若要做，只能用硬路由臂在 r36 全量上重训，再走门禁 v5 面板。

## 硬路由臂落地要改的东西（在“生产改造”之上补充）

- **C++ 前向**：零改动即可先跑（五份 PVZRN006 + 逐局重载，见上文 A 节）；逐局重载的开销是
  一次性 `Load`（728 KB × 5 份常驻内存可接受），但会清掉 `EnvironmentRollout` 的派生缓存，
  每局第一次前向略慢，续走平均成本不变。要避免这次重载才需要 PVZRN007（B 节）。
- **训练器**：`scripts/train_terrain_arms.py --arm hard_moe --width 128` 已经能跑；
  生产化要把它并入 `scripts/train_rollout_policy.py` 的 recipe/检查点元数据（新增
  `structure=hard_moe`、`terrains=5` 两个字段），并让 `export_student` 接受“按地形拆成五份”。
- **导出格式**：五份 PVZRN006（已验证）或一份 PVZRN007。**不要**用 PVZRN006 存共享主干，
  C++ 的 `Load` 会按 width=64/identity/row_pool 逐一校验权重个数，多一份就是加载失败。
- **门禁**：`python/pvz_promotion.py` 的 zone 已经就是五个地形，但 `promotion_gate.py` 的
  contract 是单文件对单文件。要让硬路由分地形晋升，必须按 D 节的第 1 或第 2 条扩展；
  在那之前，只能把五份专家当作一个整体做一次“混合部署”的对照实验，证书里写明
  “五份文件同时替换”，不能只晋升其中一份。
