## 1. 对 Luna 产物的评价

审计（`hidden-state-audit.md`）**可用**：

- 最有价值的发现：完整 JSON 早就有大部分内部状态（植物 `state` / `state_countdown` / `launch_counter`、僵尸 `phase` / `has_object` / 分部血量、`wave_timer`），
  信息是在 `render_episode._frame()` 存帧和 `featurize_numpy()` 编码这两步丢的。所以 v2 主要是“别再丢”，不需要改游戏引擎。
- 源码定位（波次 `2500 + Rand(600)`、旗帜 4500、血量 0.5–0.65 提前刷新到 200、土豆雷布防 1500 tick、射手初始相位随机）可直接用。
- 实测：撑杆跳三阶段速度 0.670 / −0.051 / 0.296，土豆雷帧里约三分之一处于未布防。
- 弱点：只复用了 3 局旧轨迹；波次间隔没有测出来（它自己承认了，这点诚实）。

草案（`observation-v2-spec.md`）**只部分可用**：

- 错误 1：把“下一波 34 类计数”既标成特权信息、又算进学生的 39 个新标量，自相矛盾。
  而且它没发现老师续走前会 `RESEED`（`pvz_env.reseed`：重抽所有未开始的波次），老师本来就不知道未来波次。学生更不该知道。
- 错误 2：把射手冷却、土豆雷布防、樱桃引信混成一个“最短动作剩余”通道，语义混在一起。
- 错误 3：“带杆威胁”用数量 / 4 编码，丢了血量；更好的做法是像其他僵尸种类一样给血量通道。
- 可取：旧数据兼容分析（哪些能从旧帧回填、哪些只能新采）、缺失值要配缺失位、Python 与 C++ 固定同一索引。

## 2. 设计原则

1. **玩家可知原则**：只输入“一个记性完美的玩家看屏幕能知道的东西”的精确值。
   可以：位置、速度、有没有杆、土豆雷是否已起、豌豆射手离下次发射多久（看历史能推）、波次倒计时（进度条 + 记时）。
   不可以：随机数状态、未开始波次的名单。这样学生与老师（续走前 RESEED）信息口径一致。
2. **只加不改**：旧 92 通道 + 115 标量保持原值原序，新量追加在后面；旧权重可做初始化。
3. **一个量一个意思**：不同语义不共用一个通道；靠同格的植物种类通道区分是谁的进度。
4. **给“感知”，学“判断”**（用户 10:50 问“哪些该直接给、哪些该自己学”）：
   直接给的只有“当前状态”——学生没有记忆，从这一帧输入推不出来的事实（玩家靠看动画或靠记忆知道的）。
   状态的含义、后果和对策（多久碰到植物、哪行危险、现在种还是等、撑杆跳会跳过第一株植物）一律让网络自己学，不做“危险度”“接触时间”这类人工特征。
   判别方法：两个局面在输入里一模一样、正确做法却不同 → 缺信息，要给；输入能区分、模型仍做错 → 是学习问题，靠数据、容量、标签解决。
5. 学生与价值网络用同一套特征；换特征 = 两边都重训（同时完成计划第 8 项“闭环”）。

## 4. 实现顺序（交给 Codex 6.1 Sol）

1. `render_episode._frame()` 存帧时保留上述原始字段（僵尸 `has_object` / 分部血量 / `chilled` 计时，植物 `state` / `state_countdown` / `launch_counter` / `launch_rate`，
   子弹位置与伤害，`wave_timer`、大波标志、本波血量、天降阳光计时）。Lean JSON 补齐这些字段（`observation_version` + 1）。
2. Python `featurize`：`--obs v2`；旧帧缺字段的通道填 0、可用位 0。
3. C++ `EnvironmentRollout::Features()` 同步（老师续走必须能用 v2 学生）；Python 与 C++ 逐位一致测试。
4. 采集：新一轮 DAgger 起所有帧带新字段。
5. 验收：同数据比较 v1 / v2lite / v2 的学生上限（3 种子）；价值网络 v2 特征重训后比较配对准确率与老师 128 局。
