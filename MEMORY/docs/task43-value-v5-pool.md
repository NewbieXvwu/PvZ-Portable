## 结果

### 1. 通道说明（2026-10-23，CodeBuddy）

**采集器是现成的**：`scripts/value_ranking_check.py`（DESIGN §14.6 第二段）。做法：
从学生真实局面出发（`--rollout-policy`），在每个被抽中的决策（`--position-rate`）枚举候选
= 等待 + 每张可种卡片的 `--cells` 个学生最中意格子（+ `--random-cells` 个随机合法格）；
每个候选在 C++ 引擎里从**同一快照**推演 `--samples` 次，所有候选**共用同一批随机未来**
（`seed*1000+index*50+k`），每次推到 `--horizon`（默认 3000 tick）取叶子，再让学生续走到终局取结果。
一次决策因此给出「每个候选的叶子 → 该次运行的真实胜负」——相邻样本只差一步棋和随机未来，
正是搜索实际要回答的问题。

**落盘**：`--dump-shards DIR` 每个种子一个 torch 文件（`--dump` 是单文件，全在父进程内存里，不划算）：

| 键 | 形状 | 含义 |
|---|---|---|
| boards | float16 [N,92,6,10] | 叶子（kind 0）或种下瞬间的盘面（kind 1） |
| scalars | float32 [N,148] | v1 `featurize`(113) + 任务上下文(35) |
| won | float32 [N] | kind 0 = 该次运行的终局胜负；kind 1 = 该候选全部运行的平均 |
| seed / position / candidate / packet / kind | int64 [N] | 分组键；同一 (seed,position) 是一个决策 |
| config | dict[str,str] | 含 `task_id`、`rollout_policy`、`samples`、`horizon` 等，可追溯 |

**能不能直接进 v4 的训练入口**：`train_value_branches.py` 能读（按 (seed,position) 算成对一致率），
但 `train_value_widen.py` 有四处挡路，第 3 步补：

1. `initialize()` 只接受 encoder v1 检查点热启动；v4 是 v2（`scalar.0.weight` 154 列）→ 改成直接 `load_value_net`。
2. `Branches.__init__` 硬性要求 dump 的 `config['task_id']` 以 `day_l7_` 开头，泳池 dump 会被直接拒。
3. `Branches.batch` 把 6 个场景标量（夜/泳池/雾/屋顶/传送带/坟头）补 0。对 L7 白天正确，
   对 L21 泳池会把「泳池=1」抹成 0，等于喂分布外输入；dump 现在只存 v1 标量，场景位没落盘。
   → 采集时在 dump 里**加法式**多存一份 v2 标量（`encode_frame(f,2)`，154 维），v1 行不动，
   `train_value_branches.py` 不受影响。
4. 混训比例：`--branch-fraction` 只有一个来源旋钮；第 3 步按来源拆（泳池决策对 : 既有各区数据 = 1:1）。

**标签粒度**：整局标签（`generate_value_data.py` 与 `train_value_widen.py` 的 episode 行）是泳池 0/256 的来源；
决策级 dump 的 kind 0 每行是「这一步 + 这次随机未来」的终局，是本次要换的粒度。

**评估工具**：`value_leaf_dispersion.py`（`search_play --leaf-probe` 的 std / top1−top2 / 推翻率）与
`value_widen_ab.py`（同种子配对、McNemar 精确检验）。两者的臂名写死 v3/v4、引擎路径写死
`ROOT/build/pvz-portable`，第 4 步按任务书要求（deploy2 的 PGO 二进制、v5 对 v4）做最小改动并提交。

--position-rate 0.25 --workers 4`。

| 项 | 值 |
|---|---|
| 决策数 | 209（4 局，rate 0.25 → 约 52 决策/局，rate 1.0 约 209/局，与计划书的“每种子约 200 决策”一致） |
| dump 行数 | 2406（kind 0 叶子 1981、kind 1 种下瞬间 425） |

| 学生遗憾 / 可改判局面 | 0.0012 / 1 个 |

**关键发现（写进“问题”）**：叶子标签的胜率只有 **0.35%**（1981 条叶子跑出 7 胜）。
原因是续走用的是学生（`env.rollout(None, 0)` = 内嵌学生），而 dw4i_s1 单独打泳池 p9k 是 0/320；
老师 25/80 的胜率来自**每步都重新搜索**，不是任何单条推演。所以按原样采 64 种子，
标签仍是 99.6% 的 0，BCE 依旧会学成常数——这正是 v4 压平的机制，只是粒度换了一层。
先把这一点量清楚，再决定是否值得按计划采满。

### 3. 中途检查：v4 在 L21 决策上的排序（前 7 个种子，离线）

用 dump 里的叶子行（kind 0）与 `train_value_branches.pair_accuracy` 同一把尺子，v4 预测值分组后算：

| 项 | 值 |
|---|---|
| 决策 / 行 | 1312 / 14443（7 种子） |
| 叶子运行胜率 | 0.60% |
| v4 成对一致率（min-gap 0.25） | **0.500**（124 对） |
| v4 成对一致率（min-gap 0.5） | 0.375（8 对） |
| 同局面候选真实胜率无差 | **94.4%** 的局面 |
| 差距 ≥ 0.25 / ≥ 0.5 的局面 | 5.6% / 0.34% |

结论有两条，都写进“问题”：
1. **v4 在 L21 上不是“排序还行”，而是恰好掷硬币**（0.500，124 对）。所以问题不只是全败区压平——
   在可赢关 L21 上 v4 也没有可用排序，决策级数据有东西可教。
2. 但可教的量很薄：94% 的局面所有候选都输光，只有 5.6% 的局面存在 ≥0.25 的真实胜率差。
   按 64 种子 ≈ 1.3 万决策外推，可用成对样本约 1.3 千对。

> 以下记录第一轮已否决模型的数据来源。第二轮自结果§17起已采用真实搜索root与冻结老师终局续走；其验证与进度见后续各节。

源码复核：`value_ranking_check._game()` 用学生 `act()` 产生 root 轨迹，随后直接 `env.step(action)`；v4 只在 `_evaluate()` 内给候选打离线分，并没有驱动 root 的实际动作。`_evaluate()` 的终局续走也是 `env.rollout(None, 0)`。因此本轮证据应精确表述为**学生轨迹上的候选分叉 + 学生续走标签**，不能称为已采到“老师搜索轨迹 + 老师续走”的终局真值。

下一轮数据修法应同时从搜索老师的真实决策轨迹选 root，并让每个候选接搜索老师续走到终局；仅换标签粒度、增加同样学生轨迹种子，仍可能把不可挽回的状态和全零结果堆得更多。本轮 (a) 的失败只否定已经实测的这个数据版本，不证明老师续走标签无效；正式 (b)(c) 已按既定模型/种子完成（结果 §13–§15），不能用它们代替缺失的老师标签源。

### 问题 1：L21 的叶子标签几乎全负，决策级粒度只把常数拆成「0.35% 的 1」

> 以下是 4 种子冒烟时的发现。完整 64 种子已复核为叶子胜率 0.874%、94.54% 决策所有候选都输；训练及全部验收已结束，最终结论见结果 §16。

- 冒烟 4 局 1981 条叶子运行只有 7 胜（0.35%）。续走用的是内嵌学生（`env.rollout(None, 0)`），
  而 dw4i_s1 单独打泳池 p9k 是 0/320；老师 25/80 的胜率来自**每个决策都重新搜索**，
  不是任何一条「种下这一步、然后学生走完」的推演。
- 所以计划书里「每个搜索决策把全部候选各推演到终局，以实际胜率做标准答案」在泳池上并不自动成立：
  标准答案的分辨率取决于续走策略会不会赢。L7 上成立（学生能赢），泳池上不成立。
- 影响：按原样采 64 种子，标签仍是 99.6% 的 0，BCE 依旧把池子学成常数——与 v4 压平同一机制，
  只是换了一层粒度。这不是通道坏了（行、候选、终局都记对了），是标签源的问题。
- 复验结论：已经采满、训练并完成验收，(a)(b) 失败、(c) 通过，否决本轮候选。下一步按结果 §16 先做少量真实老师分叉/老师终局标签，检查可教信号与采集代价；波次次级真值可供诊断，尚未作为新训练目标实测。
