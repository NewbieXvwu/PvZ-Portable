# task134：训练准入在候选之间把采集压到 1 个 worker

主控 2026-10-27 派。分支 `admitfix`，基于台式机生产代码（deploy14i，58872f22）。

## 现象（生产日志 `~/pvz-logs/curriculum.log`）

- 训练进行中，采集正常拿到 13–14 个 worker（`background headroom 1.52 GiB`）。
- 每当一个候选训完、下一个候选还没获准入，`background headroom` 跳到 **14.59 GiB**，这时开组的采集只有 **workers=1/16**。这个 1-worker 组要跑完整组：12 局用了 **2558 s**，正常约 330 s。
- K=4 串行，一轮会有 3–4 次这种空档，每次白丢约 40 分钟的满速采集。看门狗也因为日志 40 分钟没有新行而报警。
- 18:33 门禁 v5 首轮出现过同样的情况：训练要求 MemAvailable ≥ 20.59 GiB（`MEMORY_RESERVE_BYTES` 6 GiB 加估计值），采集为它让出余量，结果两边都饿着。

## 要做的

1. 找出余量从 1.5 跳到 14.6 GiB 的原因（多半是准入前 `estimate_peak()` 按“数据全量 + 匿名峰值”预留，准入后才按实测算），改成不会让一个整组只开 1 个 worker。可选做法：
   - 准入等待时，采集组按“当前训练进程实际占用 + 小余量”计算；
   - 或者训练准入等组边界，组开工时不为还没开始的训练预留整份；
   - 或者给每组一个 worker 下限。
   由你评估后选一种，写明理由。
2. 复核 6 GiB 的 `MEMORY_RESERVE_BYTES` 和 `estimate_peak()` 是否重复计算：mmap 的数据页属于可回收的页缓存，MemAvailable 已经算进去了。
3. 只跑相关单测，台式机要限内存（AGENTS §6.5 第 7 条）。写 `~/pvz-logs/qc_deploy14j.sh`，不执行。未激活和回滚分支必须照抄 `qc_deploy15.sh` 的 `start_qc`（它是最新的部署脚本，看门狗会用它）。部署前检查要便宜。
4. 结论写在本文件末尾，推送分支。不碰 qc、状态文件和看门狗。
