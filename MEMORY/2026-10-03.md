## 环境确定性与"时间回溯"方案的可行性（本次实测）

用户提出把 LLM 接进来当教师，并给出方案：给 LLM 特权，允许它在**时间轴任意时刻**操作
（时间回溯），把问题转化为"在时间轴上做一系列操作，使失败点被推到最后一波之后"。
并反驳我的"让 LLM 写规则集"建议——理由是 `scripted_baseline.py` 本身就是 Agent 写的，
照样只有 37.9%，所以"问 LLM 要规则"就是把已失败的路径再走一遍。

**我接受这个反驳。** 我唯一能补的是：原脚本是**一次性写成、只测过一次**，
没有迭代回路；而 576 例验收只需 32 秒，理论上可以迭代上百轮。
但"LLM 凭直觉给规则"这一步确实已经失败过了。

### 实测事实（决定该方案的成本）

1. **环境完全确定**：`/tmp/determinism_probe.py`，两个独立进程各跑 seed
   30000/30001/30002，比较 (动作序列+tick+sun+僵尸数) 的 SHA256 摘要、
   终局 tick/wave/result/动作数 —— **逐位相同**。
2. **因此"时间回溯"不需要改模拟器**：确定性 + 快重放 ⇒ 从起点带修改后的动作前缀
   重放就是回溯。单局重放 **0.23 / 0.65 / 1.39 秒**（level7，1175/567/1128 决策）。
   8 worker ⇒ **约 10 次重放/秒 ≈ 3.6 万次 oracle 评估/小时**。零原生改动。
3. **目标是干净的序数**：level7 的 `wave_count = 30`，胜局恰好停在 **wave 30/30**
   （seed 30000 tick 65255、seed 30002 tick 63352），败局停在 17/30。
   注意 `wave` 不是"存活 tick"，**靠拖延无法伪造**，所以这个代理量比"存活时间"好得多。
4. **一局 level7 是约 1100 个决策**，不是之前记的 79（79 是空操作 wait-300 的粒度）。
   ⇒ 逐决策喂 LLM 的成本是 **576 例 × ~1100 = 63.4 万次调用**，比我上次估的 5.8 万高一个量级。

### 我判断该方案的三个真问题（不是反对，是必须处理）

1. **"把失败点推后"是贪心，而 PvZ 有延迟回报。** tick 1000 种的向日葵在 tick 5000 才回本。
   贪心地"修最早的那次失守"会系统性挤掉经济投入 → 卡在 wave 12–20 永远赢不了。
   ⇒ 必须是真搜索（种群/重启/接受暂时变差的移动），不能是爬山。
   目标函数本身没问题，**风险在贪心**。
2. **诚信红线：逐种子规划可以在不学任何东西的情况下刷满验收集。**
   256 个开发种子是**冻结且公开**的。若对每个种子单独搜出一条胜局轨迹，就能拿 100%
   而什么都没学到。⇒ 示范必须来自**不相交的种子集**，评估必须在 held-out 种子上，
   两个数字都要报。这是"真结果"和"假结果"的分界。
3. **1100 步计划内的信用分配**：是同一个老问题换了件衣服。
   缓解：对失败前最后 k 个动作做后缀重随机，或对时间轴二分定位。
   LLM 的语义编辑恰好在这里有用（"你死在 row 3 的铁桶，那里没有坚果墙"）。

### LLM 在这个方案里的精确角色

**不是 actor，也不是规则作者，而是"语义编辑的提议分布"。**
1100 维离散动作空间里随机扰动毫无希望；"在 tick 8000 左右给 row 3 插一个坚果墙"
是可信的编辑。关键差别：**编辑是被评估的，不是被信任的** —— 这与"写规则集"有本质区别。

### 附带的最大收益（可能比教师本身更重要）

这条路线会产出**全项目从未有过的东西：一个胜局轨迹语料库**。
- 能做 BC 诊断（网络能不能表示一条获胜轨迹）。
- **能训 critic**：现在 `mc_value_explained_variance` 为负/混乱，根因是策略从不获胜，
  "没赢过"就学不到"赢长什么样"。胜局轨迹直接补上这块。
- 可作为 off-policy RL 的先验回放池。

## 战报渲染器：把一局对局变成 LLM 可读的结构（提交 ea50e51）

**用户问题**："怎么把战局数据结构化喂给 LLM？需要一个真正对 LLM 友好的数据结构，

### 结论：不要喂原始观测 JSON，要喂三样东西 + 一份派生量

原始观测是 54 个格子 + 40 张种子卡 + 每只僵尸的 `phase_counter` 的数字墙。
LLM 从里面读不出"这把输在哪"，缺的不是数据量，是**参照系**和**因果锚点**。

`scripts/render_episode.py`（新，755 行）输出：

1. **参照系** —— 同一 seed 的空操作地板。没有它，"第 17/30 波"无法判断好坏。
2. **自动诊断** —— 机械信号直接点名，规则写在代码里可逐条核对。
3. **逐波态势矩阵** —— 整局压成一张表，每波取"僵尸最多那一帧"，格内"火力/僵尸数"。
   这是信息密度最高的一块。
4. **关键帧棋盘** —— ASCII 网格（一格一字符）+ 每路派生量。

### 关键的工程决定（都是踩过才知道的）

- **文本报告本身就是最好的 LLM 输入，JSON 是给代码用的。**
  对齐的表格没有重复键，比 `indent=2` 的 JSON 省得多。28 KB JSON 里有大半是
  `"shooters": 3, "economy": 2, ...` 这种重复键名。
- **"距割草机还剩多少 tick" 要用僵尸自己的 `velocity_x` 算**，且必须特判
  `velocity_x < 0.02`（正在啃植物的僵尸速度为 0）。不特判会算出 159957000t 这种
  天文数字。这是把"位置"翻译成"还剩多久"的关键一步，也是人读棋盘时真正在看的东西。
- **割草机检测必须按 row 去重**：一次触发会被看到两次（state→2 触发、随后从
  `defenses` 列表消失被回收）。不去重会报"第 10 波 [4] 号路；第 11 波 [4] 号路"。
- **割草机 state 语义**：`0=入场中 1=待命 2=已触发 3=被压扁`（`src/ConstEnums.h:569`）。
  `defenses` 列表里少一行 = 那一路后手已用完。
- **像素→列映射**：`col = floor((x - 40) / 80)`，来自 `Board::GridToPixelX` = `col*80 + LAWN_XMIN(40)`。
- **僵尸/植物类型编号**来自 `src/ConstEnums.h` 的 `SeedType` / `ZombieType`，
  已在脚本里做成中文名表。**不要凭记忆写**。
- **"最弱一路"规则在胜局也会触发**（总有最小值），所以措辞必须是描述性的
  （"五条路里相对最弱的一条"），不能写成判决。

## LLM 教师方案的三个决定（2026-10-03，用户拍板）

1. **预算无上限**，直到模型能打完一局。唯一防卡死措施：连着若干轮最好改动都是 +0 波
   就停下，去查工具哪里给的信息不够。
2. **"改动要能写成一句策略" → 直接让模型写 skill**，能总结并自演化。
   （这正好解决了我原来的"策略 vs 剧本"难题：skill 就是那个**可测的产物**——
   写完必须在没见过的种子上加载它再测一遍。）
3. 选型：**MCP 还是轻量 Harness**。用户倾向若做 Harness，就做成 DeepSeek Harness
   (DSH) 的预设 + 插件。

### 选型调研结论：**MCP server + DSH preset 两个都做，MCP 先**

两者不是二选一。DSH 自己的定义就是"Plugin 实现零件，Preset 选择零件并限定作用域"。

**DSH 关键事实（来源：官方 README + 官方文档站 + 第三方实操文，均为 2026-08~09）**
- **原生带 MCP 客户端**（`@deepseek-ai/dsh-mcp-client`），支持 stdio 与 streamable-http，
  带断线重连。所以 MCP 工具在 DSH 里是一等公民。
- 插件 = 导出 `apply(ctx)` 的 TS/ESM 模块，用 `defineTool({name, description,
  parameters, output, execute})` 注册工具。`inject: ['tools']` 声明依赖。
  工具走统一管道：`tools/pre-execute` → `tools/execute` → `tools/post-execute`。
- **Agent Preset = 一个目录**：`agent.cordis.yml`（可执行组合）+ `preset.yml`（展示元数据）
  + `skills/`（Preset Scope Skills）+ `local-plugin.mjs`（可选本地插件）。
  目录名即 Preset ID。作用域读取顺序：agent scope → preset scope → global scope。
- **压缩是可组装能力**（`compaction/` 家族）：`compaction-basic`（token 压力自动压缩）、
  `compaction-tool-result-pruner`（修剪超大工具输出）、`command-compact`（按需 /compact）。
  **可以显式挂载来调整压缩时机与方式。**
- **会话日志与模型可见内容分离**：原始事件留在**只追加日志**里，摘要作为一条替换消息
  进入模型可见面。**恢复和回放仍可用原始日志** —— 这解决了我对"压缩丢信息"的担忧。
- 随附四种 preset：标准 / **PTC**（用 TypeScript 程序组织多次工具调用，即"并发调工具"）/
  极简 / 创造。**Preset 只能在会话仍空白时切换**（中途换会让旧工具调用无法重放）。
- 有 **Python SDK**（`guide/python-sdk`）——我们的代码库是 Python，orchestrator 可以用 Python 写。
- 安装：`dsh plugin --profile <p> add ./dir|pkg|github:...`；配置分层
  profile.bundles → profile cordis.patch.yml → `$DSH_HOME/cordis.patch.yml` → `--patch`；
  后层胜出且**替换整个 config（非深度合并）**。改 config 有 HMR，不重启。
- Node 要求 ^22.19 或 >=24（本机托管 node 22.22.2 ✓）。

**用户提的三件事在 DSH 上都有现成落点**
| 用户的提法 | DSH 里的对应物 |
|---|---|
| LLM 并发调用工具 | PTC 模式的 Code Mode SDK |
| 让模型写 skill 自演化 | Preset Scope Skills（skill 的定义就是"一类任务应该怎样完成"） |
| 时间回溯（在任意时刻操作） | 不需要 DSH 能力，靠我们自己的 `whatif` 确定性重放 |

**为什么不自己写轻量 Harness**：agent loop、工具管道、权限审批、会话持久化、重连、
HMR、压缩、skill 加载、子代理委派——DSH 全有，且是它最成熟的部分。我原来唯一担心的
"上下文不受控"已被证伪（压缩可选可换，原始日志始终保留）。

**成本**：MCP server ≈200 行（Python `mcp` SDK，转发到现有 12 个子命令）；
DSH preset ≈100 行配置 + `skills/` 初始内容（就是我给用户看的那份方案改写成 skill 格式）。

**动手前必做（step 0）**：我引用的是第三方博客 + 官方 README 摘要，**没通读官方文档**。
要先读：`packages/preset/agent-presets/README.zh.md`、
`apps/cli/config/agent-presets` 的实际配置、`docs/subsystems/compaction.md`、
`guide/python-sdk`。DSH 是 v0.2 预览版，字段会变 → **锁版本**。

### 我对"无限预算"的两条补充（已向用户说明）
- 真正的风险不是"卡死"，是"烧了很多 token 之后发现工具信息不够，却不知道从哪一步开始不够"。
  所以无上限必须配**每一步落盘**（哪一步、提了什么、真实结果、当时的理由）——

## 切到 dsh-v0.2.0-rc.2 后重核（提交 6872460）—— preset 实现被整个换掉

**教训（写进判据）**：**DSH 的字段以源码为准，不以博客为准；源码以最新 tag 为准，
不以 clone 时的默认分支为准。** 我第一版读的是 clone 时的默认分支
`dsh-v0.1.2-rc.1`，把当时的结构当成了现行结构，整节重写了一遍。

`git fetch --tags` 后最新 tag = **`dsh-v0.2.0-rc.2`**，64 个包（v0.1.2 是 56 个）。

### 我说错的两处
1. "做成 Agent Preset" 只在 web profile 成立 —— `agent-preset-registry` **只挂
   `web-app` bundle**（base/headless/sdk-app/sdk-minimal 都没有）。
2. **"preset = 目录 + `agent.cordis.yml`" 是 v0.1 的形态，v0.2 已废弃。**
   v0.2 起 preset = bundle 补丁里的一行 `@deepseek-ai/dsh-agent-preset` 声明，
   `config` 字段 `id`(必填,小写字母数字连字符) / `plugins`(必填, Cordis entry list)
   / `name` / `description` / `order`。**注册表不扫描目录、不接受 preset 路径。**
   随附 preset 现在是 `packages/bundle/web-app/presets/{standard,ptc,minimal,cordis}.patch.yml`。

### 最终结论（两次更正后）
**preset 与 profile patch 本来就是同一个机制**（都是 bundle 补丁）。所以
"同一份行列表两处引用"不是妥协，而是它本来的设计：**写一个 bundle，装进 profile，
preset 声明就在里面**，根本不存在维护两份的问题。

  `package.json`（带 `dsh.bundle.patch`）+ `cordis.patch.yml`。

## S4：什么时候写 skill —— 判据 + 闸门（2026-10-03 下午）

### 起因

用户问：「需要定个标准，究竟什么时候写skill？不是每一局都有价值写skill 的」。

复盘 S3 发现根因**不是模型没内容，是没有判据**：S3 的最终回答里有 4 条
「可复用的判断」（质量不差），但**一条 skill 都没写**；它的推理轨迹（677 行）里
`skill` 这个词**出现 0 次**。没有判据时只有两种结果：写噪音，或干脆不写。

### 判据（三问，全过才写）

1. **反例问**：这条判断在什么情况下**不成立**？答不出 ⇒ 不是判断，是复述。
2. **证据问**：**至少 2 个不同决策点**上被 whatif 验过？只有 1 个 ⇒ 可能是运气。
3. **迁移问**：判据**换一局还能算出来**吗？带本局坐标 ⇒ 一次性答案。

**为什么是 2 个点**：S3 自己的数据 —— 挪到 `(3,3)` 通关，但 `(3,4)`/`(2,5)`/`(0,4)`
