# 用户立场（长期有效）

- 整个奖励系统/训练范式需要从头重新设计；**此前所有项目规矩都是他在特定时点定的，他有权推翻**。
- **一切从事实出发，不从书本出发。** 不许把项目里自己定的规则当物理定律 —— 不许说"做不到"，
  要说"**需要改哪一行**"。
- **不要再各种微调参数**（原话）。要问"它到底在干什么"。
- 派活原则：**长跑交给 codex（它在台式机不会关），本 Agent 负责把关**；但**"跑出来的东西对不对"不能交出去**。
- **（10-14）项目初衷与当前困境（用户自述）**：最初想要的是“像 AlphaGo 下围棋那样能打 PvZ 的 AI”。
  **很难接受退回手写公式**（“那还训个蛋的 AI，难道又做成专家系统？”）。算力只有一张 RTX 5080。
  用户自认 ML 了解不多，感到项目一直是 Agent 在建议往哪走，自己已经说不清想要什么。
  → **提方向性建议前先对齐“要什么”，别再替用户定方向**；用户手写的目标定义优先于任何 Agent 提议。
- **（10-14）用户给出的目标排序：5 自己学会 ML > 1 强（打通冒险模式）> 4 举一反三 > 3 超越人 > 2 策略自己学会。**
  用户对 ML 感兴趣但非科班，想亲手做；自认被 Agent 牵着走、把 Agent 当“许愿机”。
  → **Agent 的角色从“执行者”改成“导师”**：先解释、让用户决定并尽量亲手做；
  实验要能在几分钟到一小时内出结果（快反馈才学得到东西），不要再把整夜跑交给 codex 代劳。
- **（10-14）★ 用户厌恶 Agent 遇事先手搓一个公式/规则的条件反射**（原话：“这是你作为 Agent 所不知道的”）。
  **不要把“手写公式 / 规则脚本 / 阈值启发式”当默认解法提出来。**“教师起步 → 学生超越教师”是用户认可的理想形态；
  若起步必须借助已有脚本，要明说它只是起点、后面怎么被学习推翻。
- **（10-14）用户的学习路线**：时间和能力有限，先做出能跑的版本、在指挥中踩坑、理解基础概念，
  再回头学“为什么能成”（自上而下）。**最缺的是正反馈** → 每个里程碑要有看得见的成果，
  汇报时**正面结果要说清楚，不能埋在一堆问题和 caveat 下面**。
