
## task18 采集 worker 内存瘦身（slimworker 分支）

- 测量：worker 静态 160 MB private / 217 MB RSS，其中 torch 136 MB；三个网络 + 导出一共 2.4 MB。
  一局之内再涨 ~150 MB（档案帧列表 17.5 MB + 对局活对象 ~57 MB + 分配器高水位 ~70 MB），
  写档案再 +50 MB。不是泄漏（终局只剩 2 份完整观测活着）。
- 改法：`scripts/search_play.py` 里把 `_load_nets` 从 `_init_worker` 拆出，父进程预载 + fork 建池；
  再 `gc.collect() + gc.freeze()`（关键：不 freeze 时 GC 遍历继承堆，写时复制把共享页全私有化）；
  每局结束 `malloc_trim(0)`（glibc）。
- 结果（8 局 day_l9_train_d7，种子 1826000–1826007）：worker 峰值 454/377 → 304/247 MB，
  常态 170–210 MB，父进程 221 MB 一份共享拷贝。逐位一致（新脚本 `scripts/compare_run_bytes.py`）。
- 报告与未解问题写在 `MEMORY/docs/task18-slim-worker.md` 的结果/问题两节。
- 第二轮（同日）：第一轮"对局内 150 MB 是帧列表/活对象"的归因是错的 —— 探针里的 `psutil.Process()`
  是在 fork 之前建的，在子进程里一直报父进程的内存，曲线是平的。改成每次新建 `Process()` 后：
  活对象只涨 2 MB，涨的是 libmalloc 的空区域（已 free、macOS 不归还），也就是说
  **worker 的 RSS ≈ 本局最大的一次同时分配**，而那个高水位是价值网络一次全批前向
  （终局 ~240 帧 × 122 通道）。改成 `VALUE_BATCH=32` 固定分批后，峰值 304 → **124.8 MB**。
- 另外两条：`BRANCH_SNAPSHOT=8`（原来 128，模拟器每分支回一份完整观测，301.9 → 277.3）、
  `Pool(maxtasksperchild=1)` 每局回收进程（峰值不再随局数叠加，551 → 384 的和）。
  三条都逐位一致；8 个 worker 进程峰值 124.8/123.9/122.9/112.1/109.6/98.9/94.6/92.4 MB，全部 < 250。
- 方法论教训（写进报告问题第 7 条）：macOS 上 `malloc_zone_pressure_relief` 对已释放的 100 MB 返回 0 字节，
  别指望它回收；fork 子进程里量内存要么新建 `psutil.Process()`，要么从外部采样。
- 台式机复核（同日，Linux + fork + glibc，20 核 / 24 GB，load 13–22）：工作树
  `/home/newbiexvwu/PvZ-search/.claude/worktrees/slimworker` @ 67c12e5，`-j4` 编译；改前用只读的 rowpool
  （= origin/pvz-env）。同样 8 局、2 worker、同一组种子 → `compare_run_bytes.py` **identical**（两遍都一致）。
  改前每 worker RSS 峰值 594.9/590.5 MB（复现了任务书的 650 MB），PSS 401.7/399.1，私有脏页 393.7/391.5；
  改后每 worker 私有脏页 43–62 MB、PSS 143–181 MB，父进程一份 torch（552.6 RSS / 134.9 PSS）。
  墙钟 693.1 s vs 609.2 s，第二遍反过来，load 波动盖过差异。
- 教训（报告问题 §8）：Linux 上 fork 出来的 worker 的 RSS 含父进程共享页（394 MB），**不能拿 RSS 和 250 MB 比**，
  要比 PSS / 私有脏页；另外采样器判角色要用 `/proc/<pid>/comm`（cmdline 里有 `--executable .../pvz-portable`，
  会把 worker 全判成模拟器），找子进程要遍历 `/proc/<pid>/task/*/children`（multiprocessing 的 handler 线程 fork）。
