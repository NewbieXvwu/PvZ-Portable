## 教师"打不赢"的根因分析（本机实测，未改动任何训练产物）

新增三个诊断脚本（都可直接跑，资源目录 `/Users/newbiexvwu/Downloads/Plants_Vs_Zombies_V1.2.0.1073_EN`，Python 用 mise 3.14）：

- `scripts/scripted_baseline.py`：40 行手写规则策略，用作"任务到底能不能赢"的难度探针。

### 结论 1（最重要）：当前环境下**不可能赢**，不是打得好不好的问题

- 每局 t=0 场上就有 9–18 只"街头预览僵尸"（level 1:10 / 5:9 / 7:9 / 8:9 / 11:9 / 20:18 / 35:9），`has_head=1`，x∈[833,1068]，**永不移动、永不受伤、永不死亡**（追踪 7500 tick 位置逐位不变；跑满 1.79M tick 仍是同样 9 只）。
- 来源：`LawnApp::EnvironmentReset` 里 `StartLevelIntro()` + `CancelIntro()` → `CutScene::PlaceStreetZombies()`，这些僵尸 `mFromWave == ZOMBIE_WAVE_CUTSCENE`，`Zombie::IsOnBoard()` 对它们返回 false。
- 但 `Board::AreEnemyZombiesOnScreen()`（src/Lawn/Board.cpp:261）**不看 `IsOnBoard()`**，所以恒为 true；而唯一的通关判定 `Zombie::TrySpawnLevelAward()`（src/Lawn/Zombie.cpp:7135-7169）要求 `mCurrentWave >= mNumWaves && !AreEnemyZombiesOnScreen()` → **永不成立**。`CountZombiesOnScreen()`（Board.cpp:275）才是带 `IsOnBoard()` 的正确版本，胜利路径没用它。
- 实测：规则脚本在 seed 30000 活到 wave 30/30、tick 1,796,340（≈5 小时游戏时间）、30,000 个动作后仍未终局，场上只剩那 9 只。
- 修复方向（二选一，都要回归验证）：`AreEnemyZombiesOnScreen()` 增加 `IsOnBoard()` 条件；或 `EnvironmentReset` 在 `CancelIntro()` 后 `RemoveAllZombies()`。

### 结论 3：值模型自举是死循环

- 训练数据 100% 是败局，目标 `-0.99^((T-t)/300)` ∈ [-1, -0.41]，模型里不存在"赢"这个概念。
- 目标随 300 tick 只变 ~0.007；训练后兄弟动作预测差 spread=0.0102 / std=0.0030，而训练 RMSE=0.229（真实 32+32 集版 loss 0.0088 → RMSE≈0.094）→ 搜索在最大化噪声。

- 值模型随 tick 单调下降（0→900 tick: -0.7389→-0.7546，掉 0.0157，大于兄弟动作全部差异）→ 任何零 tick 动作严格优于等待 → 种了又铲。

## 架构层评审：教师设计本身是否成立（结论：不成立，非调参问题）

用户要求退一步评估 SearchTeacher 的架构，而不是继续查 bug。核心判断：
**整个设计是一个没有外部锚点的封闭自举环**——候选生成不带游戏先验、值模型从自己的败局学、
教师从值模型来、学生从教师来。环里没有任何组件知道"PvZ 该怎么打"。
自举在 AlphaZero 成立靠的是真实胜负信号 + 可穷举搜索；这里连"赢"在环境层都是死的。

四个原理级缺陷（不是参数问题，改参数修不好）：

1. **无外部锚点**：能守满 30 波的规则脚本是调查阶段才临时写的（`scripts/scripted_baseline.py`），
   说明设计阶段从未验证"任务存在可达解"。缺一个固化的 oracle / baseline 教师。
2. **值目标与用途错配**：搜索要用它做**相对排序**（兄弟叶差异 0.010），训练却做**绝对回归**
   （MSE，自身 RMSE 0.094）。用绝对回归分辨比自身误差小一个量级的差异，原理上不成立。
   且 `discounted_terminal_value = ±γ^(remaining/300)`（DISCOUNT_REFERENCE_TICKS=300）把"赢"压成符号、
   "进度"压成时间衰减，胜率 0 时退化为"还有多久死"。→ 应改 pairwise/排序损失 + 同决策内中心化 + 验证集。
3. **时间尺度错配 + 零 tick 退化**：horizon 900 tick ≈ 9 秒 < 一波 24–28 秒，也短于向日葵 ~45 秒回本，
   MPC **结构上不可能**表示"投资—回本"。且 PvZ 是分阶段任务，MPC 无机制表示"当前阶段"。
   零 tick 退化是动作空间时间语义与价值函数时间语义直接冲突，不是调参能解。
4. **教师→学生的桥搭错**：教师有 256 次模拟前瞻 + 完美状态，学生只有一次前向 + GRU；BC 只蒸馏 argmax
   是最弱蒸馏。**DAgger 只修分布偏移、不修目标错误**，原理上无救。能放大能力的只有环境奖励（RL）
   和搜索暴露的因果结构（值函数/候选排序），当前两样都没给学生（学生 value / aux_outcome 头标签同样 0 胜）。

次级：无课程（`zombie_count_multiplier` 下界 1.0，波数由 `gZombieWaves[level]` 定，env 无法缩短一局）；
候选生成的多样性是几何的而非语义的（向日葵被排到前排；开局 `lane_pressure` 全 0 时选择退化成列表顺序）；
流程上没有"能赢吗"这道 gate。

建议的六层修复（每层都在给闭环注入它缺的东西，顺序即依赖）：
1 修环境 +「能赢吗」冒烟测试做 stage gate → 2 规则脚本固化为课程教师，产出首批胜局轨迹 →
3 课程（需给 env 加可配置波数上限）→ 4 值模型改排序目标 + 验证集 + 密集塑形（击杀/阳光/波次进度）→
5 搜索：语义候选 + 分层视野（≥1 波）+ 软分配替代硬淘汰 + 禁止零 tick 退化 →
6 蒸馏值函数与候选排序（不止 argmax），教师可靠后再接 PPO 让环境奖励成为最终能力来源。

## 「推翻重写」提案的评估（结论：整仓重写 = 错，定向重写决策层 = 对）

用户提出前一个 Agent 能力弱、代码硬编码多，想整仓推翻重写。实测数据否决了整仓重写：

- **魔数密度分布证明垃圾是局部的**（每百行浮点魔数）：`pvz_env.py` **0.6**（720 行仅 5 个，
  全仓最干净）、`pvz_agent_model.py` 4.5、`pvz_imitation.py` 8.1、`pvz_search.py` 8.7、
  `pvz_search_candidates.py` 10.4、`pvz_search_value.py` **19.0**。垃圾集中在决策层，不在基础设施层。
- **依赖严格单向，分层是对的**：`pvz_agent_model` / `pvz_env` / `pvz_value` / `pvz_common` 零业务依赖，
  决策层（search / search_candidates / search_value / imitation）依赖它们，反向没有。
  → 决策层可整体摘换，基础设施一行不动。设计决策错了，但抽象边界没画错。
- **已证明正确的资产重建不起**：`2e62d07` 修的是"同进程第二个 episode 不可复现" + restore 丢状态
  SIGSEGV，并用变异测试证明验证脚本有效；加上 192 个 Python 测试、跨进程 hash 稳定、二进制等价性。
  这类 bug 重写时会静默复发（症状只是"结果有点不对"）。
- 测试总数 192：test_search_teacher 49 / test_agent_model 37 / test_env_protocol 27 /
  test_training_semantics 26 / test_search_audit 19 / test_shared_helpers 18 /
  test_search_value_features 15 / test_seed_jobs 1。

**关键警告（比"要不要重写"更重要）**：重写前必须先有 oracle，否则新代码同样无法判断好坏，只会再来一轮 0/1024。
顺序强制为：修 L0 +「能赢吗」gate + 固化规则脚本课程教师 → 然后才重写决策层。

**测试会锁死设计**：test_search_teacher(49) 与 test_search_value_features(15) 的断言编码了当前设计，
重写时必然全红。这不是坏事，但要先定设计再定测试，不要试图让旧测试通过。

切分方案：保留 env + 学生编码器 + 预算记账/可观测性；重写候选生成 + 值目标 + 搜索结构；
新增课程教师 + 可配置波数 + 排序损失 + 蒸馏桥。

## 关键实测：模拟器吞吐（改变设计结论的数字）

用户要求从头设计（反对 MVP、反对只刷一个关卡、反对硬编码僵化脚本）。设计前先测了吞吐：

- **243,893 game-ticks/s**（level 7，seed 30000–30004，随机合法策略跑完整局，Mac 本机 `build/pvz-portable`）
- 单核 26.3 局/s（随机短局）；**推算 40,000 tick 的完整胜局仅 0.16 s**，约 20,000 局/小时/核
- 观测 token 数实测约 64（含 54 cell）
- 对照组：`SearchTeacher.advice()` 一次决策约 **150 ms** → **搜索比环境推进慢约 3 个数量级**

**这条实测推翻了当前路线的两个前提**：① 样本并不稀缺，"用教师蒸馏省样本"的动机不存在；
② 搜索不是资产是负债，它把采集吞吐压低约 1000 倍，换来的只是跨不过一波的局部信息。
→ 新设计原则：**让环境的速度决定架构，不要让教师的成本决定架构。**

## DESIGN.md（仓库根，新设计文档，取代教师蒸馏路线）

范式改为「任务族上的直接强化学习」，要点：

- **任务族参数化**：`θ=(level, deck, zombie_count_multiplier, wave_cap, sun_start, preplanted, scene)`。
  `wave_cap`（波数上限）与 `preplanted`（开局预置）是**当前 env 缺的、必须新增**的能力，是课程与能力拆解的物理前提。
- **自适应难度前沿**（POET 式，按 pass rate ∈ [0.2,0.8] 动态调权），不手写课程表（那本身也是硬编码）。
- **进度度量 = 能力剖面**（各任务 pass_rate / 终局波次 / 经济曲线），**不看 loss**。
- **网络分层 Strategist + Tactician**：慢系统每波输出目标向量 g + 每行资源权重（显式维护"阶段"，
  解决 MPC 无法表示阶段的问题，快系统回合长度被缩短）；快系统在给定 g 下做战术决策。
- **动作改为意图空间 + 确定性执行器**（BUILD_ECONOMY / BUILD_OFFENSE(lane) / FORTIFY / ANSWER_THREAT /
  SHOVEL / WAIT_UNTIL(event)）。执行器只做"意图→合法格子"，不含策略判断；
  `WAIT_UNTIL(event)` 取代 WAIT_TICKS 三档，顺带消除零 tick 退化。
- **值头改 P(win) 分类 + E[剩余波数] 回归**；辅助头用 privileged 信息（wave_timer / next_spawn /
  lane_threat）**只在训练时给、推理时丢弃**（当前代码把 privileged 拿去当 critic 是错用）。
- **奖励 = 二元胜负 + potential-based shaping**（F=γΦ(s')−Φ(s)，Ng et al. 1999），
  理论上不改变最优策略，因此**不需要退火**；当前 `_transition_reward` 的任意常数惩罚不属此类。
- **取消固定教师**，改专家迭代；**规则脚本降级为环境可解性验证器，不进训练数据**（修正上一轮"固化为课程教师"的建议）。
- **归纳偏置 vs 硬编码的判据**：这条规则错了梯度能修正吗？能→归纳偏置；不能→硬编码。
- 阶段门槛（不看 loss）：0 可解性 → 1 短任务 >90% → 2 中任务 >70% → 3 完整关卡 >50% →
  4 held-out 泛化 >50% 且差距 <15pp → 5 对抗性加固。估算阶段 4 需 50–100 核时。
- 最大风险：① 模型推理 2–5ms 成为新瓶颈（需并行批量推理）；② 分层 credit assignment 信号稀疏。

## 内存诊断：WSL 16GB 吃满的根因（提交 b89028f，文档 MEMORY_BUDGET.md）

用户观察到台式机 WSL 吃满 16GB。实测诊断（探针 /tmp/pvz_mem_probe.py，跑在 Mac 上用真实训练路径）：

**实测数字**：
- 一个 observation（Python 对象）= 42.4 KiB，pickle 后仅 4.0 KiB → **Python 对象表示 10.6× 膨胀**
- 一个 privileged_state = 76.9 KiB
- 一个 transition 合计 = **184.6 KiB**；cap1 一局 79 决策（tick 7889 终局）
- 模拟器子进程 RSS = 222 MB（稳定，不增长）
- import torch + 模型 = 224 MB；模型仅 3.68M 参数（14 MB fp32）+ AdamW 28 MB
- 投影：轨迹缓冲 batch=100 → 1.39 GiB；batch=500 → 6.95 GiB；**batch=2000 → 27.8 GiB（爆）**
- 固定开销（8 workers）≈ 3.6–4.4 GB（模拟器 222MB×8 + python/torch ×8）

**结论**：TODO 要求"每次更新 ≥2000 局"，按当前表示需要 27.8 GiB。吃满是必然不是意外。

**三处浪费（按性价比）**：
1. `privileged_value` 只用 privileged_state 的 `hidden["wave_timer"]` + `hidden["zombies_in_wave"][cur][:15]`
   → 16 维数组。**为 16 个 float 存了 77 KiB，浪费 99.7%**。改法：拆出 `privileged_extra()` 纯函数，
   rollout 时算好 16 floats 存 `critic_extra`，删掉 `privileged_state`。**数值完全等价，零风险**。
   −42% 内存，且省掉每 epoch 重新解析 77 KiB dict（ppo_epochs=2 = 两遍）。
2. observation 每 epoch 重新 token 化（`model.step` 首行 `observation_tokens(obs)`）。
   改法：rollout 时 token 化一次存张量（无状态可缓存；output 依赖 hidden 不能缓存）。
3. 训练循环 batch=1 串行：`x.unsqueeze(0)`、hidden 写死 `(gru_layers,1,gru_width)`，
   `for transition in ...: model.step(...)` 逐条。

**顺带推翻自己的一个判断（重要）**：我此前写"更新占 95% → 批量矩阵运算 → RTX 5080 强项 → 迁台式机"。
**错了**。真实原因是 batch=1 串行 + 每 epoch 重做 Python token 化。`resolve_device` 的 docstring
自己都写了 "no such path exists in the training loop"。i7-12700F 单核只有本机一半，
**若 GPU 红利不成立，台式机未必更快**。正确顺序是"先 batch 化，再选机器"。
教训：别把"耗时占比"直接翻译成"计算形态"，要先看代码确认 batch 维到底是多少。

**另注**：WSL2 的 page cache 计入 vmmem 且不主动归还，"吃满"可能是假象——
要看 WSL 内 `free -m` 减 buff/cache，不是 Windows 任务管理器。

**本轮未改代码**（台式机在跑，避免分支分歧），等其结束后按 MEMORY_BUDGET.md 合并。

## 注意力机制移植性分析 + 台式机缺口补齐核验（2026-09-30 上午）

### 用户请求：分析 7 个 LLM 前沿注意力机制能否移植以省内存提速

用户贴的内容带 `:chatgpt-content-reference{index="N"}` 标记（ChatGPT 输出），
我先做了**来源核实**——7 项全部真实存在，数字基本吻合：
CSA2/DeepSeek V4.1 Flash（09-10 发布）、QSA/Qwen3.8-Flash-Next（08-26）、
MSA/MiniMax M3（arXiv 2606.13392，已读摘要）、SGA/A.X K2（arXiv 2608.30181，688B）、
IndexShare/GLM-5.2（06-16）、KDA+Kimi K3（2.78T/104B，47 页报告）、
Gated DeltaNet-2（arXiv 2605.22791，NVIDIA）。Hy4 未找到一手来源。
修正两处：MSA 是 per-GQA-group 选 KV **block**，且论文称与 GQA **同精度**；
CSA2 的"跨层复用"复用的是一个随上下文增长的 KV Cache，PvZ 没有对应物。

### 实测结论（新增 scripts/attention_cost_profile.py 固化全部测量）

- **L 只有 74–116 token**（开局/中局/密集），对比这些机制的 10^5–10^6，差 6 个数量级
- **没有 KV Cache**：每次决策把整条序列从头重算，无可压缩、无可跨层共享
- **attention 只占单层算力 4.2%**，却占 70.5% 的时间 → **时间受限，不是算力受限**
- 每决策 3.002 ms：step_tokens 2.749 ms（91.6%）、observation_tokens 0.165 ms、
  select_action 0.087 ms（仅 2.9%）
- **relation-bias 构造 = 0.266 ms/层 = attention 的 67.1% = 每决策约 35%**
- 该构造**一次派发 117 个算子**（27×as_strided、14×unsqueeze、5×where…），
  算术量微秒级 → **纯调度开销**
- **`torch.compile(dynamic=True)` → 1.83–1.86×，`torch.equal == True`（逐位相同）**，
  投射每决策省 16.0%

**唯一有直接对应物的机制是 GLM-5.2 的 IndexShare**（索引比它索引的东西更贵 → 共享/缓存）：
relation-bias 的索引张量（row_bucket/col_bucket/same_cell/kind_pair 索引）**只依赖
kinds/rows/cols，与层参数无关**，可提到层循环外一次算好，砍掉约 90 次派发。不改模型语义。

不建议做（已记录进文档避免重复讨论）：加稀疏 indexer（L=102 时 indexer 开销 > 省的 4.2%）、
线性注意力（摧毁关系偏置）、KV 压缩（没有 KV Cache）、量化（已实测无收益）、滑窗（L<窗口）。

未完成的测量：相邻决策的 token 变化率（决定"跨决策增量编码"是否可行）——

### 并行化结论

- rollout 已充分（台式机实测 18×1 优于 12×2/16×2，多线程会超订阅）
- **评估是最大浪费**（单线程），是并行化的第一目标
- **评估不该搬 GPU**：batch=1 上 CUDA/MPS 更慢（项目已实测记录 predict 68µs→451µs）
- GPU 在 rollout(1615s) 和评估(1103s) 期间完全空闲

### 用户提示"稀疏=全注意力+掩码"的推论

本模型 CUDA 路径**已经是这个范式**（FlexAttention 的 `score_mod` 注入关系偏置 +
`key_mask` 压 padding）。所以：
- 不需要移植新注意力算法，加稀疏性应在**已有 score_mod 里加一项掩码**
- **CPU 路径缺的正是融合**，`torch.compile` 就是把 eager 的 117 算子链变成融合 kernel
  ——等价于把 FlexAttention 的 score_mod 思想搬到 CPU，正是本次做的事
- `-1e9` 而非 `-inf` 是有意的（padding query 行需有限值，否则反向 NaN），新掩码须遵守
