## 接入方案设计（12:30，待拍板）

核心判断：**教师不碰训练，教师碰尺子。** 教师产出的是"人话结论"，训练要的是
梯度；把结论写成奖励项就是硬编码进主线（红线）。所以接入点是"我们看什么"，
不是"模型学什么"。

三层结构：
- **自动层（零 LLM）**：在 HF 上现成的 update 节点上跑固定一批局 → 用 probe
  打标签 → 画"每个失败模式的出现率 vs 训练进度"曲线。现在退化只能靠"平均种植
  概率"这种全局数字看，看不出**具体哪种行为坏了、从哪个 update 开始坏**。
  再加一层告警（如"0 次种植率 > 50%"）避免整晚白跑。
- **自动层**：挑局。判据三条 —— ① 贪心与采样**分叉**的局（塌陷的直接证据）；
  ② 同任务同种子空操作能过、模型过不去的局；③ probe 命中密度最高的局。
  现在模型塌成 100% 等待时随便抓一局都是"它啥也没干"，教师看完只能说"它不种
  东西"；挑出来的局才带着"它本来该种什么"。
- **判断层（2h / 8M token 一次）**：教师看证据包 → skill + 新 probe。
  **触发条件**要明确：新失败模式出现 / 某 probe 突增 / 胜率掉了但曲线没动
  （最后这类最该叫教师）。

落地顺序：第 0 步拿粗 probe（"整局 0 次种植"）在已有节点 0/4/39/186/328 上跑
曲线，几分钟、零 LLM 成本，直接回答"渐变还是突塌"。有用再往上加。

边界（必须说清）：这套东西**让问题可见，不直接让训练变好**。如果病是优化动力学
塌陷，修它要靠训练侧实验（MC 目标 / entropy / advantage 归一化）。另外 probe
集合是教师从少数几局归纳的，当尺子有"跟着看到的局走"的风险 → 只增不减地版本化、
看趋势不看单点、保留一组手工粗 probe 做对照。

## 奖励结构的决定性发现：塑形项**精确抵消**（19:50，数值验证）

用户判断"奖励做得太差"，并质疑我的"改成植物血量上限"方案。**两条都成立**，
但定性要改：**不是 reward hacking，是"信号饥饿"。**

**一、塑形项在数学上等于 0（我数值验过，不是推理）**

代码（`train_pvz_ppo.py:148-151`）：`shaping = γ^Δ·Φ(s') − Φ(s)`，
Φ = (min(1,阳光/1000) + min(1,波数/总波数) + 植物**平均**血量)/3，`Φ(terminal)=0`，
`Δ = 本步 tick 数 / 300`（`DISCOUNT_REFERENCE_TICKS=300`）。

因为回报也按同一个 per-step discount 累积，**塑形项在回报里逐项相消**：

```
Σ D_i·(disc_i·Φ_{i+1} − Φ_i) = D_N·Φ_N − D_0·Φ_0 = 0 − Φ_0 = −Φ(开局)
```

**实测验证**（`/tmp/pvz-mainline/train_full_level7_v1`，186 步、22,029 tick）：
塑形项总和 = **−0.016667**，理论值 −Φ(开局) = **−0.016667**，**六位小数吻合**。

→ **这个"密集奖励"是一个常数偏移，对所有轨迹完全相同，提供零学习信号。**
→ 所以"它在 reward hacking（攒阳光不花）"**不成立**：没有奖励在给攒钱付钱。
   而且**动作空间里根本没有"收阳光"**（只有 plant/wait/shovel，`probe.py` 词表确认）
   —— 阳光是自动累积的。它唯一的选择是"种/不种"，它一直选"不种"。

**二、真正的学习信号只剩一个终局 ±1，且被长度指数削掉**

`D_N = γ^(总tick/300) = 0.99^(总tick/300)`，实测：

| 局面 | 总 tick | D_N | 赢 vs 输的回报差 |
|---|---|---|---|
| 屋顶 5 波 | 9,127 | 0.737 | **1.473** |
| 无援助 cap10 | 21,725 | 0.483 | 0.966 |
| 完整第 7 关（输） | 22,029 | 0.478 | 0.956 |
| 完整第 7 关（S8 通关那局） | 31,530 | 0.348 | **0.695** |

→ **短关的胜负信号是长关的 2.1 倍。** 而且**局内前期的权重更小**：
第 1 步拿到的终局权重是 0.348，最后一步是 ~1.0 → 策略被告知"后期比开局重要 3 倍"，
对 30 波的关卡恰好是反的。
（优势是**全局归一化**的：`train_pvz_ppo.py:235`，`(A−mean)/std`。所以跨任务尺度被拉平，
但**局内前/后期的相对权重不受归一化影响**。）

**三、最关键的一条推论：从没赢过的任务，梯度是 0**

奖励只有终局 ±1 时，**一个从未赢过的任务上，所有轨迹的终局信号完全相同** →
value function 把 V 拟合成那个常数 → advantage → 0 → **归一化后只剩噪声**。
**"无援助完整关卡通过率 0%" 的直接原因就是这个：它不是学不会，是没有东西可学。**

这同时解释了三件事：短任务学得好（cap1/3/5 信号强）、长任务差（信号被削）、
无援助完整关恒 0%（**信号没有方差**）。也解释了为什么援助任务学得好（它会赢，所以有方差）。

**四、这恰好证明用户的直觉对**：不能"祈祷它在迷宫里撞出出口"——
对从没赢过的任务，PPO **连"该往哪推"都不知道，它没有梯度**。
**教师/课程的作用是"注入方差"，不是"提供知识"。** 一条通关轨迹的价值不是数据量，
而是让一个原本没有方差的终局信号**第一次有了方差**。

**五、不需要写任何"善恶观"的三个修法（全是数学/工程）**
1. **拉长折扣参考**：300 tick → 3,000 tick，完整关的终局权重从 0.35 升到 ~0.90。
2. **`preplanted` 退火课程**（10→8→6→4→2→0）：先让它在有方差的档位上学会，
   再逐步撤脚手架。现成机制，只需改清单。
3. **删掉那个塑形项**：它精确等于常数，删掉不改变任何东西（只省算力），
   但能消除"我们有一个密集奖励"的错觉。

**六、我的"改成植物血量上限"方案是错的（用户指出）**
- 对**墙类/瞬爆类**植物，血量与"有没有尽责"**负相关**：满血坚果 = 它没被需要；
  土豆雷炸掉（血量归零）= 它干完了活。**奖励植物血量 = 奖励"别用你的防御"。**
- 更一般的道理（用户的原话）：**不可能靠一行规则写明"一切操作是好是坏"**。
  所以任何手写 Φ 都是"善恶观"，都会有反例。
- 结论：**方向应该是把奖励退到最接近真实目标处（赢），并保证它不被折扣/抵消削掉**，
  而不是继续手写更聪明的 Φ。

**"没有梯度"这个说法要永久更正**：不是没有梯度，是**梯度指向"别死太快"**。
证据：平均末波 5.22 → 9.49（它一直在往那个方向走）。

## 奖励设计头脑风暴（20:50，用户要求"竭尽全力枚举"）

用户给了三个他想要模型学会的东西，问奖励到底怎么设计：
① "我刚才干的事扭转了战局" ② "豌豆射手种在僵尸面前被啃了，不行"
③ "刚开局用土豆雷解决第一个僵尸、延长经济发育，非常好"。

**关键判断（本轮最重要的产出）：他这三个例子里两个半不是"奖励设计"问题，
是"信用分配"问题。**
- 奖励设计 = "什么算好" → 一行规则写不出来（用户自己已论证）
- 信用分配 = "我哪一步导致了现在的结果" → **不需要写规则，需要工具**
- 把"好"拆两层：**目标层（赢/输）我们定、已经很清楚；过程层（这一步帮没帮上忙）
  不该我们定，应由"比较"和"反事实"测出来。**

**三条拆信用的路（画了图）**：
1. 跟同题其他遍比（组内比较 GRPO/RLOO）
2. 跟"换掉这一步"比（反事实重跑 —— **我们有确定性模拟器 + snapshot/branch，这是稀缺优势**）
3. 跟自己最好的那遍比（自模仿 SIL / AlphaStar UPGO）
**前提**：三条都拆不动"一次都没赢过"的局 → 那种题得先降难度。

**枚举的 30 条方法分七类**（详见对话）：A 信用分配（反事实/RUDDER/事后信用/COMA/
attention-critic/VinePPO 式从中间状态估价）；B 基线比较（组内/空操作基线/PopArt/
UPGO/分位）；C 用数据代规则（SIL/Go-Explore/Backplay/HER 重标注/GoalGAN/
"还剩几波"辅助头/胜负分类器当势函数）；D 改题目不改奖励（**僵尸倍率 0.5→1.0**、
cap 阶梯补 6/7/8/9、开局阳光 1000→50、预种 10→0、自身好局面重启）；E 改结构
（options/宏动作、分层、动作掩码）；F 明确不推荐（好奇心/RND、手写势函数、
BC/DAgger、从规则脚本重启）。

**我排的优先级**：
- "有信号但被淹没" → 组内比较 + 批次开大 + 空操作基线
- "根本没信号" → 降难度。**⚠️ 我一开始想推荐"僵尸倍率从 0.5 起"，查完发现不行**：
  `pvz_env.py:349-351` 硬性要求 `1.0 <= multiplier <= 10.0`（**只能变难不能变简单**），
  现有任务是 1.0/1.5/2.0。`sun_start` 也被 `check_task_manifests.py:173` 钉死在 50。
  **所以今天不改代码能用的难度旋钮只有两个：`wave_cap` 和 `preplanted`。**
- "信号太晚、分不到开局那步" → 反事实重跑 / 自模仿 / 从中间状态估价
- **诚实结论：靠调折扣修不好**——γ<1 会制造"别死太快"的假梯度，γ=1 又完全没有信用分配。
  所以别在折扣上做文章，要换"谁来提供梯度"。

**难度阶梯的具体缺口（查证）**：训练池 13 个任务里草地无预种只有 cap10 / cap15 / 全开。
cap5 的空操作基线是 7/8（几乎白送，无信息），cap10 是 0.5。
**信息量最大的区间恰好在 cap6~cap9，而这四档一个都没有。**

**重要区分（防止再被误读）**："这株豌豆活了 620 tick 就被啃了"是**环境报的事实**，
不是我们写的价值观——和"血量高就是好"完全不同。

### LLM 教师怎么教套路（回答用户的问题：能，而且这是它最该干的活）

**关键是把"教师产出"分两种**：
- ❌ 教师写**轨迹**（每局怎么打）→ 违反现行约束、慢、且是"教动作"
- ✅ 教师写**知识**：套路 / 检查表 / 里程碑 → **不违反**，而且正好补上纯 RL 学不动的那层

**最有用的形式：让教师产出"可被程序检查的谓词"。** 教师那句话可直接翻译：

| 教师原话 | 变成可检查的东西 |
|---|---|
| 开局先种向日葵 | 第 10 个决定时 向日葵数 ≥ 2 |
| 第一只僵尸靠土豆雷 | 第一只僵尸死时 凶手是土豆雷 |
| 经济起来再种豌豆 | 向日葵数 ≥ 5 之前 射手数 = 0 |
| 优先覆盖所有行 | 有射手的行数 = 5（而不是某行有 5 个） |
| 除非某行威胁超出防线 | 某行僵尸血量和 > 该行火力×可用时间 时触发例外 |

**这些不是轨迹，是"局面该长什么样"，程序可以逐条检查。** 三种用法：
① 诊断（量出模型在第几步偏离好玩家，比"它没赢"具体一万倍）；
② **里程碑奖励（成就系统）——达成时给一次分，而不是每一步打分**；
③ 课程起点（用"好玩家走到第 k 步的局面"当训练起点）。

**铁律**：每个里程碑都必须能被数据验证"达成它是否真的更容易赢"，没预测力的删掉。
这样它就不是"硬塞的善恶观"，而是"被数据认证过的中间目标"。

**⚠️ 需要用户拍板的边界**："用教师描述的好局面当训练起点"算不算违反
"教师轨迹不进训练数据"？我倾向不算（那是**状态**不是**轨迹**，且从知识生成而非从操作录下）。
若这个口子开了，"脚本打出的好局面当起点"也顺理成章——而那条可能是最快的路。

## 「脚本示范 vs LLM 示范」之争（21:14，用户邀请我反驳）

用户："几千局 LLM 数据和几千局脚本可不一样啊，脚本是死的，我实在怀疑它能否真正教给模型
策略性，而 LLM 能随机应变，真正理解战场。当然这个你可以反驳"

### 我的判定：一半同意，一半反驳

**同意的**：脚本确实是死的，而且比用户想的更严重。
它的规则带**硬上限**（生产者 <10、射手 <14、土豆雷 <4）——**到顶之后它就不动了**，
只能攒钱（实测平均剩 **864.6** 阳光）。所以**脚本能教会"怎么做"，教不会"什么时候该破例"。**

**反驳的核心**：**"随机应变"恰恰是不能靠示范教会的。**
让一个会应变的老师做示范，学生学到的是**老师那一次的具体应变**，不是"应变能力"。
**应变能力 = 好的价值判断 + 敢试，来自"能预测后果"，不来自"看别人应变"。**
→ 所以 LLM 的价值不在"示范应变"，在"**说出判断**"。

### 关键区分（本轮产出）：行为 vs 判断

| 从谁身上 | 提取什么 | 得到什么 | 补的是哪个缺口 |
|---|---|---|---|
| **脚本** | **行为**（该做什么） | 一个"会建防线"的起点（38% vs 我们 0%） | 现在的**起点是 0** |
| **LLM** | **判断**（这个局面好不好、为什么） | **一个价值函数** | 正是我们诊断出的缺口（λ=1 扔掉了价值函数）|

**两者不冲突，是两步。** 而且第二步正好对准"长远把握"那个缺口。

### 一个反直觉的成本账（重要）

**LLM 做"判断"比做"操作"便宜约 190 倍**：打一局 = 190 个决策 × 每轮几分钟 = 几小时；

### 模型以什么形式学 —— 推荐方案

**"这一步该扣多少分"——而分数不用我们定，是实测出来的。**

模型现在的处境：一局打完只知道"输了"，**不知道输在哪一步**。教师补的正是这个。
模型学到的形式：

> **在"这种局面"下，动作 A 的实测价值比动作 B 低 X。**

**X 不需要设计——它就是教师实测出来的结果差**（例：`第 5/5 波 (+2 波)`）。

**落地**：只在教师验证过的那一小撮步骤上，把 B 的概率往上推、A 往下压，**推力 = 实测差**；
其余步骤完全不变。

**为什么这不是"改奖励"**：奖励加在每一步、大小由我们定；
这个是**只加在教师验证过的具体步骤上、大小由实测决定**。
前者是"装善恶观"，后者是"告诉它这一步实测错了"。

**备选一：稀有成功样本（SIL/UPGO 式）** —— 把"改这一步就赢"的那整局当成功样本加大权重。
不碰奖励，但那一局只有 1 步是教师改的，其余 190 步是策略自己走的。
**备选二：训练起点** —— 最安全，但只能解决"开局就错"。

## 外部求助回复：逐条核完，质量很高（22:11）

### 它最有价值的一条：**Q 依赖"之后由谁接着打"（μ）**

`Q^μ(x,a) = Pr(赢 | 从 x 做 a，之后按 μ 走)`，信用 = `Q^μ(x,a) − Q^μ(x,b)`。
**关键洞察：两个动作必须配合才能赢时，只替换其中一个，完全可能始终得到零收益。**
→ **这直接解释了 S8 的"改任何单步都无效"** —— 可能不是"策略塌陷"，是
**用塌陷的策略当续跑者，任何单步都测不出价值**。
**修法（它给的）**：续跑用"当前策略的随机采样 + 在该任务上已验证能赢的脚本"混合，两边同比例同预算。
先例 LOLS (Chang 2015)。
两边都还全输 → 保留为"尚无法区分"，不能声称相等或无解。

**⚠️ 它顺带指出了一个致命细节，我们没注意**：
**确定性模拟器 + 确定性策略 + 重复 = 同一份证据（只有 1 个样本）。**
我们的 `episode_query` 反事实路径**默认 `deterministic=True`**（`_run_variant` 第 71/750/815/864 行）。
**→ 不改成采样，整套"多次续跑估 Q"的方案根本跑不动。**（有 `--sampled` 开关，第 1166 行。）

## 🔴 排查结论：**这一轮作废，根因是我的交接书**（10-06 00:0x）

**SSH 连过去读了 `~/PvZ-Portable/artifacts/research/bc_finetune_level7_v1/` 的落盘。**

### 事实 1：三次更新，每局都被砍

```
update 1: counters={episodes:64, decisions:10000}  won=0  truncated=64
update 2: counters={episodes:128,decisions:25000}  won=0  truncated=64
update 3: counters={episodes:192,decisions:50000}  won=0  truncated=64
```

**→ 192 局，零个终局。** 终局 ±1 从来没响过 → **RL 根本没有信号可学**。

### 事实 2：主线不是这样

主线 250k 的 328 次更新：**`truncated` 中位 0、`won` 中位 1**（范围 0~2 / 0~4），
**只有 5/328 次是全截断**。→ **主线的局正常跑到终局。**

### 事实 3：根因 —— `exact_decisions_v1` 的**决策配额**

`pvz_research.py:690-694` 记录 `decision_budget`：`boundary_mode: exact_decisions_v1` 会给
**每一局分配一个决策配额 = 剩余预算 ÷ 在飞局数**，配额用完就截断。

| | 每批局数 | 配额/局 | 一局需要 | 结果 |
|---|---|---|---|---|
| **主线** | 4 | **中位 4,000**（上限 `max_actions`） | ~190 | ✅ 正常跑完 |
| **这次** | **64** | **157 / 235 / 391** | **~986** | ❌ **每局被砍在 16~40%** |

**→ 配额 = 节点间隔 ÷ 每批局数。** 64 局 × 1,000 决策 = 一次 rollout 就要 64,000 决策，
而节点间隔只有 10,000 → 配额 157。

### 事实 4：**这是我的错**

交接书 #4 的 4.3 节**同时**要求了：
- `sampling.rollout_episodes: 64`
- `evaluation.decision_nodes: [0, 10000, 25000, 50000]`

**这两个参数一起用就是致命的**：批次开大 16 倍，但节点间隔没跟着放大，
配额就被摊薄到一局都跑不完。**我只想着"批次开大几乎免费"（PPO 时间），
忘了 rollout 的决策数会按局数线性增长。**

### 事实 5：所以那条曲线**不能解读**

- 采样 80.47→75.39（p=0.20，不显著）
- 贪心 82.03→**64.45**（p<0.0001，显著）

**但没有奖励信号，这个漂移不是"RL 有害"的证据。** 而且有一个能解释它形状的机制：
**没有奖励信号时，`entropy_coefficient: 0.01` 会把策略推向更分散** →
**贪心塌陷、采样基本不动** —— 正好是观察到的形状。

### 🔑 修法（一条规则，写进下一份交接书）

> **节点间隔 ÷ 每批局数 ≥ 一局长度的 3 倍。**

一局约 1,000 决策 → 配额要 ≥ 3,000：
- `rollout_episodes: 4` → 节点间隔 ≥ 12,000
- `rollout_episodes: 16` → 节点间隔 ≥ 48,000
- `rollout_episodes: 64` → 节点间隔 ≥ **192,000**（即预算要 60 万以上才够几个节点）

**并且在开跑前加一道自检**：第一局跑完后立刻打印"这一批的实际决策数 / 局数"，
和"一局完整对局需要多少决策"对比。**不满足就先停下。**

### 批次大小的最终定论（用户问"改成 4 会不会明显差"）

**我在这个问题上前后说了三个版本**（"几乎免费" → "改回 4" → "16"），最后定 16。理由：

1. **4 在这里不像在主线那么差**：主线是 **13 个任务共用 4 局**（每任务 0~1 局），
   **而这次只有 1 个任务** → **跨任务方差这个主线最大的噪声源根本不存在**。
   而且主线就是用 4 局从 0% 学到 41.2% 的。
2. **但这个实验最怕的结果是"RL 什么都没干"**——那个结果最模糊（分不清"信号弱"还是"估计吵"）。
   **批次开大能让那个结果更有解释力**，所以用"负担得起的最大批次"，不是最小批次。
3. **代价**：rollout 时间按局数线性涨（4 局≈12s → 16 局≈50s）。

**配额的正确算法（这次修正的）**：配额 = 剩余预算 ÷ 在飞局数，**在一段节点内递减**。

| 每批局数 | 一次 rollout | 节点间隔 | 节点内第 1 次配额 | 最后一次配额 | 结果 |
|---|---|---|---|---|---|
| 4 | 3,944 | 50,000 | 12,500 ✅ | 668 ❌ | 每节点末尾截断 4 局 |
| **16（定案）** | 15,776 | **100,000** | **6,250 ✅** | 334 ❌ | 每节点末尾截断 16 局（14%）|
| 64（上次） | 63,104 | 10,000 | **157 ❌** | — | **全截断** |

**判据**：只要节点内前几次 rollout 的配额 > 一局长度（986），局就能跑完；
**只有每个节点最后那一次会截断**——这是边界机制的固有代价，主线也一样（5/328 次有截断）。

**交接书 #5 已改成**：`rollout_episodes: 16`、节点每 100,000、预算 1,000,000（10 个节点）；
自检改成"**先只跑前几个更新**，检查 `won` 占多数且 `budget_boundary_truncations` 明显小于批大小"。

## 🔑🔑 找到 codex 反复被杀的根因：**WSL 会在空闲时自动关机**（10-06 21:48）

### 症状

codex 连续三次启动后 1~3 分钟静默退出，**日志里没有任何 error**，也没有 EXIT 标记
（说明是被杀的，不是正常退出）。tmux 会话的 socket 也会消失。

### 根因

`uptime` 每次都显示 **`up 0 min`** —— **整个 WSL 虚拟机重启了**。
**WSL 2 在没有 `wsl.exe` 客户端连接后（约 60 秒）会自动关掉整个 VM**，
把里面所有进程一起杀掉。我的 SSH 命令一结束，客户端就断了。

**→ 这解释了之前所有"run 中途没了"的现象**（包括上一个 Agent 的 v2 停在 node 0）。
**不是磁盘、不是 OOM、不是代码问题。**

### 修法（**已验证有效**）

**在 Windows 侧挂一个常驻 `wsl.exe` 把虚拟机顶住。** 关键是**必须真正脱离 SSH 会话**：

```powershell
# ✗ Start-Process 不行 —— 从 SSH 会话里起的进程会随会话一起死
# ✓ 用计划任务（跑在 Task Scheduler 服务下，真正脱离）
schtasks /create /tn "PvZWSLKeeper" /tr "wsl.exe -d Ubuntu -e sleep 2147483647" /sc once /st 00:00 /f
schtasks /run /tn "PvZWSLKeeper"
```

**验证（等 4 分钟不连）**：`uptime` 显示 **`up 5 min`**（以前恒为 `0 min`）、
tmux 会话在、codex 进程在、keeper 在、日志从 298 行长到 3612 行 ✅

### 顺带记下的环境事实

- `~/.wslconfig`：`[wsl2] memory=24GB swap=8GB localhostForwarding=true`；
  **`[experimental] sparseVhd=true, networkingMode=Mirrored`**
- WSL 里 **`tmux` 和 `screen` 都装了**；**`systemd=true`**（PID 1 是 systemd）
