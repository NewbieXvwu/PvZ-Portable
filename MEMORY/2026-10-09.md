## ★ 决定性结论：学习慢的直接原因是 **KL 信任域把 90.5% 的更新截断**

### 先纠正问题的性质：**v3 达成了它自己的目的**

配置里的 `purpose` 原话：
> "Verify the terminal-outcome discount hypothesis using the GRU sequence d1 behavior-cloning
> checkpoint; **keep the v1 task distribution and PPO recipe unchanged**, with the same
> 16-episode rollouts and 1M-decision budget."

→ **"只改终局折扣，其他一律不动"**。所以"只涨 6 个点"**是设计，不是失败**——
这轮的目的就是验证病根，不是调参提分。

**对照组 `idle_control` = 0/256 = 0.00%**（什么都不做，完整第 7 关全输）
→ **86.7%→92.6% 全部是学出来的，这道题没有白送的分。**

### 机制（读代码 + 实测，`train_pvz_ppo.py:325-410`）

```python
approximate_kl = float(((ratio - 1) - log_ratio).mean().detach().item())
kls.append(approximate_kl)
if target_kl is not None and approximate_kl > target_kl:
    stop_for_kl = True
    break                      # ← 在 optimizer.step() 之前 break，整次更新终止
```

**KL 检查在梯度步之前；一旦均值超阈值就 `break`，后面的 minibatch 全扔。**

| 指标 | 实测 |
|---|---|
| `stopped_for_kl` 为 True | **90.5%（76/84）** |
| `optimizer_steps` | 中位 **21**、最小 **2**、最大 130 |
| 未触发 KL 的更新 | 只有 `[0,5,7,10,15,33,41,67]` |
| `approx_kl` | 中位 **0.00408**、最大 0.058（`target_kl=0.03`） |
| `max_log_prob_change` | 中位 **6.15 nat**、最大 **56.5**、>5 的占 **61/84** |
| `first_minibatch_log_prob_max_error` | 最大 **3.1e-5** → **回放一致，不是 bug** |

**因果链**：BC 给的策略极尖锐（熵 0.0036–0.014，54 个动作全随机应是 ln54≈3.99）
→ 尖锐策略上少数决策的单步 log-prob 跳 **6–56 nat**
→ 把 **均值** KL 顶过 0.03 → 整次更新被 `break`
→ **平均只走 21 步梯度**。**这就是 100 万决策只换来 6 个点的直接原因。**

**另一个观察：`optimizer_steps` 越训越少**（前 10 次中位 **75** → 后 10 次中位 **25**）。
**原因未查明**（熵反而在升 0.0036→0.0139，所以不是"变尖锐"）。
相关性仅供参考：`steps vs won = +0.365`（可能是反向因果：赢得多的批次优势小、动得少、步数多）。

**`entropy_coefficient=0.01` × 熵 0.014 = 0.00014 → 这个"鼓励探索"的旋钮等于没开。**

### 修复方向（按外科程度）

1. **改 KL 判据**（最外科）：现在是"整批**均值**超阈值就全停"，
   而均值是被**少数跳变决策**顶上去的 → 改成**逐决策裁剪**或**分位数**判据。
2. **降 lr**：1e-4 在尖锐策略上单步就超 KL。
3. **给熵真正的权重**：现在 0.01 配 0.014 等于没有。
4. **`target_kl=0.03` 本身不算严**（OpenAI 惯例 0.015）——**问题不在阈值大小，在判据形式。**

### ❌ 更正：**"130 是允许的额度"是我编的**（用户追问后查出）

我上一条说"规则允许它每节课改 130 处"——**错。130 只是 update 0 的实测值，不是额度。**

真实额度是**按当次采了多少数据算的**（`train_pvz_ppo.py` 主循环）：
每局按 `sequence_length=128` 切块 → 同一位置的块组成一个 `layer` →
每步取 `minibatch_chunks=2` 个块 → 跑 `ppo_epochs=2` 轮。
→ **额度 = 2 × ceil(块数 / 2)，随数据量浮动。**

| 指标 | 实测（84 次更新）|
|---|---|
| 步数额度 | 中位 **108**，范围 2–124（**不是固定值**）|
| 实际步数 | 中位 **21** |
| **实际 / 额度** | 中位 **22.8%** |
| 用完额度的更新 | 只有 **11/84** |
| 每更新决策数 | 中位 13,724 |

→ **正确说法：它平均只用了额度的 23%，77% 的学习预算被扔掉。**

**安全阀本身是正当的**（PPO 信任域：数据是旧策略采的，改太远数据就失效）。
`target_kl=0.03` 是**惯例值不是推导值**（OpenAI 常用 0.015，0.03 算宽松）。

## ★ 翻案：**"策略太尖锐导致 KL 爆炸"讲反了**（10-09 17:00）

我先前说"BC 策略太尖锐 → 少数决策跳 6 nat → KL 顶破线"。**方向是反的。**

**正确的机制**（`/tmp/decline.py` 实测 84 次更新的相关与前后对比）：

| 变量 | 前 10 次中位 | 后 10 次中位 | 变化 |
|---|---|---|---|
| `optimizer_steps` | 75 | 25 | **0.33×** |
| **`approx_kl`** | 0.00108 | 0.00669 | **6.19×** |
| **`clip_fraction`** | 0.00144 | 0.00773 | **5.38×** |
| **`entropy`** | 0.0033 | 0.0137 | **4.15×** |
| `advantage_std` | 0.415 | 0.417 | 1.00× |
| `max_log_prob_change` | 6.91 | 6.42 | 0.93× |
| 决策数 | 14,650 | 13,620 | 0.93× |

`steps` 的相关系数：`clip` −0.346、`kl` −0.333、`vloss` −0.311、`won` +0.365、`dec` +0.319。

**→ 机制链（自洽）**：
1. 训练中策略**变软**（熵 0.0033 → 0.0137，涨 4 倍）
2. **越软的策略 Fisher 信息越大** → 同样一步梯度引起的 KL **更大**
   （极尖锐时 `p(1−p)≈0`，Fisher 很小 → 每步 KL 很小；变软后每步 KL 变大）
3. → KL 累积到 0.03 所需步数从 **75 掉到 25**
4. → **每次更新能学到的越来越少，正好和期望相反**

**⚠️ 而且阀门不是被"单个离群点"顶破的**——是**稳定累积**（0.03 ÷ 25 步 ≈ 每步 0.0012），
这跟"离群点假说"完全相反。**之前那个假说作废。**

### 炸弹 1：**`rollout_episodes=16`，而 CLI 默认值是 2000——差 125 倍**

这**一次**解释了之前所有对不上的现象：
- PPO 每 transition 64 ms vs 基准 0.75 ms（**85 倍**）→ 小批次固定开销

- 梯度噪声大

## HF 上传：codex 查错了，token 一直在
