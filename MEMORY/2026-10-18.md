### 第 11 轮：`GrowRoots` 换地址后没人刷新 `Arguments` 里抄走的指针（UB，已修 + 加了运行时不变量）

- 症状：`PHASE=1` 批量门跑 z15 语料（425 真根），10/30 道正常、100 道 `illegal memory access`；
  二分 → 第 35 根对多数种子都崩。`compute-sanitizer` + `-lineinfo` 指到 `SimTick.inc:895`
  `waves.zombieCount[wave]`，越界地址正好是 roots 缓冲末尾（425×17652 B）。
  同一根同一未来在 ASan 主机参考上完全正常 ⇒ 不是共享核心的状态 bug。
- 根因：`DeviceOpen` 把 `dev.roots/dev.waves`（当时 256 条）抄进 `dev.arguments`，
  而 `GrowRoots/GrowPairs` 是 `cudaFree + cudaMalloc`，**会换地址**。批量门随后
  `GrowRoots(dev, 425)`，服务端每波也可能长：主机往新缓冲 memcpy，内核读旧映射。
  判据"≤256 根的语料永不扩容"解释了为什么 z13（144 根）的阶段 1 早期对照一直没露馅；
  而 `corpus_phase1`（276 根）、`corpus_l7_z15`/`z15_skip0`（各 425 根）都过了线 ⇒
  **阶段 0 的 15,770 rollouts/s 与阶段 1 逐项对照都需在修后二进制上重测**。
- 修法不只刷新指针：`RunBatch` 顶部加了"捕获指针必须等于当前 `dev.*`，否则 `Fail`"的运行时检查，
  因为这类 bug 是否发作取决于分配器是否把旧地址原样还回来（修前 round8 二进制与修后**逐字节相同**、
  也不崩 = 运气）。用一个注释掉刷新的 `sabotage` 构建验证过：检查会立刻 `rc=1` 报出原因。
- 回归测试：`python/test_cuda_serve_merge.py::RootArrayGrowthTest` 把 425 根语料截成 256 根前缀
  （不扩容，指针必然有效）与全量（扩容）各跑同一批 (root, future)，断言 33-int 记录与
  5668-float 叶子**逐字节相同**，并断言非空（4 个根结果互不相同、errorFlag 为 0、ticks>0）。
- 教训：**设备侧数组一旦可能重分配，就必须要么在重分配处刷新所有持有者，要么根本不复制指针**。
  这个仓库里有两份这种"抄过去的指针"（`dev.arguments` 与 `Device` 本身），后者是对的，前者靠运气。
  任何"看起来是对的"的 GPU 数字，若它依赖分配器行为，就应当在代码里写成断言而不是靠测试碰运气。

### 第 12 轮：门槛在修后二进制上重测过线；"块大小对本机无效"是只在峰值上测出来的错话

**测量**：GPU 空闲窗口重测阶段 0 —— 27,200 道 15,518 条/秒 = 门槛的 **1.72×**（4 次 1.70/1.71/1.72/1.72），
`--bench sim` 6.21×。修后二进制把 per-lane 代价曲线补全了：**临界点 ~80–100 道**，10 道 34.1 ms/条
（比一个 CPU 线程慢 3 倍）、1000 道 1.22 ms（9×）、3000 道 0.45 ms（24×）。

**改**：`RunBatch` 按本波道数选块（≥128 道 64 线程，否则 256；`--block` 默认改成 0=自动）。
根因是 profile 里的反常：`heads+apply` 在 1000 道要 14.7 ms/回合、27,200 道只要 9.2 ms ——
同样的活、线程少 27 倍反而更快 ⇒ 小波是 **SM 饥饿**（`grid=lanes/block`，248 寄存器/线程让一个
256 线程块正好占满一个 SM 的寄存器堆，1000 道只发 4 个块、80 个 SM 闲着）。
**收益**：256/512/8192 道 +38%/+40%/+41%，1000–3000 道 +21~28%，<128 道 ≈0，峰值门槛批 −2%（噪声内）。

**教训（两条，都值得记住）**：
1. **一次"某旋钮无效"的结论，必须说清它在哪个参数区间被测。** 第 3、9 轮都写过"块大小 ±0.4% 无效"，
   那是**只在 27,200 道峰值**测的；服务路径真正工作的 150–8192 道区间里它值 21–41%。
   门槛用的大批和线上用的中批不是同一个受限机制，拿一个区间的结论否定整个旋钮是错的。
2. **验等要量，不要推。** 改动的不变性是这样证明的：改前/改后二进制各跑 `--out --leaf-out`，
   100 道（宽块）与 1000 道（窄块）**记录与叶子 SHA 逐字节相同**。顺带又清掉一条注释里的假话
   （"服务器按请求在批式/每道前向之间选交叉点"）——实测 `--bench lane` 只有 1–8 条/秒、
   交叉点不存在，且服务路径从来没选过它（grep 只有 bench 分派一处）。
   **注释里"代码会按 X 做 Y"这种断言，要么当场 grep 证实要么别写**；它这次多骗了我一轮。

**待主控定**：≤4 worker 的 CPU 纪律与"有意义的 DAgger 墙钟收益"直接冲突（波 <100 道时 GPU 打不过
一个 CPU 线程，收益≈0）。已写进 `~/pvz-logs/qoder_questions.md`，先按选项 B 推进：报 ≤4 纪律下的真实
改前/改后 + 8/16 worker 对照，说明瓶颈是并发上限而非接缝。
