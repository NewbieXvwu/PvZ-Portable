## §10.8 两项"未做"的结论（提交 `68d34f8`，已推送 `pvz-env`）

### P2 跨决策增量编码：**已测，否掉**（`scripts/token_delta_probe.py`）
前提成立（token 块确实稳定），但结论反过来：

| 字段 | dtype | 形状变化 | 元素变化率 |
|---|---|---|---|
| ids | int8 | 125/459 | 0.1% |
| features | float16 | 125/459 | 0.3% |
| cell_index | uint16 | 0/459 | 0.0% |
| packet_ids | uint8 | 0/459 | 0.0% |
| packet_index | uint16 | 0/459 | 27.2% |

压缩比：原样 5371 B (1.00×) / 增量 1770 B (**3.04×**) / **单块 zlib 632 B (8.50×)**。
598.0 MiB → 191.7 vs **70.4 MiB**。

**为什么低变化率也没用**：变化粒度是"行"不是"元素"。逐元素只变 0.1–0.3%，
但 32.1% 的 token *行* 变了，变一行要付整行 69 B + 2 B 索引。
逐元素稀疏编码要变 94% 以上才追平 zlib。

**更根本的**：内存不是瓶颈。父进程 770 MiB vs 18 worker 进程树 RSS 峰值
**19,168 MB**（`T5_PERFORMANCE_REPORT.md`），更新 184 s 是 GPU 计算受限。

### shard 写入：**建议保留**
去掉只省 0.4%/update（0.8 s / 184 s）+ 1.8 GB/run 磁盘，代价是丢掉断点续跑。
重采一个 update 的 rollout 只要 11–17 s，所以"崩溃损失"确实小；
但在**一台已证明会掉 GPU 的机器上**，0.8 s 换断点续跑划算；
且 `run_seed_jobs` 被 4 个入口共用（T5 trainer / t5_worker_batch_benchmark /
benchmark_pvz_agent / train_pvz_agent），改语义要加参数分支。
若用户认为磁盘更重要 → 改成显式 `persist=False` 开关。

顺带否掉"改成不压缩换 0.45 s"：磁盘会从 178 → 814 MiB/update（8 个 run 从 1.8 → 8.1 GB）。

### 教训
- **"变化率低"不等于"增量编码划算"** —— 必须看变化的*粒度*。我原来的预期是反的，
  测了才知道。
- 顺带确认：`forward_sequences` 确实直接读 `transition["tokens"]["ids"]/["features"]`
  （`pvz_agent_model.py:821`），所以"内存里 zlib、前向时解压"技术上可行，
  但会改变 `episode_digest` 的输入形态，而摘要必须在 T5 出结果前定死 —— 不值。

- `legal_actions` 5,309 B (43.6%) / `cells` 4,375 B (36.0%) —— 两者 79.6%，**都有读取者**
- **未读字段合计只有 127 B = 1.0%**（`grid` 121 B + `coins` 2 + 3 个版本号 + `playthrough`）
- 所以**"传了没用的字段"是错觉**

但**形式极贵**（这才是真问题）：
- `legal_actions.plants` 90 条 `{"packet":0,"col":0,"row":0}` = 2,611 B，
  **78% 是键名**；列式 `{"packet":[...],"col":[...],"row":[...]}` 只要 **568 B (21.8%)**
- `cells` 54 格**全空**仍花 4,375 B，每格 80 B 承载 6 个小整数（键名 55 字符），
  `row`/`col` 还是数组下标；稀疏编码约 400 B
- `loadout_context` 230 + `player_profile` 208 + `defenses` 231 = **669 B 每步重传不变数据**
- **合计可省 ~6,800 B = 观测的 ~56%**

### 二、但协议瘦身不是性能收益（关键）

每 decision 往返实测（120 次）：`env.step` 0.108 ms + `critic_inputs` 0.012 ms。
`json.loads` 0.037 ms = **decision 的 31%**（载荷大时 43%），是 `env.step` 里最大单项。

但每局分解（`worker_single_core_current.json`，单 worker 单线程 CPU，0.5128 s/局）：
`model` **85.3%** / `environment` 10.3% / `tokenization` 3.5% / `persistence` 2.5% / `critic_inputs` 0.75%。
**观测砍一半只省每局 ~2%。真正的墙是 `model`。** GPU 上才会反转，届时重测。

### 三、`CRITIC_INPUTS` 有一半是纯冗余（已证实，不是推测）

```
critic_inputs['wave_timer'] == observation['wave_timer']:  120/120 decisions
```
`CRITIC_INPUTS`（`src/main.cpp:534`）返回的 `wave_timer` 就是
`mZombieCountDown`，而公开观测（`src/LawnApp.cpp:1524`）**已经带了同一个数**。
更荒唐的是 `pvz_agent_model.py:190` 用 `observation["wave_timer"]/6000` 喂 actor，
`:950` 用 `critic_inputs["wave_timer"]/6000` 喂 critic —— **同一个数取两次、
算两遍、喂两个头**。`CRITIC_INPUTS` 唯一不可替代的只有 `wave_zombies`。
这是**唯一一项"改了就直接省时间"**（9.6% decision）且不需要动 `OBSERVATION_VERSION` 的改动。

### 四、`PRIV` 是协议里最大的一块死重

57,907 B 中 `hidden.reanimations` **39,737 B (68.6%)** + `rand_state_hex` 5,002 B。
`debug_replay` 默认 `False`（`pvz_env.py:178`），**训练路径一次都不发 PRIV**；
只有 `verify_env_equivalence.py` 和 4 个基准脚本在用。实测 0.229 ms/次。
不能删（是等价性证据的基础），但应拆成 `PRIV_CORE` / `PRIV_ANIM`。

### 五、"存了没用的" —— 这次是真的

- `training_state.json` **每 update 全量重写 ~102 KiB**，其中
  **70.3 KiB (69%) 是 `last_update.losses.rollout_episode_hashes`**（2,000 个
  32-hex digest），而 `checkpoint.provenance.trajectory_sha256` **已存同一批**。
  `atomic_json(indent=2)` 未压缩。时间成本可忽略，**信噪比很差**。
- **仓库里既没有 `training_state.json` 也没有 `learning_curve.json`** ——
  训练从未跑完（GPU 掉线），这些格式**从未被真实数据检验**。

### 六、"算了就扔"的两类数据（这才是该存的）

1. **`profile_seconds`**：`collect_task_episode`（`train_pvz_ppo.py:202`）**每局**
   都返回 `{model, environment, critic_inputs, tokenization}` 四个耗时，
   而 T5 训练器**从不聚合**。只有 `t5_throughput.py` /
   `t5_worker_batch_benchmark.py` / `training_hotspot_profile.py` 三个离线脚本在用。
   **每局都量了体温，然后把体温计扔了。**
2. **`env.episode`**：`pvz_env.py:711` 每个 decision 都往 `self.episode` 追加

   `collect_episode` 和 `train_pvz_agent.py`/`benchmark_pvz_agent.py` 会存）。
   **每局都在累积完整回放，然后被垃圾回收。**

### 七、"跑的时候只能死等" —— 完全正确

### 最重要的数字：91.2% 的 token 每个决策逐字节不变

| kind | 不变占比 |
|---|---|
| `cell` (54.0, 68% 序列) | **100.0%** |
| `defense` (5.3) | **100.0%** |
| `zombie_roster` (1.6) | **100.0%** |
| `profile` (1.0) | **100.0%** |
| `grid_item` (1.3) | 96.8% |

| **`global` (1.0)** | **0.0%** |
| **合计** | **91.2%** |

**只有 `global` 每步全变。** 而 **97.7% 的 cell token（10,395/10,638）
既没有植物也没有物品** —— 全部信息是 `(row, col, terrain, row_type)`，`reset`
时就固定了。

### 但 padding 不是速度问题

feature 向量 **76.0% 是填充**（`zombie_roster` 只填 **1/32**、`defense`/`lane`
填 4/32）。但 `FlopCounterMode` 实测 **`feature_projection` 只占一次前向的
0.9%**。填充是清晰度问题。

FLOPs 分解（75 token，1.234 GFLOP/决策）：FF(gate/value/down) **21.6%**、
attention **15.7%**、feature_projection 0.9%、GRU 0.1%。
**FF 线性于 token 数、attention 平方于 token 数 → 杠杆是 token 数，不是宽度。**
模型 3,682,505 参数（14.05 MiB fp32）。

### 同一信息多通道 + 不进 token 的字段

多通道：`cell.terrain`（category + feature[2]）、`cell.row_type`（variant +
feature[3]）、`cell/plant/zombie.row/col`（row/col embedding + feature[0..1]）、
`projectile.motion`（variant + feature[8]）、`seed_packet.index`（feature[0] +
metadata）。**`zombie_roster` 的 feature 向量字面量是 `(1.0, 0, 0, ...)`**，
全部信息在 category。

不进 token：`legal_actions`、`level`、`terrain`、`enemy_zombies_on_screen`、
`coins`、`grid`。`level` 缺失是有意的（场景类型已由 `night`/`pool`/`fog`/`roof`
和 `cells[].terrain` 表达）。

### 诚实边界（写进了文档和提交信息）

**token 输入不变 ≠ 表示不变。** attention 是全局的，其他 token 变了这个 token
的输出也变；`cell_keys` 是选格子的打分依据（`cell_ids = range(54)`），
**必须每步重算**。所以这不是"可以跳过"，而是"可以用不同方式表示"。
把 54 个 cell token 换成位置编码 + 稀疏非空格子能把序列从 79 降到 ~25，
**但那是架构改动，会改变模型语义，需单独验证学习能力，不与 A 档混做**。

### 判断：这是"为什么学不会"的候选假设，比性能更有价值

阶段 0 还没跑通（GPU 掉线），模型学习能力未验证。**在不知道能不能学会的
情况下重构输入表示是过早优化。** 但反过来：如果注意力被 68% 的静态 cell token
淹没，这本身就是解释"零信号"的一个候选假设 —— 值得在 T5-A 诊断时一起看。

### 教训
- **按 (kind, slot) 聚合检测"常数"有方法缺陷**：`cell` 的 54 个格子混在一起，
  `_ratio(row,5)` 当然不恒定。正确做法是**逐 index 比较相邻决策的 token**
  （token 顺序确定 → 同一 index 通常指同一实体）。
- `FlopCounterMode` 的 `get_flop_counts()` 返回 `{module: {op: count}}`，
  没有 `["Global"]` 键（我第一版写错了）；按模块名前缀归并即可。

  维度 pad，GRU 走 `pack_padded_sequence`。**批维度已经是紧的，不需要序列打包。**

### 每局成本分布（`worker_batch_sweep_2000.json`，18 worker、2,000 局、161.6 s）

**model 88.9% / environment 7.1% / tokenization 3.3% / critic_inputs 0.4%**。

→ **rollout 是模型受限的**，不是环境受限。每局 49.2 决策 → 18 ms/决策（batch=1）。
→ **整个观测载荷只值每局的 10.4%**，所以 B2–B6（`legal_actions` 占 43.6% 线上字节、
`grid` 无人读、`cells` 97.7% 空）**天花板是整循环的 4.8%**。值得做，但换不来数量级。
→ 真正的杠杆是**模型前向**：rollout 里 143.6 s（整循环 40.7%）。

### 已实施的两项位等价优化（`torch.equal` 逐位相同，不改模型语义）

**① `replay_log_probs` 不再逐行写设备张量**（原来每 plant 行写一次设备张量 +
`int(sel_pos[r])` 回读，**读标量会同步设备**）。
CPU **2.91 → 1.55 ms（1.9x）**、MPS **52.11 → 5.94 ms（8.8x）**。
第一版重写反而让 MPS 恶化到 155 ms（`float(tensor_element)` 触发 1,536 次同步），
改成一次 `index_put` + 一次 `torch.cat` 才修好。

**② 关系偏置的四次 permute 合成一次**（`relation_bias_from_indices`）。
`permute` 是 view 不搬数据，**代价在随后那次加法必须按跨步读这个 view**。原来三个
加法各付一次跨步读；改成全在 `(B,L,L,H)` 里查表相加、**只在最后 permute 一次**，
每个元素的加法次序不变。

| 路径（单核 CPU，`git stash` A/B） | 改前 | 改后 | 加速 |
|---|---|---|---|
| rollout `step_tokens`（batch=1, L=108） | 2.297 ms | 1.975 ms | **1.16x** |
| update `forward_sequences` | 290.7 ms | 248.0 ms | **1.17x** |
| update `everything_else`（反向+损失+优化器） | 545.2 ms | 390.1 ms | **1.40x** |
| **update 每步** | **838.7 ms** | **639.8 ms** | **1.31x** |

**反向也赚 1.40x 是最大的意外**：旧写法在反向里要为 3 个被 permute 过的分支各生成一份
跨步梯度，每层约 236 MB 中间梯度分配；新写法只要 1 份，约 118 MB。
→ **关系偏置在 CPU 上是分配受限的，不只是算术受限。**

**必须说清生效范围**（生产 rollout 和 update 跑在不同设备：`rollout_device=cpu`、
`update_device=cuda`）：

| 路径 | kernel | ② 是否生效 |
|---|---|---|
| **rollout（CPU，batch=1）** | eager（flex 要求 batch ≥ 32） | **生效** |
| update（CUDA，batch=256） | **FlexAttention**，偏置在 `score_mod` 里算 | **不生效** |
| update（CPU / dense） | eager | 生效 |

→ 对生产循环的实际收益 = **rollout 模型前向 143.6 s × 14% = 20.1 s**，
整循环 352.6 → 332.5 s = **1.06x**。update 的 1.31x 只落在 CPU/dense 配置上。
→ **生产 update 的 36.6% 关系偏置（flex `score_mod`）仍然没被碰到**，需在 CUDA 上实测。

### 结论二：精度（推翻 "bf16 3.85x"）

* `ppo_update_lr_1e4.json` 的顶层字段**没有 `warmup` 也没有 `attention_backend`** →

* **结论：bf16 安全但买不到东西，不开。**
