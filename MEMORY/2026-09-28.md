### 等价性论证的关键事实（不要重新推导）
- **Python `float` 就是 IEEE-754 binary64**，所以 list 与 numpy float64 表示同一个值；
  numpy 的 `arr[i] += x` 与 `list[i] += x` 是同一个 round-to-nearest-even 的 binary64 加法。
- 唯一一次 float64→float32 转换仍在同一批 binary64 输入上发生。已实测
  `torch.tensor(list, float32)` 与 `torch.from_numpy(np.asarray(list, float32))` 在
  **257 万对抗性 double**（非规格化数 / tie-to-even 边界 / 量级两端 / 溢出饱和）上**逐位一致**。
- **累加顺序必须保持不变**（浮点加法不结合）。测试语料必须含**同槽碰撞**用例，否则测不到顺序。
- `array.array('d')` **不可用**：它的切片是**拷贝不是视图**，`arr[a:b][i] += x` 会静默丢弃累加。
- 防御性测试：`test_accumulating_in_float64_is_required` 证明 float32 累加器会给出**不同的** float32 结果
  （7×`+=0.2` → 1.4000000000000001 vs 1.4000000953674316），所以该契约不会被无声降级。

### 两条高价值性能事实（非显然，勿忘）
1. **`F.linear` 在 M≥2 时比连续权重慢 3.2 倍**：`F.linear(x, W, b)` 走
   `addmm(bias, x, W.t())`，而 `W.t()` 是**非连续转置视图**，M≥2 掉出快速路径。
   实测 `Linear(4116,128)`：batch=1 → 6.06 µs，batch=4 → 47.59 µs；
   而 `x @ W.t().contiguous() + b` batch=4 → 15.78 µs。与 bias 无关、与线程数无关（1/5 线程同结果）。
   → **叶子估值批量化的收益被 ~44 µs 固定开销吃掉**（每批只有约 4.3 行），
   已否决；要吃到收益必须缓存连续转置权重，而权重每次 `optimizer.step()` 都变，是真实的陈旧风险。
2. **批量前向 ≠ 单行前向逐位相等**（GEMM vs GEMV 累加顺序不同）：随机稠密输入偏差 ≤3.1e-7，
   稀疏真实特征 ≤1.3e-8。若将来仍要做批量化，只能给**误差上界**，不能声称 `torch.equal`。

## 第五轮：精度预算调研（「容忍误差能不能换速度」）

**结论：不能。不是误差预算不够，而是这份代码的时间不在精度敏感的算术上。**
脚本：`scripts/precision_budget.py`、`scripts/decision_margin.py`。

### 误差预算（真实模拟器，160 次决策）
- margin 中位 **6.2e-4**，p90 4.0e-2；**10.6% 的决策 top1/top2 精确同分（margin=0，翻转无质量损失）**。
- 排除并列后（143 次）：**0/143 低于 1e-7**（float32 舍入量级翻不动任何决策）；
  1.4% 低于 1e-5；9.8% 低于 6.6e-5。
- 误差预算大致 **1e-5 ~ 1e-4**；1e-3 以上会翻转超过一半决策（56.2%）。

### 降精度全部更慢（batch=1，基线 15.72 µs）
| 方案 | 速度 | 误差 |
|---|---|---|
| 特征累加器 float32 | **1.00×（零收益）** | 0（该观测无碰撞） |
| fp16 权重+输入 | 0.27× | 2.5e-5 |
| 稀疏首层 nonzero gather | 0.18× | 3.7e-9 |
| bf16 autocast | 0.12× | 6.6e-5 |
| 仅首层 bf16 | 0.09× | 1.9e-5 |

根因：**`torch.backends.mkldnn.is_available() = False`、CPU capability = DEFAULT** ——
本机没有 oneDNN、没有 AVX512-BF16/AMX，低精度 matmul 退回未向量化参考实现。
随 batch 增大差距继续拉大（batch=1024 时 bf16 慢 24 倍）。
→ **这台机器上不存在「降精度换速度」这条路**；若换机器需重测这一条。

### 反直觉数据点
- 特征向量只有 **1.1%–3.3% 非零**（46–134/4116），但稀疏首层反而慢 5.6 倍：
  `Linear(4116,128)` batch=1 只要 6.59 µs（2.1 MB 权重命中 L2/L3），
  `torch.nonzero` + fancy indexing 的开销远超省下的乘加。**小批量 + 缓存驻留的形状上，稀疏 ≠ 快。**
- nn.Module 调度占前向 15.72 µs 中的约 5.7 µs（三层实际计算只有 6.59+2.13+1.29 = 10.0 µs）。

### 正确的问法
不是「能容忍多少误差」，而是「**能不能少算一些**」：减少叶子估值次数、剪枝更激进、
把 C++ 往返批得更狠 —— 改的是**算法**而非**数值精度**。
真实环境下 Python 侧全部优化到零，端到端也只能 164.6 → ~56 ms（2.9×），
瓶颈是 §5.5 那个 C++ 快照保存/恢复，与精度无关。

## 第六轮（20:20–20:35）：Apple Silicon 设备策略 —— 并更正第五轮的错误根因

用户质疑：「我是 Apple Silicon 啊，没有更快的路径吗？是不是 torch 装错了？」

### 先更正第五轮的错误结论（重要）

第五轮写的「本机没有低精度向量化路径，依据是 `mkldnn.is_available() = False` +
`get_cpu_capability() = DEFAULT`」——**推理链是错的**。这两个是 **x86 专用探针**：
官方 macOS arm64 wheel 本来就 `USE_MKLDNN=OFF`，`get_cpu_capability()` 在 ARM 上恒返回
`DEFAULT`，与硬件能力无关。结论**碰巧**没变，但证据必须换成实测。

### torch 没装错

```
机器   Apple M5 Pro, 15 核 (5 P + 10 E), uname -m = arm64
Python 3.14.6, sysconfig.get_platform() = macosx-11.0-arm64
torch  2.13.0，libtorch_cpu.dylib = Mach-O 64-bit ... arm64
构建   BLAS_INFO=accelerate  LAPACK_INFO=accelerate  USE_MKL=OFF
       USE_MKLDNN=OFF  USE_MPS=ON  AT_BUILD_ARM_VEC256_WITH_SLEEF  USE_OPENMP=ON
```
`torch.get_num_threads() = 5` == M5 Pro 的 P 核数，macOS 上正常，不是配置错误。

### 低精度：有路径，但更慢（Apple AMX 是 fp32 单元）

```
fp32 基线（手工函数式）   10.38 us
fp16 权重 + fp16 输入     43.11 us   0.24x   max|d|=6.951e-06
bf16 首层（fp32 其余）    31.29 us   0.33x   max|d|=1.741e-05
```

## 第十轮：BRANCH_SNAPSHOT_FAST 优化（任务 #7）

### 同进程 reset 不可复现 —— 根因与修复（上一轮未结的案子）

根因不是 effect system，是 `DataArray`：`mNextKey` 只在 `DataArrayInitialize` 里被设成
`1001U`，`DataArrayFreeAll` / `DataArrayDispose` 都不重置它。于是同一进程里第二个 episode
同一个对象拿到不同的 id —— `hidden.reanimations[14].tracks[27].attachment: 65601536 →
65732608`（key 1001 → 1003）。

修法：加 `DATA_ARRAY_KEY_INITIAL` 常量，在 `Initialize` / `Dispose` / `FreeAll` 三处都重置。
修完同进程 4 个 episode 两两完全一致。

**教训**：对象 id 只在「一代」内唯一，所以跨代递增的计数器会让两个本应相同的 episode
走出不同分支。这类 bug 用「对比两个进程」永远抓不到。

### 分项剖面：先量再改

给协议加了 `BENCH_SNAPSHOT <reps>`（保留，不是临时代码），在进程内分项计时。
level 8 / seed 30000 / tick 2192，载荷 86,424 B：

| 成分 | 轮次前 | 轮次后 |
|---|---|---|
| `EnvironmentSnapshotHash` | 77.2 µs | **9.7 µs** |
| `LawnSaveGameToMemory` | 89.1 µs | 86.8 µs |
| `LawnLoadGameFromMemory` | 68.7 µs | 68.4 µs |
| `EnvironmentObservation` | 23.2 µs | 22.2 µs |
| 端到端单分支 | 343.8 µs | **256.1 µs** |

**踩坑**：`measure([&] { return EnvironmentSnapshotHash(parent); })` 被编译器整段删掉了
（纯函数、返回值没用），哈希显示 0 µs。必须把结果喂给 `volatile` 汇聚点。
同样的坑也会让「优化后变快」变成假象。

### 两轮改动

1. `SaveGame.cpp`：`WriteChunkV4` 直接写进 payload，去掉三遍拷贝。48 个板面新旧写入器
   逐字节相同（用进程内双写器比对，因为载荷里有裸指针，跨进程比不了）。
2. `EnvironmentSnapshotHash`：逐字节 FNV-1a → **64 位字折叠 + MurmurHash3 fmix64**。
   逐字节版每个输入字节都是串行 xor/乘法链的一环，86 KB 上 77 µs。
   字折叠只有 2 条指令/8 字节，代价是差异只向高位扩散，所以必须加最终雪崩。

**哈希值是不透明的转置键，改写不算兼容性破坏** —— 前提是它真的只被当相等性用。
改之前确认过：`state_hash` 只出现在 `_transposition_key` 里，没有落盘数据集依赖它。

### 等价性怎么证明（这是本轮最值钱的部分）

筛选/深度预算拆分。**3/3 种子逐位一致**，真实 `advice()` 159.8 → 142.7 ms（1.12–1.16×）。

这个脚本**刻意不比较 `state_hash`**：它是转置键，改写哈希必然改变数字但不应改变任何
去重决策 —— 比较它会在一次合法优化上误报。这一点值得记住：**等价性断言必须挑「语义上
必须不变」的量，而不是「碰巧能拿到的所有量」。**

哈希质量单独用雪崩实测背书（3000 次真实载荷单比特翻转）：均值 32.08 bits（旧 30.74）、
最低 20（旧 19）、碰撞 0 —— 新哈希比旧的混得更好，不是「变快但变差」。
